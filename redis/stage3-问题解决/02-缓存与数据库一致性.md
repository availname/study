# 02 · 缓存与数据库一致性

缓存 = DB 的副本。DB 改了，缓存怎么跟上？这是缓存系统最纠结的设计题。

## 先立起一个认知：没有绝对一致，只有最终一致

缓存和 DB 是**两个独立系统**，更新不可能原子。方案设计的本质是：**把不一致的窗口压到最小、把不一致的代价降到可接受**。

## 四种方案逐一推演（谁先谁后很重要）

### 方案 1：先更新缓存，再更新 DB ❌

缓存成功、DB 失败 → 缓存是新数据、DB 是旧数据，**读请求永远拿到错的**。直接排除。

### 方案 2：先更新 DB，再更新缓存 ❌（并发下仍错）

看似合理，但并发写时序会乱：

```
线程A 更新 DB（价格=100）─┐
线程B 更新 DB（价格=200）─┤  DB 最终=200 ✓
线程B 更新缓存(200) ←──┐   │
线程A 更新缓存(100) ←──┘   缓存最终=100 ✗ 与 DB 不一致！
```

网络抖动让 A 的缓存写晚于 B，**旧值覆盖新值**。除非加分布式锁串行化（成本高），否则不用。

### 方案 3（业界主流）：先更新 DB，再删除缓存（Cache Aside）

**读**：先缓存 → 未命中查 DB → 回写缓存。
**写**：先更新 DB → **删除**缓存（不是更新！）。

为什么"删"而不是"更新"？
- 删除是幂等的、无并发覆盖问题（下次读自然重建）
- 很多场景写缓存代价高（要聚合多表数据），惰性重建更省

#### 方案 3 还残留的不一致窗口（推演）

```
读线程：缓存未命中 → 查 DB 得旧值
写线程：更新 DB → 删缓存
读线程：回写缓存（旧值！）  ← 删除发生在回写之前，旧值"复活"
```

发生条件苛刻（读请求恰好在写请求前查库、又恰好在写之后回写，且回写比删除慢），概率极低。**接受它**——下一次写或 TTL 到期自然修正。

### 方案 4：延迟双删（把残留窗口也尽量抹掉）

写操作后延迟几百毫秒**再删一次**，把"读线程慢回写"的残留也删掉：

```java
public void update(Product p) {
    db.update(p);
    redis.delete(cacheKey);                     // 第一次删
    // 异步延迟双删：不阻塞主流程
    delayExecutor.schedule(() -> redis.delete(cacheKey), 500, TimeUnit.MILLISECONDS);
}
```

延迟时间 ≈ 一次读请求的总耗时（几百 ms 经验值）。用 MQ 做延迟投递更可靠（避免内存延迟队列应用重启丢失）——**这就是 MQ 延迟消息的又一用法**（[mq 教学坑五](../../mq/踩坑实录-完整复盘.md)同款思路）。

## 先删缓存再更新 DB？推演后排除

```
写线程：删缓存 → [此刻读线程：未命中→查DB(旧值)→回写缓存(旧值！)] → 更新 DB
→ 缓存长期停留旧值，比方案3的窗口大得多。排除。
```

## 生产级保障：订阅 binlog 删缓存（解耦版）

应用双写（改 DB + 删缓存）有遗漏风险（有人改库忘了删缓存）。更强的方案：

```
DB 更新 → binlog → Canal/Debezium 伪装从库解析 → 发 MQ → 消费者删缓存
```

- **业务代码零侵入**：只管改 DB
- 消费失败可重试、可补偿（MQ 的老三样：幂等 + 重试 + 死信）
- 延迟略增（百 ms 级）

选型：普通业务用方案 3；对一致性要求高、又不想侵入代码 → binlog 方案。

## 决策表

| 方案 | 一致性 | 侵入性 | 结论 |
|------|--------|--------|------|
| 先缓存后 DB | 差 | — | ❌ |
| 先 DB 后**更新**缓存 | 并发覆盖 | 中 | ❌ |
| **先 DB 后删缓存**（Cache Aside） | 极小窗口 | 低 | ✅ 默认选它 |
| 延迟双删 | 更小窗口 | 中 | ✅ 高要求加它 |
| binlog → MQ → 删缓存 | 最终一致 | 零侵入 | ✅ 复杂系统 |

## 强一致怎么办？

真需要"改完立刻读到新值且绝无旧值"——**别用缓存**（读 DB），或业务上用版本号/分布式锁串行化读写。缓存天生是为"容忍毫秒级陈旧"的场景服务的。

## 面试问法

**Q: 缓存与数据库一致性怎么保证？**
A: 接受最终一致，业界默认 Cache Aside：读-缓存未命中回写；写-先更新 DB 再**删**缓存（删除幂等，避免并发更新覆盖）。残留窗口极小，高要求场景加延迟双删（或 MQ 延迟二次删除）；跨团队系统用 binlog（Canal）→ MQ → 删缓存做到零侵入最终一致。先更新缓存再改 DB、先删缓存再改 DB 都因失败/并发窗口被排除。强一致场景放弃缓存直读 DB。
