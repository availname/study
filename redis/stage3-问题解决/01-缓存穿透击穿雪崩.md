# 01 · 缓存三大天劫：穿透、击穿、雪崩

> 🎬 **配套交互演示（容易看懂版）**：[diagrams/cache-3problems.html](../../diagrams/cache-3problems.html)——奶茶店比喻：货架=Redis、后厨=MySQL，三种灾难各配“演示+解法”按钮，压力条可视化后厨被打爆的过程。

缓存系统最经典的三个故障模型。一张表先分清（面试必背）：

| | 穿透 (Penetration) | 击穿 (Breakdown) | 雪崩 (Avalanche) |
|--|-------------------|------------------|------------------|
| 查的是什么 | **DB 里也没有**的数据 | **热点单个 key** | **大面积多个 key** |
| 命中哪里 | 恶意/异常请求，缓存永远不命中 | 热点 key **恰好过期**的瞬间，万请求直冲 DB | **同一时刻**大量 key 集中失效或 Redis 整体挂 |
| 比喻 | 探子反复敲一堵不存在的门 | 千军万马冲一座城门 | 城墙同时塌了全段 |

## 一、穿透：查不存在的数据，缓存形同虚设

**场景**：攻击者用随机 ID 狂刷 `GET /user/-1`——`-1` 在缓存和 DB 都不存在 → 每次请求都穿透到 DB → DB 被打挂。

### 方案 1：缓存空值（最常用）

未查到也往缓存写一个"空标记"，短 TTL：

```java
public User getUser(long id) {
    String key = "user:cache:" + id;
    String json = redis.opsForValue().get(key);
    if (json != null) {
        return "NULL".equals(json) ? null : JSON.parseObject(json, User.class);
    }
    User user = userDb.findById(id);
    if (user == null) {
        // 空 TTL 短（1~5 分钟），DB 补上数据后自然恢复
        redis.opsForValue().set(key, "NULL", Duration.ofMinutes(2));
        return null;
    }
    redis.opsForValue().set(key, JSON.toJSONString(user), Duration.ofHours(1));
    return user;
}
```

适合"空 key 数量可控"的场景；攻击 ID 无限随机时空值缓存也防不住（塞爆内存），配合方案 2。

### 方案 2：布隆过滤器（Bloom Filter）

在缓存前加一道"可能存在"检查：所有合法 ID 预载入布隆过滤器；查库前先问过滤器——**说不存在则一定不存在**，直接拒绝。

```java
// Redisson 自带 RBloomFilter，或 Redis 的 BF.ADD（RedisBloom 模块）
bloomFilter.add(legalUserId);       // 数据写入时同步登记
if (!bloomFilter.contains(id)) return null;   // 一定不存在，秒拒
```

原理：多个哈希函数把元素映射到位数组；**误判率可调**（说存在可能误判，说不存在绝对正确）。适合"合法 key 集合基本不变"的场景（商品ID、用户ID）；要支持删除用布谷鸟过滤器。

### 方案 3：入口校验

id < 0、格式非法、越权 ID 在网关/参数校验层直接拒——最便宜的防线最先上。

## 二、击穿：热点 key 过期瞬间，万级并发冲库

**场景**：某爆款商品缓存 1 小时到期，瞬间 1w QPS 同时发现未命中，全部冲向 DB 查同一行。

### 方案 1：互斥锁，只放一个请求去重建

```java
public Product getDetail(long id) {
    String key = "product:cache:" + id;
    String json = redis.opsForValue().get(key);
    if (json != null) return parse(json);

    // 未命中 → 抢重建锁（只有一个人去查 DB）
    String lockKey = "lock:rebuild:" + id;
    String requestId = UUID.randomUUID().toString();
    Boolean locked = redis.opsForValue().setIfAbsent(lockKey, requestId, Duration.ofSeconds(10));
    if (Boolean.TRUE.equals(locked)) {
        try {
            Product p = productDb.findById(id);            // 只有持锁者查库
            redis.opsForValue().set(key, JSON.toJSONString(p), Duration.ofHours(1));
            return p;
        } finally {
            releaseLock(lockKey, requestId);               // Lua 校验 requestId 再删（stage3/03）
        }
    }
    // 没抢到锁的：短暂等待后重读缓存（重建者很快会填上）
    Thread.sleep(50);
    return getDetail(id);
}
```

其余请求短暂自旋等待——DB 只承受 1 个查询。demo 的 `/breakdown` 接口完整演示了这个模式。

### 方案 2：逻辑过期（热点 key 永不过期）

物理上不设 TTL，value 里**内嵌过期时间字段**：

```java
// 命中后发现逻辑过期 → 返回旧值 + 异步起一个线程去重建（不等重建完成）
```

优点：永不击穿、无锁等待；缺点：短期返回旧数据、实现复杂。适合极端热点（首页商品）。

### 方案 3：热点永不过期 + 后台定时刷新

顶流 key 干脆不设 TTL，后台 job 定时刷。

## 三、雪崩：大面积同时失效

两种成因、两种对策：

### 成因 1：同一批 key 设置了相同 TTL → 同时过期

**对策：TTL 加随机抖动**

```java
long ttl = baseTtl + ThreadLocalRandom.current().nextLong(0, 300);  // 基础+0~300s 随机
```

一行代码消灭"同时失效"。

### 成因 2：Redis 整体宕机 → 全部请求打 DB

**对策（多级防御）**：
1. **多级缓存**：本地缓存（Caffeine，进程内）挡第一波 → Redis 挡第二波 → DB 兜底
2. **熔断限流**：Sentinel 对 DB 访问限流，宁可返回部分降级数据也不挂 DB
3. **高可用架构**：哨兵/集群，Redis 不单点（stage2/05）
4. **预热**：大促前把热点数据提前灌入缓存

## 三大问题联合防御清单（上线 checklist）

- [ ] 所有缓存读取都有"未命中查 DB + 回写"路径，回写**必带 TTL**
- [ ] TTL 有随机抖动
- [ ] 已知查询不存在的场景 → 空值缓存（短 TTL）
- [ ] 可枚举合法 ID 的业务 → 布隆过滤器前置
- [ ] 热点 key → 互斥锁重建 或 逻辑过期
- [ ] 多级缓存 + DB 限流熔断兜底
- [ ] 监控：缓存命中率（命中率骤降 = 穿透/失效事故的前兆）、DB QPS 突增告警

## 面问法

**Q: 穿透、击穿、雪崩的区别和解决方案？**
A: 穿透是查不存在的数据永远不命中——空值缓存+布隆过滤器+参数校验；击穿是单个热点 key 过期瞬间并发冲库——互斥锁重建（一人查库他人等待）或逻辑过期；雪崩是大面积同时失效——TTL 随机抖动防同批过期，Redis 高可用+多级缓存+DB 熔断限流防整体宕机。
