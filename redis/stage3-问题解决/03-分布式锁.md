# 03 · 分布式锁：SETNX 到 RedLock

> 🎬 **配套交互演示（容易看懂版）**：[diagrams/distributed-lock.html](../../diagrams/distributed-lock.html)——公共储物柜：三人抢锁（NX）、B 拿 A 的钥匙开柜被拒（requestId 校验）、持锁人断电→EX 自动开锁（防死锁兜底），全流程可视化。

单机多线程用 JVM 锁（synchronized/ReentrantLock）；**多实例部署后 JVM 锁失效**——两台机器各锁各的。跨进程互斥需要一把"所有实例都看得见"的锁：分布式锁。

```
实例1 ─┐                      ┌→ 抢到 → 执行业务 → 释放
       ├──  SET lock:sku1 XX NX  ┤
实例2 ─┘                      └→ 抢不到 → 失败/等待/重试
```

典型场景：定时任务防重复执行、库存扣减防并发超卖、缓存重建互斥（上一章的方案 1）。

## 演进一：SETNX + EXPIRE 的经典错误

```java
// ❌ 经典错误：两条命令不是原子的
redis.setnx("lock:sku1", clientId);   // 抢锁成功
redis.expire("lock:sku1", 10);        // ← 若在两句之间进程崩溃，锁永不过期 → 死锁！
```

## 演进二（正确基础版）：一条命令三合一

```java
// ✓ 原子抢锁 + 自动过期，requestId 证明"这锁是我的"
Boolean ok = redis.opsForValue().setIfAbsent("lock:sku1", requestId, Duration.ofSeconds(10));
if (Boolean.TRUE.equals(ok)) {
    try { doBusiness(); }
    finally { releaseLock(); }
}
```

`SET key value NX EX 10` 单命令原子执行，不存在"抢到锁还没来得及设过期"的窗口。

## 演进三（必须）：释放锁要校验"是不是自己的锁"

**为什么会误删别人的锁**：A 抢到锁（10s 过期）→ A 业务执行了 12s → 锁自动过期 → B 抢到锁开始干活 → A 终于执行完，`DEL lock` → **把 B 的锁删了**！

```java
// ❌ 直接删 = 可能误删别人的锁
redis.delete("lock:sku1");

// ✓ Lua 原子"校验身份再删"（get+del 两步不能拆）
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT = new DefaultRedisScript<>("""
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    end
    return 0
    """, Long.class);

public void releaseLock(String lockKey, String requestId) {
    redis.execute(UNLOCK_SCRIPT, List.of(lockKey), requestId);
}
```

**requestId 用唯一值**（UUID/实例ID+线程ID）——每个持锁者只认自己的锁。

## 演进四：锁提前过期怎么办——续期（看门狗）

业务执行 12s > 锁 TTL 10s 的问题，两个方向：

1. **兜底版**：TTL 设得足够大（业务耗时的数倍）——简单，但锁卡死时间也变长
2. **看门狗版（主流）**：后台线程每隔 1/3 TTL 检查"锁还是我持有的"就续期

```java
// Redisson 的 watchdog：不手动指定 TTL 时自动启用，默认锁 30s，每 10s 续回 30s
RLock lock = redisson.getLock("lock:sku1");
lock.lock();            // 自动续期，直到 unlock
try { doBusiness(); }
finally { lock.unlock(); }
```

**Redisson unlock 内部同样是 Lua 校验 requestId**（演进三），且业务代码零心智负担——生产首选。

### 为什么要 Redisson 而不是手写？

| 手写 SETNX | Redisson |
|-----------|----------|
| 看门狗要自己写后台线程 | `lock()` 自动续期 |
| 重试/自旋自己写 | `tryLock(waitTime, leaseTime)` 一步到位 |
| 可重入自己实现 | 支持可重入（同线程再 lock 不死锁，内部 hash 记录重入次数） |
| 异常清理容易漏 | 官方实现经过大规模验证 |

## 完整的生产级代码骨架（demo 有可运行版）

```java
public boolean doWithLock(String resource, Supplier<Boolean> biz) {
    RLock lock = redisson.getLock("lock:" + resource);
    boolean acquired = false;
    try {
        // 两参 tryLock：不传 leaseTime → 看门狗启用（默认 30s，每 10s 续回）
        // 注意：三参 tryLock(3, 30, SECONDS) 传了 leaseTime 反而会关闭看门狗！
        acquired = lock.tryLock(3, TimeUnit.SECONDS);
        if (!acquired) return false;           // 没抢到：快速失败或走降级
        return biz.get();
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        return false;
    } finally {
        if (acquired && lock.isHeldByCurrentThread()) lock.unlock();   // 只解自己持有的
    }
}
```

## 锁的正确性边界（诚实面对）

Redis 分布式锁的固有弱点：

1. **主从切换丢锁**：A 在主库抢到锁 → 主库宕机 → 锁还没同步到从库 → 新主上 B 又抢到 → **双持锁**。
2. GC 停顿/时钟跳变可以让"过期判断"失真。

**RedLock**（Redis 官作者提出的向多台独立 Redis 抢锁、过半成功才算）争议很大——Martin Kleppmann 指出其在时钟跳变下不安全（这场论战的完整展开、以及 **fencing token** 正解，见 [05-RedLock争议与FencingToken](05-RedLock争议与FencingToken.md)）。**务实结论**：

- Redis 锁用于**效率**场景（防止重复干活，偶尔双持也无大碍）：完全够用，Redisson 首选
- **正确性**场景（绝不允许并发，如资金扣减）：锁只做**第一道防线**，真正的正确性靠**DB 层兜底**——乐观锁 `WHERE stock>0`、唯一索引、状态机 CAS。**Redis 锁挡 99% 并发，DB 约束兜住 100% 正确**——这与 mq-mall 秒杀的双保险（Redis 预扣 + DB WHERE stock>0）完全同构。

## 面试问法

**Q: Redis 分布式锁怎么实现？**
A: `SET key requestId NX EX ttl` 原子抢锁（一条命令避免 setnx+expire 非原子死锁）；释放用 Lua 校验 requestId 再删（防误删他人锁，如 A 执行超时锁过期 B 获锁后 A 误删）；执行超过 TTL 用看门狗续期（Redisson lock() 默认 30s 每 10s 续）。生产直接用 Redisson（可重入/tryLock/watchdog 全内置）。

**Q: Redis 锁可靠吗？主从切换呢？**
A: 异步复制导致主挂切换后可能双持锁；RedLock 试图解决但有时钟安全争议。务实分层：效率场景 Redis 锁足够（Redisson）；正确性场景 Redis 锁做第一道防线、DB 层乐观锁/唯一约束做最终兜底。
