# 05 · ZSet：实时热搜榜

微博热搜每分钟都在变——实时更新、热度随时间衰减、还要防刷。ZSet 的招牌场景，也是最完整的"score 算法设计"案例。

## 需求拆解（微博热搜的产品行为）

| 功能点 | 技术形状 |
|--------|---------|
| 某词条被搜索/讨论 → 热度上涨 | 加分 |
| 榜单实时按热度排序，前 50 | ZREVRANGE |
| 热度随时间衰减（早上的爆点到晚上该降） | 定时衰减任务 |
| 用户点"查我搜的词排第几" | ZREVRANK |
| 同一词条被同一人狂刷 → 防刷 | Set 记名 + 限次 |
| 榜单只留前 N，历史下榜 | ZREMRANGEBYRANK |

## 核心：score 是什么（热度算法设计）

### 版本一：加权热度

不同行为价值不同（转发 > 评论 > 点赞 > 搜索）：

```java
// 各行为发生时，给词条加对应权重分（原子）
ZINCRBY hot:search:20261105 1   词条X      // 搜索 +1
ZINCRBY hot:search:20261105 2   词条X      // 点赞 +2
ZINCRBY hot:search:20261105 5   词条X      // 评论 +5
ZINCRBY hot:search:20261105 10  词条X      // 转发 +10
```

### 版本二：热度 + 时间衰减

榜单要"新爆点顶上去，旧爆点沉下去"。两种做法：

**做法 A：定时衰减任务**（简单，分钟级榜单够用）

```bash
# 定时任务每 5 分钟：全榜分数 × 0.98（半衰期约 2.8 小时）
ZADD hot:search:20261105 的新分数...   # 读出→乘0.98→写回
# 或更快的原子技巧：对全量做衰减没有单命令，用 ZINTERSTORE 配合权重？也不行——
# 所以实践中：遍历 TOP 1000（榜单容量有限，遍历成本低）逐个 ZADD 覆盖
```

**做法 B：score 混合编码（免衰减，数学流）**

score = `热度值 × 常数 + 最后更新时间戳`，排序即"热度优先、同热度新者先"；衰减由"旧词条长期不被更新、相对排名自然下滑"体现。**不用定时任务，但热度不可读**（score 是混合值）——两个版本按需选。

### 榜单容量控制（防大 Key）

```bash
ZREMRANGEBYRANK hot:search:20261105 0 -1001    # 只留前 1000，尾巴随时裁
```

热搜本来只展示前 50，留 1000 条绰绰有余。

## 防刷：Set + 限次组合（与验证码防刷同构）

```bash
# 用户 u1 对词条"XX"的搜索计数（防一人刷爆一个词条）
INCR hotsearch:count:u1:XX:20261105      # 首次 INCR 后 EXPIRE 当日
# 计数超过 3 → 本次不再加分
```

或者更狠：`SADD hotsearch:voters:XX u1` + `SCARD` 限人数。**原理与 [01 验证码防刷](01-String-短信验证码登录与防刷.md) 完全相同**：计数闸门 + Lua 原子化。

加分操作防并发乱序（计数判断+加分）用 Lua：

```lua
-- vote.lua：每人每词条限 3 次热度贡献
local c = redis.call('INCR', KEYS[2])
if c == 1 then redis.call('EXPIRE', KEYS[2], 86400) end
if c > 3 then return 0 end               -- 超限，不加热度
redis.call('ZINCRBY', KEYS[1], ARGV[1], ARGV[2])
return 1
```

## 查询端

```bash
ZREVRANGE hot:search:20261105 0 49        # 热搜前 50（页面主榜单）
ZREVRANK hot:search:20261105 词条X        # "第xx位"角标
ZSCORE hot:search:20261105 词条X          # 热度值展示
```

三个都是 O(logN)，百万词条毫秒响应。

## 多维度榜单 = 多个 ZSet（组合拳）

真实热搜产品是**一组榜单**：总榜、科技榜、娱乐榜、地区榜——同一行为同时写多个 ZSet（一次事件 `ZINCRBY` 多个榜的 key）。榜单间数据冗余换取查询零聚合。每小时榜单快照落 DB 供历史回看（"昨天 14 点的热搜"）。

## 生产增强

| 增强 | 做法 |
|------|------|
| 榜单重建 | Redis 挂了榜单可丢——行为流水在 MQ/DB，重放流水即可重建榜单（对账同款思路） |
| 全网合并 | 多机房行为事件汇到 Kafka → 单点消费写入榜单（防多地分写竞争） |
| 榜单缓存 | 前 50 榜单页 5s 缓存一份 JSON，扛住榜单页的读洪峰（ZREVRANGE 虽快，页面级缓存更省） |

## 面试问法

**Q: 设计一个实时热搜榜。**
A: ZSet 存词条(score=热度)，行为加权 ZINCRBY（转发>评论>点赞>搜索）；时间衰减用定时任务乘衰减系数或 score 混合时间戳编码；ZREMRANGEBYRANK 限榜单容量防大 Key；防刷用"用户+词条"当日计数 Lua 原子限次；查询 ZREVRANGE/ZREVRANK 都是 O(logN)。榜单是可重建数据——行为流水在 MQ/DB，Redis 挂了重放重建，可靠性要求低所以敢放 Redis。
