# 07 · HyperLogLog：大促 UV 统计大屏

大促零点，运营大屏上的"实时 UV：2,347,891"每秒都在跳——这个数字怎么来的？HLL 用 12KB 回答它。

## 需求（数据产品视角）

| 功能点 | 技术形状 |
|--------|---------|
| 每个页面/活动页的当日 UV | 去重计数 |
| 大屏秒级刷新 | 实时读 |
| 月报/活动期总 UV | 多日合并 |
| **允许千分之几误差**（大盘数字） | 误差换内存 |
| 但"某用户今天来过没"精确判断 | 不归 HLL 管 |

## 实现

```bash
# 每个页面每天一个 key；用户访问即 PFADD（重复访问自动去重，幂等）
PFADD uv:page:detail:20261105 u1 u2 u1 u3 u2

PFCOUNT uv:page:detail:20261105          # 当日 UV → 3（标准误差 0.81%）
PFMERGE uv:page:detail:202611            # 月度合并：把每天的 HLL 合并成月 HLL
PFCOUNT uv:page:detail:202611            # 月 UV
```

```java
// Java：埋点上报到达时
redis.opsForHyperLogLog().add("uv:page:" + pageId + ":" + today(), userId);

// 大屏接口
Long uv = redis.opsForHyperLogLog().size("uv:page:" + pageId + ":" + today());
```

PFADD 是 O(1) 常数耗时——**百万 QPS 埋点直接打 Redis 也扛得住**（当然生产会先过 Kafka 削峰再批量 PFADD，与 mq 教学的日志管道同构）。

## 误差 0.81% 到底意味着什么（选型的关键理解）

| 日 UV 真实值 | HLL 输出 | 绝对偏差 |
|-------------|---------|---------|
| 100 | 99~101 | 个位数 |
| 100 万 | ~99.2 万 | 约 8000 |
| 5000 万 | ~4960 万 | 约 40 万 |

- **大屏/大盘/日报**：业务只关心量级和趋势 → 0.81% 完全可接受
- **财务结算/佣金分成按 UV**：错 8000 个就是真金白银 → **必须精确**（Set 或 DB `COUNT(DISTINCT)`）
- **风控名单**（这个设备出现过吗）→ HLL 根本不提供成员查询，用 Set/Bitmap

**选型三句话**：
1. 只要"有多少不同"不要"谁是谁" → HLL
2. 要精确判断"某个在不在" → Set（量小）/ Bitmap（值域有限 0/1 场景）
3. 都要 → HLL 上大屏 + Set/DB 留精确明细（双轨）

## 12KB 的代价与秘密

HLL 是**概率数据结构**：用 16384 个"寄存器"，每个存某哈希前缀下观察到的最大前导零数，以此估算基数。代价：

- 有 0.81% 标准误差（哈希均匀性保证）
- **不能查成员、不能删除**（没有"从 UV 里移除某用户"这种操作）

12KB 固定成本与基数无关——1 个 UV 和 1 亿 UV 都是 12KB。**日 key 按天分，月合并用 PFMERGE**，避免单 key 承载无限时间跨度。

## 与其它计数方案的总对账（本篇最值得背的表）

| 方案 | 内存（亿级） | 精确 | 可查成员 | 场景 |
|------|-------------|------|---------|------|
| Set | 数 GB | ✅ | ✅ | 小规模精确去重、名单类 |
| Bitmap | ~12MB（值域映射） | ✅ | ✅（0/1 场景） | 签到、活跃标记 |
| **HLL** | **12KB 固定** | ❌ 0.81% | ❌ | UV/大盘计数 |
| DB COUNT(DISTINCT) | 无 | ✅ | ✅ | 离线报表（慢） |

## 大屏链路（把场景拼完整）

```
客户端埋点 → Kafka（削峰/解耦，mq 教学场景）→ 消费者
   ├→ PFADD（实时 UV，Redis）
   ├→ 明细落 DB/数仓（精确对账与离线分析）
   └→ Flink/Spark 离线 job 出日报表（与 HLL 大屏对账，误差内视为正常）
```

HLL 数字与数仓精确数之间的差异是**已知且被接受的**（产品文档写明"UV 为估算值"）——技术方案要让业务方知情并确认，这叫**口径对齐**，比代码本身更重要。

## 面试问法

**Q: 亿级页面的 UV 统计怎么做？**
A: HyperLogLog：PFADD 按页面+天分 key 埋点去重，PFCOUNT 读数，PFMERGE 合并月报。固定 12KB 与基数无关，标准误差 0.81%。选型对比：要精确或查成员用 Set/Bitmap（贵），只要量级大盘用 HLL（省）。业务上需与数仓口径对齐并明示"估算值"；财务类精确 UV 不用 HLL。埋点入口过 Kafka 削峰批量 PFADD。
