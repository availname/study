# 04 · 缓存设计模式与选型总结（Stage 4 收官）

前三章是"术"，本章是"道"：缓存的经典设计模式 + 一套完整选型心法。

## 一、经典缓存模式

### 1. Cache Aside（旁路缓存）—— 90% 场景的标准答案

```
读：先缓存 → 命中返回；未命中 → 查 DB → 回写缓存（带 TTL）
写：先更新 DB → 删除缓存
```

就是 [stage3/02](../stage3-问题解决/02-缓存与数据库一致性.md) 的结论。特点：**应用自己管理缓存**，最简单最可控。

### 2. Read/Write Through（读写穿透）

应用只和缓存层对话，缓存层负责读写 DB（Redis 不原生支持，需封装"缓存服务"）。适合团队想收口缓存逻辑、屏蔽细节的中台场景。

### 3. Write Behind（异步写回）

先写缓存，异步批量刷 DB。**快**，但缓存挂了丢数据——适合点赞计数、浏览量（丢了少量无所谓，攒批落库反而省 DB）。mq-mall 的秒杀"Redis 预扣 + MQ 异步落库"正是这个思想的工程化（用 MQ 保证落库不丢）。

### 4. 多级缓存（本地 + 分布式）

```
请求 → [Caffeine 本地缓存 ~µs] → [Redis 分布式 ~ms] → DB
```

本地缓存挡住最热的那 5%，Redis 挡住 90%，DB 只接漏网。注意本地缓存的**一致性更弱**（多实例各自的本地缓存要用 Redis Pub/Sub 或 MQ 广播失效）。

## 二、TTL 设计心法

| 数据 | TTL 建议 |
|------|---------|
| 常规业务缓存 | 10min~1h + **随机抖动**（stage3/01 防雪崩） |
| 验证码/Token | 业务决定的短 TTL（3~5min） |
| 极端热点 | 逻辑过期/不设 TTL 后台刷 |
| 空值缓存（穿透防御） | 短 TTL（1~2min） |
| 分布式锁 | 租期制（看门狗续期，stage3/03） |

**没有 TTL 的缓存 = 没有自我修复能力**。除了锁和刻意永久的极端热点，缓存一律带 TTL。

## 三、命中率：缓存是否有效的唯一硬指标

```
命中率 = hits / (hits + misses)      INFO stats 的 keyspace_hits/misses
```

- 健康业务缓存 > 90%
- 命中率骤降的排查顺序：①大面积失效/穿透事故 ②maxmemory 打满开始淘汰（evicted_keys）③业务变更导致 key 规律变化

## 四、Redis 使用规范的"军规十条"

1. Key 命名 `业务:对象:ID`，杜绝裸名 key
2. 缓存回写**必带 TTL**
3. 禁 KEYS/FLUSHALL，SCAN 分批扫
4. 集合类 key 设上限（LTRIM/ZREMRANGEBYRANK/分桶），防大 Key
5. 复合逻辑用 Lua，不用"GET 再 SET"的竞态写法
6. 分布式锁用 Redisson，释放校验 requestId
7. 大 Key 删除用 UNLINK
8. 值序列化统一 JSON，key 统一字符串
9. 内存策略选对（纯缓存 allkeys-lru；有锁 key 分实例 noeviction）
10. 监控四指标：命中率 / evicted_keys / 慢查询 / 内存水位

## 五、何时不用 Redis（避免"手里有锤看啥都是钉"）

| 场景 | 更好的选择 |
|------|-----------|
| 强一致资金数据 | DB 是 source of truth，Redis 只加速 |
| 消息必达的 MQ | RabbitMQ/RocketMQ（Redis Stream 可靠性不足） |
| 全文检索 | Elasticsearch |
| 海量冷数据 | DB/对象存储 |
| 复杂关联查询 | SQL |
