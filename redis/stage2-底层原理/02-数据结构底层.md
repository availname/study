# 02 · 数据结构底层：值的"外壳"与"内核"

`TYPE` 看到的是**外壳**（string/hash/list/set/zset），底层实际用的结构叫**编码**（`OBJECT ENCODING key` 查看）。Redis 对每种外壳准备了多种内核结构，**小数据用紧凑省内存的，大了自动换成快的**——这是"高效数据结构"的具体含义。

## 先看一眼编码切换（动手）

```bash
SET n 1
OBJECT ENCODING n        # → "int"（纯数字直接存 int）
SET s hello
OBJECT ENCODING s        # → "embstr"（短字符串）
SET s aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
OBJECT ENCODING s        # → "raw"（长字符串，>44 字节）
RPUSH list1 a b
OBJECT ENCODING list1    # → "listpack"（7.0 小列表用紧凑列表）
RPUSH list1 [1MB 大元素]
OBJECT ENCODING list1    # → "quicklist"（大了换快结构）
```

## String 的内核：SDS（简单动态字符串）

不是 C 字符串（`\0` 结尾），SDS 多了一个 **len 头**：

```
┌─────┬─────────┬──────┐
│ len │ alloc   │ data │   O(1) 拿长度；二进制安全（可存图片/JSON 任意字节）
└─────┴─────────┴──────┘   预分配空间，追加省 realloc
```

- **二进制安全**：`SET k "\0abc"` 也合法——所以能存序列化字节
- 三种编码：`int`（≤ long）→ `embstr`（≤44 字节，头和数据一次分配，省一次内存寻址）→ `raw`

## Hash / ZSet / Set 的"小数据紧凑内核"

Redis 7.0 用 **listpack**（紧凑列表，元素连续存放，替代旧 ziplist）：

```
listpack: [len][elem1][len][elem2]...   连续内存，无指针，省内存但插入删除要整体挪
```

小 Hash（默认 ≤128 个 field 且 value ≤64B）用 listpack 存储，**遍历快、内存省**；超过阈值自动转 dict（哈希表）。这就是"小对象用紧凑编码"——百万小 Hash 节省的内存非常可观。

阈值可调（一般不动）：

```bash
CONFIG GET hash-max-listpack-entries   # 128
CONFIG GET hash-max-listpack-value     # 64
```

## dict：全局哈希表与渐进式 rehash

Redis 所有 key 都在一个**全局 dict** 里。哈希表扩容要搬移所有元素——百万 key 一次性搬会卡死，所以用**渐进式 rehash**：

```
dict:  ht[0]（旧表，正在被搬出）  ht[1]（新表，正在搬入）
每次增删改查顺手搬一个桶 + 后台定时搬
查找：先查 ht[0]，查不到再查 ht[1]
搬完：ht[1] 变成新的 ht[0]
```

**问答**：rehash 期间读写会不会丢？不会，两表都查/写新表。内存会短暂翻倍（两表并存）——大实例扩容时内存告警要预留。

## ZSet 的内核：跳表（skiplist）——面试最爱

ZSet 要同时支持"按 member 查 score（O(1)）"和"按 score 范围排名（O(logN)）"，所以用**跳表 + dict 双结构**：

```
跳表（按 score 排序的多层链表）：
L3: 1 ────────────────────→ 9
L2: 1 ─────→ 5 ───────────→ 9
L1: 1 → 3 → 5 → 7 → 9
查找 7：从高层往右跳（9>7 退回）→ 5 → 下层 → 7，O(logN)
```

- 每个节点随机决定层数（抛硬币式，概率 p=0.25 升层）——**免旋转、实现简单**，性能与平衡树相当
- dict 负责 member→score 的 O(1) 查询（`ZSCORE`）
- 为什么不用红黑树？跳表实现简单、范围查询天然顺链表走（ZRANGEBYSCORE）、并发改造容易。官方原话大意："跳表和平衡树性能相当，代码简单得多"

成员数小（≤128 且元素 ≤64B）时 ZSet 也是 listpack 编码。

## List 的内核：quicklist = 双向链表串 listpack

7.0 的 List = **quicklist**：多条 listpack 用双向链表串联。兼得"链表好插删"+"紧凑段省内存"，每段默认大小 `list-max-listpack-size` 控制（-2 表示每段 8KB）。

## Set 的内核

- 全整数且数量少 → `intset`（有序整数数组，省内存）
- 一般 → dict（member 为 key，value 全 NULL）

## 为什么要懂这些（务实价值）

1. **内存优化**：小对象凑紧凑编码（比如 Hash 字段控制短小），亿级 key 省一半内存不是吹的
2. **性能预期**：知道什么时候 O(1)、什么时候 O(N)（listpack 满了转 dict、Set 交并集 O(N)）
3. **面试硬通货**：跳表为什么不用红黑树、渐进式 rehash 为什么不卡——高频考点

```bash
# 内存分析利器：看一个 key 的编码 + 内存占用
OBJECT ENCODING key
MEMORY USAGE key SAMPLES 0
```

## 面试问法

**Q: ZSet 底层为什么用跳表不用红黑树？**
A: 双结构：dict 保 O(1) 按 member 查 score，跳表保 O(logN) 范围/排名。跳表相对红黑树：实现与调试简单、范围查询沿链表顺序走天然友好、层数随机生成无旋转；性能同量级。小数据量时整体退化为 listpack 更省内存。

**Q: 渐进式 rehash 是什么？**
A: 扩容时新旧两表并存，每次读写顺手迁移一个桶+后台任务迁移，避免一次性搬移百万 key 阻塞主线程；查询先查旧表再查新表，写只写新表；迁移期间内存短暂翻倍。
