# 05 · 高可用三件套：主从复制、哨兵、集群

单机 Redis 两大死穴：**挂了就没**（可用性）和**内存封顶**（容量）。三件套逐级解决。

## 一、主从复制：一主多从，数据冗余

```
        ┌── 写（SET）──→ [主 master]
应用 ───┤                     │ 异步复制（RDB全量 + 命令流增量）
        └── 读（GET）──→ [从 slave1] [从 slave2]   读写分离
```

### 复制原理（面试骨架）

1. **首次全量**：从库发 `PSYNC` → 主库 BGSAVE 生成 RDB → 发给从库载入 → 期间的写命令缓存在"复制缓冲区"→ 增量补发
2. **长期增量**：主库每条写命令实时发给从库（repl_backlog **环形缓冲区**）
3. **断线重连**：从库带上 offset 请求增量；offset 还在缓冲区范围内 → 续传；被冲掉了 → 退化全量

### 关键认知：异步复制 = 可能丢数据

主库写入 → **不等**从库确认就回复客户端 → 主库宕机时，从库可能落后若干毫秒的写入 → 提升从库为主后**这部分写入丢失**。

> 这是 Redis 高可用的固有取舍（对比：Kafka 的 acks=all 是同步确认）。**资金/库存类数据 DB 是唯一可信源，Redis 缓存丢了可以重建**——这是架构层面的兜底思路。

### 读写分离的坑：复制延迟读到旧值

写主库后立刻读从库，可能读到旧值（延迟几 ms~几 s）。要求"写后立即可读"的操作读主库。

### 动手搭（两分钟体验）

```bash
# 三个节点：1 主 2 从
docker run -d --name redis-master -p 6391:6379 redis:7-alpine
docker run -d --name redis-slave1 -p 6392:6379 redis:7-alpine
docker run -d --name redis-slave2 -p 6393:6379 redis:7-alpine

# 从库指定主库（用容器互通网络更佳，教学用最简方式）
docker exec redis-slave1 redis-cli REPLICAOF redis-master 6379   # 同一 docker 网络
# 或宿主机测试：docker network create redis-ha && 三个容器都加入后用容器名
```

验证：`docker exec redis-master redis-cli SET a 1` → `docker exec redis-slave1 redis-cli GET a` → `1`。从库写会报错 `READONLY`（只读保护）。

## 二、哨兵 Sentinel：主挂了自动换主

主从解决"数据冗余"，但**主库挂了要人工提从为主**——半夜谁上？哨兵解决：

```
[哨兵1] [哨兵2] [哨兵3]（奇数个，至少3，互相通信）
   │ 监听主库 + 从库（每秒 PING）
   │
   ├─ 主观下线（SDOWN）：某哨兵 ping 不通主库
   ├─ 客观下线（ODOWN）：≥ quorum 个哨兵都认为挂了（防误判）
   ├─ 选举 leader 哨兵（Raft 思想，少数服从多数）
   └─ leader 挑选最合适的从库提升为主 → 通知其它从库改挂新主 → 通知客户端新地址
```

### 从库提升优先级怎么选

`replica-priority` 数字越小越优先 → 其次比较复制 offset（数据最全的）→ 再比较 runid。**原则：选数据最全的，少丢数据。**

### 客户端怎么知道换了主

应用连的不是固定 IP，而是**哨兵集群**：Spring 配置 `spring.data.redis.sentinel.master=mymaster + nodes`，客户端自动从哨兵查询当前主库地址，主从切换自动跟随。

### 哨兵的局限

- 写能力仍是**单主**（容量与写吞吐没扩）
- 切换期间（10~30 秒）不可写

## 三、Cluster 集群：数据分片，水平扩容

内存 256GB 装不下 → 分片。Cluster 把 key 空间切 **16384 个槽（slot）**，按 CRC16(key) mod 16384 分给节点：

```
key → CRC16(key) % 16384 → slot=槽号 → 所属节点

节点A: slot 0~5460      （含主从副本）
节点B: slot 5461~10922
节点C: slot 10923~16383
```

- **每个主节点自带从节点**（副本 redundancy）——哨兵的职责内置到集群
- 客户端直连任意节点，若 key 不在本节点，返回 `MOVED` 重定向到正确节点（smart client 本地缓存路由表）
- **扩容**：加节点 → 迁移部分槽（`CLUSTER ADDSLOTS`），在线进行

### Cluster 的代价（为什么小规模不用它）

| 代价 | 说明 |
|------|------|
| **多 key 命令受限** | MGET/事务/Lua 跨槽会报 `CROSSSLOT`——key 加 `{tag}` 哈希标签强制同槽：`user:{1001}:cart` |
| 客户端要求高 | 需支持集群协议的客户端 |
| 运维复杂 | 槽迁移、副本均衡 |

**选型经验**：单机内存装得下（≤ 25GB 级）→ 主从+哨兵；装不下或写吞吐超单机 → Cluster。**分片的另一种路子：客户端分片/Codis/多实例按业务拆**——很多公司业务量级根本用不到官方 Cluster。

## 三件套对比总表

| | 主从复制 | 哨兵 | Cluster |
|--|---------|------|---------|
| 解决什么 | 数据冗余、读扩展 | 主挂自动切换 | 容量/写吞吐水平扩展 |
| 高可用 | ❌ 人工切换 | ✅ 自动切换 | ✅ 内置 |
| 分片 | ❌ | ❌ | ✅ 16384 slot |
| 复杂度 | 低 | 中 | 高 |
| 适合 | 读多写少的小系统 | 中型系统标配 | 大容量/大吞吐 |

## 面试问法

**Q: 主从复制的原理？主从切换会丢数据吗？**
A: 首次 PSYNC 全量 RDB+缓冲区增量，长期靠 repl_backlog 环形缓冲区实时命令流；断线按 offset 续传，冲掉则全量。复制是**异步**的，主挂瞬间从库可能落后，切换后会丢主库最后几毫秒写入——Redis 高可用固有取舍，资金类数据以 DB 为准。

**Q: 哨兵的工作流程？**
A: 每秒 PING 主从库 → 单个哨兵 ping 不通为主观下线 → ≥quorum 个确认即客观下线 → 哨兵间选举 leader → leader 按 replica-priority/offset 选从库提主 → 通知从库和客户端。至少 3 个奇数哨兵防脑裂误判。

**Q: 集群怎么知道 key 在哪个节点？**
A: 固定 16384 个槽，CRC16(key)%16384 定位槽，客户端按槽路由（smart client 缓存路由表），不在本节点返回 MOVED 重定向。多 key 操作要求同槽——key 加 {tag} 哈希标签。
