# 03 · 持久化：RDB 与 AOF

Redis 在内存里，断电即失——持久化解决"重启数据还在"。两套机制：**RDB（快照）和 AOF（操作日志）**，生产通常两者都开。

## RDB：定时全量快照

把某一时刻的**全量内存数据**写成紧凑的二进制文件（`dump.rdb`）。

### 两种触发方式

**① SAVE**：主线程自己写文件——**阻塞所有请求**，生产禁用。

**② BGSAVE（默认方式）**：fork 子进程写文件，主线程继续服务：

```
主线程 ──fork──→ 子进程 ──遍历内存──→ dump.rdb
   │（fork 后各自独立，主线程继续处理命令）
```

**关键机制：写时复制（Copy-On-Write）**——fork 不复制全部内存，父子共享物理页；主线程此后**修改某页时，内核才把该页复制一份给子进程**。所以：

- BGSAVE 期间数据修改越多，内存膨胀越多（最坏翻倍）——大实例做 BGSAVE 要预留内存
- fork 本身也有耗时（复制页表，10GB 实例约几十~几百 ms）——**大实例高峰期 BGSAVE 有毛刺**

### 自动触发：save 规则 + 主从同步

```bash
# 默认规则：900s 内 1 次修改 / 300s 内 10 次 / 60s 内 1 万次 → 触发 BGSAVE
CONFIG GET save
# 手动：BGSAVE（后台） / LASTSAVE（上次快照时间戳）
```

**优点**：文件紧凑（恢复快，适合备份/迁移/主从全量同步）；**缺点**：两次快照之间的数据宕机即丢（分钟级窗口）。

## AOF：追加写命令日志

把每条**写命令**追加到 `appendonly.aof` 文件。重启时重放全部命令恢复数据。

```
客户端: SET a 1 → [主线程] 追加到 aof_buf → 按策略刷盘
```

### 三种刷盘策略（appendfsync）

| 策略 | 行为 | 丢数据窗口 | 性能 |
|------|------|-----------|------|
| `always` | 每条命令都 fsync | 基本不丢 | 差（每命令一次磁盘 IO） |
| **`everysec`（默认/推荐）** | 后台线程每秒 fsync | **最多丢 1 秒** | 好 |
| `no` | 交给 OS（~30s） | 最多 30s | 最好 |

生产用 `everysec`——在"最多丢 1 秒"和性能之间的工程平衡点。

### AOF 重写（Rewrite）：日志太大了怎么办

一个 key 改 1 万次，AOF 里就有 1 万条 SET——重写按**当前数据状态**生成最小命令集（`SET key 最终值`，一条搞定）：

```
BGREWRITEAOF  ← fork 子进程按内存现状生成新 AOF
重写期间的新命令写进"AOF 重写缓冲区"，完成后追加替换旧文件
```

自动触发阈值：`auto-aof-rewrite-percentage 100`（比上次翻倍）`+ auto-aof-rewrite-min-size 64mb`。

### AOF 文件格式（动手看）

```bash
# 开启 AOF 跑几条命令后：
docker exec redis-learn cat /data/appendonlydir/appendonly.aof.1.incr.aof | head
```

7.0 后是 MULTI-PART：`appendonlydir/` 目录下 base（全量）+ incr（增量）文件。

## RDB vs AOF 对比表（背）

| | RDB | AOF |
|--|-----|-----|
| 本质 | 某时刻全量快照（二进制） | 写命令日志（文本追加） |
| 丢数据 | 两次快照间的（分钟级） | everysec 最多 1 秒 |
| 文件大小 | 小（紧凑） | 大（命令+重写控制） |
| 恢复速度 | 快（直接载入） | 慢（逐条重放） |
| 性能影响 | fork 毛刺 + COW 内存膨胀 | 持续刷盘 IO |

**生产推荐**：两者都开。**重启恢复优先用 AOF**（数据更全，`aof-use-rdb-preamble` 让 base 部分就是 RDB 格式，兼得恢复速度）。

## 混合持久化（4.0+，生产标配）

```
aof-use-rdb-preamble yes
```

AOF 重写时：base 文件用 RDB 格式（全量、载入快），之后增量用 AOF 命令。**恢复快 + 丢数据少**，两全其美。

## 持久化的局限 → 主从复制

就算 everysec，单机宕机也可能丢 1 秒 + 恢复期间不可用。**完整的高可用 = 持久化 + 主从复制 + 哨兵自动切换**（下一章）。注意一个反直觉事实：**主从复制是异步的，主挂时从可能还没同步到最新写入**——极端主从切换仍可能丢少量数据，这是 Redis 高可用的固有取舍（对比 Kafka 的 ISR 强同步）。对资金类数据，DB 是 source of truth，Redis 只做加速。

## 面试问法

**Q: RDB 和 AOF 怎么选？**
A: RDB 是全量快照，文件小恢复快，但分钟级丢数据窗口，fork 有毛刺；AOF 是命令日志，everysec 最多丢 1 秒，文件大恢复慢、需重写压缩。生产两者都开 + 混合持久化（AOF 重写时 base 用 RDB 格式），重启优先 AOF 恢复。

**Q: BGSAVE 时为什么不会阻塞业务？内存会翻倍吗？**
A: fork 子进程 + 写时复制：父子共享物理页，只有被主线程修改的页才复制给子进程。所以平时不复制全量内存，但写入越多膨胀越多，最坏翻倍；大实例 fork 复制页表有几十毫秒毛刺，建议避开写高峰。
