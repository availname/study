# 04 · 过期删除与内存淘汰

两类"删数据"要分清：**过期删除**（key 带了 TTL，到期了）和**内存淘汰**（内存满了，被迫杀）。面试常混着问，一张表分清。

## 一、过期删除：一个 key 的三种死法

TTL 到期的 key 不会"瞬间消失"——单线程逐个检查太贵，Redis 用三招组合：

### ① 惰性删除（访问时检查）

GET/SET 该 key 时发现已过期 → 删除并当它不存在。省 CPU，代价：过期后**没人访问就一直占内存**。

### ② 定期删除（后台抽样）

后台事件循环每 100ms 抽样：每个过期字典随机抽 20 个 key，删掉过期的；若过期比例 > 25%，继续下一轮抽样。**兜底**扫描，不保证全量及时。

### ③ 内存淘汰兜底（见下节）

惰性+定期都清不过来，内存满了由淘汰策略强杀。

**体感验证**：SET 一个带 TTL 的 key，等它过期后不访问直接 `MEMORY USAGE`——可能还在；`INFO memory` 里的 `expired_keys` 计数反映定期删除的工作量。

## 二、内存淘汰：maxmemory 满了怎么办

### 配置三件套

```bash
CONFIG SET maxmemory 2gb                      # 内存上限
CONFIG SET maxmemory-policy allkeys-lru       # 淘汰策略
INFO memory                                   # used_memory / maxmemory 观察水位
```

### 八种策略（按作用范围记，3 组）

| 策略 | 范围 | 算法 | 场景 |
|------|------|------|------|
| `noeviction`（默认） | — | 满了**拒绝写入**报错 | 数据绝不能丢（如分布式锁 key！） |
| `allkeys-lru` | 全部 key | 最近最少使用 | **纯缓存首选** |
| `allkeys-lfu`（4.0+） | 全部 key | 最不经常使用（按频次） | 访问频率差异大的缓存 |
| `volatile-lru/lfu` | 仅带 TTL 的 key | LRU/LFU | 缓存与永久数据混存 |
| `volatile-ttl` | 仅带 TTL | 剩余寿命短的先删 | |
| `volatile-random` / `allkeys-random` | — | 随机 | 极少用 |

**选型口诀**：
- 纯缓存实例 → `allkeys-lru`（或访问频次差异大用 lfu）
- 缓存+锁/永久数据混跑 → `volatile-lru`（只动带 TTL 的）——但**带 TTL 的 key 必须占多数**，否则可淘汰池太小照样报错
- 有"绝不能被自动删"的 key（分布式锁、幂等键）→ 要么分开实例部署，要么接受 noeviction 的写入报错风险

### LRU 的实现：近似 LRU

真 LRU 要全局链表 O(N) 维护——Redis 用**抽样近似**：每次淘汰随机抽 5 个（`maxmemory-samples`），杀其中最久未用的。`lfu` 用 16 位计数器（对数衰减 + 概率累加）近似频次。**工程上：牺牲一点精度换 O(1) 无锁。**

### 动手观察淘汰

```bash
CONFIG SET maxmemory 10mb
CONFIG SET maxmemory-policy allkeys-lru
# 循环塞大 value……内存满了后看：
INFO stats | grep evicted_keys      # 被淘汰的 key 计数（监控必须盯它！）
```

**evicted_keys > 0 说明内存打满开始杀数据**——缓存命中率会突然下降，必须告警。

## 三、与业务的三个联动坑（预告 stage3）

1. **淘汰会杀掉分布式锁/幂等键** → 要么这类 key 放独立实例用 noeviction，要么监控 evicted
2. **SET 覆盖会清 TTL**（stage1/04 提过）→ 缓存更新务必带 EX
3. **过期 key 正在被业务使用**：惰性+定期删除有时间差，高并发下"过期未删"的旧值可能被读到——**库存/资金类判断不能只依赖 Redis TTL**，配合 Lua 原子操作与 DB 兜底（stage4/01）

## 面试问法

**Q: Redis 的过期删除策略？**
A: 组合拳——惰性删除（访问时查）+ 定期删除（每 100ms 随机抽 20 个，过期超 25% 继续抽）+ 内存淘汰兜底。逐个定时检查太贵，组合拳平衡 CPU 与内存。

**Q: 内存满了怎么办，策略怎么选？**
A: maxmemory + 八种策略。纯缓存 allkeys-lru/lfu；有不可淘汰 key 用 volatile 系；默认 noeviction 写入报错。Redis 的 LRU 是抽样近似 LRU（随机 5 个取最旧），O(1) 无锁换精度。监控 evicted_keys，>0 即告警。
