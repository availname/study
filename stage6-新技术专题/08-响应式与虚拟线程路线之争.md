# 08 · 响应式与虚拟线程：路线之争（2026 观点）

Java 高并发的两条路线：**Reactor 响应式**（2017~）和 **虚拟线程**（2023~）。它们解决同一个问题——"线程太贵，IO 等待不能干等"——但哲学完全相反。这一篇给你一张决策表，并诚实评估"2026 年新项目该怎么选"。

## 两条路线的本质

| | 响应式（Reactor/WebFlux/R2DBC） | 虚拟线程（Loom） |
|--|-------------------------------|-----------------|
| 解法 | **换编程模型**：不用线程，用事件回调的数据流（`map/flatMap` 组装管道） | **换线程实现**：还是线程思维，但阻塞成本被 JVM 消化 |
| 代码形态 | 链式算子、非阻塞、声明式 | 普通同步代码，和你写循环一样 |
| 并发容量 | 单机几万连接（少量事件循环线程） | 百万虚拟线程（同步阻塞写法） |
| 心智负担 | 高：背压、订阅时机、上下文丢失、调试栈断裂 | 低：就是普通代码 |
| 生态成熟度 | 非常成熟（7 年+），网关/流式场景统治级 | 快速成熟中（3 年），Spring 生态已全面适配 |

## 响应式的"贵"，体现在哪

```java
// 响应式版"查缓存→未命中查库→回写"（一个最普通的业务）
public Mono<Order> getOrder(long id) {
    return redisOps.get("order:" + id)
        .switchIfEmpty(db.findById(id)
            .flatMap(o -> redisOps.set("order:" + id, o).thenReturn(o)));
}
// 看着还行？真实的业务里：异常分支、重试、熔断、超时、事务边界——
// 每个都要算子表达，链路一长就是 40 行的管道，堆栈里没有你认识的类名
```

**响应式最贵的不是性能调优，是团队每个人都要保持"函数式纪律"**——一行 `.block()`（同步等待）混进响应式链，整个非阻塞优势报废，还可能死锁。这类事故极隐蔽。

## 虚拟线程改变了什么

```java
// 同样的业务，虚拟线程版：就是普通代码
public Order getOrder(long id) {
    Order order = redisGet(id);              // 阻塞？unmount，让出载体线程
    if (order == null) {
        order = dbFind(id);                  // DB 阻塞同样 unmount
        redisSet(id, order);
    }
    return order;
}
// 每个请求一个虚拟线程，3 万并发 = 3 万虚拟线程，就完事了
```

**JDK 21 的 pinning 遗留问题**（synchronized 内阻塞钉死载体线程）在 JDK 24 已解决（JEP 491）。生态适配：Tomcat/Jetty、Lettuce、Spring 全线就绪；R2DBC 之外，普通 JDBC 在虚拟线程上**也可以**跑高并发（连接池注意限流即可）。

## 决策表（直接背）

| 你的情况 | 选什么 |
|---------|--------|
| 新项目、普通 Web/MQ 业务系统 | **虚拟线程**（一行配置 + 普通代码） |
| 已运行的成熟响应式系统 | 保留，不建议迁移（收益/成本不划算） |
| 网关/代理/SSE 大规模长连接推送 | WebFlux 仍是精品方案（Netty 场景统治级） |
| 团队没人懂响应式、deadline 紧 | 虚拟线程，别让一半团队学习成本压垮交付 |
| 需要严格背压控制的数据流处理 | Reactor（背压语义目前无可替代） |
| "既要高并发又要代码简单" | 虚拟线程 + 必要处少量 Reactor（混用合法） |

## 2026 观点（行业现状）

- Spring 官方口径：Boot 3.2+ 全面拥抱虚拟线程，`spring.threads.virtual.enabled=true` 是新项目默认推荐
- 大厂存量系统大量是 WebFlux/Netty——**响应式不会死**，它是网关、流媒体、实时推送的地基
- 新人学习顺序反转：**先学普通并发+虚拟线程，再按需学响应式**——直接学响应式的人容易患上"万物 Mono"综合症，写个 CRUD 都要包 Mono

## 与 MQ/Redis 的交汇点

- **MQ 消费者**：虚拟线程让"批量拉取→并行处理"变成三行代码（stage6/01）；响应式里要用 flatMap+concurrency 参数做同样的事
- **Redis 客户端**：Lettuce 本身就是异步驱动（Netty），虚拟线程下用同步 API 也跑得飞快；响应式下用 ReactiveRedisTemplate
- **你的 community**：已加 `spring.threads.virtual.enabled=true`——这就是你的技术选型答案

## 面试问法

**Q: 虚拟线程和 WebFlux 怎么选？**
A: 同问题不同解法：响应式换编程模型（事件流+算子，并发强但复杂），虚拟线程换实现（同步代码，JVM 消化阻塞）。2026 选型：新业务系统默认虚拟线程（一行配置+团队零学习成本）；存量成熟响应式不迁移；网关/长连接/严格背压场景仍用 WebFlux。注意 JDK 21 pinning 与瓶颈转移（连接池）。混用合法——虚拟线程里可以局部用 Reactor。
