# 延迟任务方案横向对比（一次讲透"到点执行"的全部选型）

> 🎬 **配套动画**：[diagrams/delay-task.html](../diagrams/delay-task.html)——"延迟消息为主 + 扫表兜底 + CAS 裁决"三层防线的四种真实结局推演。

> 🎯 **专题定位**：[stage3/05 延迟消息](stage3-问题解决/05-延迟消息与死信队列.md) 讲了 TTL+DLX 怎么用，[stage4/02 超时关单](stage4-高并发实战/02-订单超时自动取消.md) 讲了完整业务链路——这篇把"延迟执行"这件事**所有主流方案放到一张桌上对比**，帮你建立选型能力。面试官问"订单超时怎么关"之后，下一步往往就是"如果不用 MQ 你还有什么办法？"——这篇就是答案库。

## 场景引入：延迟任务无处不在

| 业务场景 | 延迟要求 | 量级 |
|----------|---------|------|
| 订单 30 分钟未支付自动关闭 | 分钟级、允许秒级误差 | 日百万 |
| 优惠券/会员到期提醒 | 小时级、允许分钟误差 | 日十万 |
| 支付发起后 15 秒未回调主动查单 | 秒级 | 日百万 |
| 消息重试的退避（1s/5s/30s…） | 秒级、精确 | 高频 |
| 会议开始前 5 分钟推送提醒 | 分钟级 | 中量 |

**先分清两个概念**（面试易混）：

- **延迟任务**：某个时间点执行**一次**（到点关单）——本文主角
- **定时任务**：固定**周期**重复执行（每晚对账）——见 [XXL-Job 篇](../java-core/05-微服务全家桶/07-XXL-Job分布式任务调度.md)

一个是"闹钟响一次"，一个是"每天早上 7 点的闹钟"。

## 六大方案横向对比（总表）

| 方案 | 精度 | 可靠性 | 水平扩展 | 运维成本 | 适用量级 | 一句话定位 |
|------|------|--------|---------|---------|---------|-----------|
| ① JDK DelayQueue | 纳秒 | ❌ 内存，重启全丢 | ❌ 单机 | 零 | 单机小量（如本地连接池空闲检测） | 内部零件，不是方案 |
| ② DB 定时扫表 | 分钟 | ✅ 数据在 DB 最稳 | ✅ 但扫描分页麻烦 | 零 | 小体量/兜底位 | 简单可靠但"钝" |
| ③ Redis ZSet | 秒 | ⚠️ 依赖快照/主从 | ✅ | 低 | 中大 | 无 MQ 时的轻量主力 |
| ④ Redis 过期通知 | 不定 | ❌ 不保证及时、不保证送达 | — | 低 | **❌ 不能当主方案** | 只能做"锦上添花" |
| ⑤ RabbitMQ TTL+DLX / 延迟插件 | 毫秒 | ✅ 复用 MQ 可靠性全套 | ✅ | 中（已有 MQ 则零） | 中大 | **本工作区主线方案** |
| ⑥ RocketMQ 延迟消息 | 18 等级 / 5.x 任意毫秒 | ✅ Broker 持久化+定时轮 | ✅ | 中 | 大 | 大厂标配，精度最好 |

**核心认知**：选型的本质是"**精度、可靠性、成本**"三角——没有全能冠军，只有场景匹配。下面逐个看原理与代码。

## ① JDK DelayQueue：单机零件

```java
BlockingQueue<Delayed> queue = new DelayQueue<>();
// 元素实现 getDelay() 返回"还剩多久到期"，到期才能被 take() 拿走
```

**致命短板**：纯内存、无持久化、单进程——应用重启任务全没。它适合**进程内部**的调度（Netty/Kafka 内部时间轮、连接池空闲检测），不适合业务任务。**面试点**：DelayQueue = 优先级堆 + take 时按剩余时间 await，这是理解时间轮的前置。

## ② DB 定时扫表：笨但最稳

```java
@Scheduled(cron = "0 */5 * * * ?")   // 每 5 分钟
public void sweep() {
    // 只捞一小批 + 走索引（created_at + status 联合索引），避免大事务
    List<String> ids = orderDao.findTimeoutPending(30, 100);
    ids.forEach(this::closeIfTimeout);   // 复用幂等关单逻辑
}
```

- **优点**：任务就是 DB 里的一行数据，天然持久化、天然可恢复——**任何其他方案挂了，扫表都是最终兜底**
- **缺点**：精度 = 扫描间隔（5 分钟一扫，最多晚 5 分钟）；数据量大时 `LIMIT 100` 分页要按 id 滚动，漏扫风险要靠"扫到没有为止"
- **定位**：单独用 = 小体量业务；配合延迟消息 = **双保险**（见实战节）

## ③ Redis ZSet：score 存到期时间戳

ZSet 按 score 有序——把"执行时间戳"当 score，捞到期任务就是一次 `ZRANGEBYSCORE`。

```java
// 下单时登记任务
redis.opsForZSet().add("delay:order:close", orderNo, System.currentTimeMillis() + 30 * 60_000);

// 调度线程每秒捞一次（多实例部署）
Set<String> due = redis.opsForZSet().rangeByScore("delay:order:close", 0, System.currentTimeMillis(), 0, 100);
for (String orderNo : due) {
    // 关键：ZREM 抢占（原子），删成功才算抢到——多实例不重复消费
    if (Boolean.TRUE.equals(redis.opsForZSet().remove("delay:order:close", orderNo))) {
        closeIfTimeout(orderNo);   // 失败可 ZADD 回投 + score 加退避
    }
}
```

**原理图**：

```
delay:order:close (ZSet)
score=执行时间戳, member=任务ID
10:00:00  O1001   ←── ZRANGEBYSCORE 0~now 捞出
10:00:05  O1002
10:29:59  O1003        ZREM O1001 成功 → 执行关单（原子抢占，多实例安全）
                              失败 → ZADD 回投，score += 退避间隔
```

- **优点**：秒级精度、量级轻松十万级、不依赖 MQ
- **坑**：①调度线程"捞了但还没 ZREM"就崩溃 → 任务卡在"已被捞出"边界——所以**必须 ZREM 成功才执行**，不能先执行后删；②重试要自己写回投；③Redis 挂了靠快照恢复（可能丢最后几秒）→ 兜底照旧交给扫表
- **对照**：ZSet 的排序思想就是 [redis stage5/05 热搜榜](../redis/stage5-类型场景实战/05-ZSet-热搜榜.md) 同款，只是 score 从"热度"换成"时间"

## ④ Redis 过期通知：❌ 为什么不能当主方案

```java
// 配 notify-keyspace-events Ex 后订阅过期事件——看着很美：
redisMessageListenerContainer.addMessageListener(msg -> closeOrder(msg), new ChannelTopic("__keyevent@0__:expired"));
```

**三宗罪**（面试要能说全）：

1. **不保证及时**：Redis 惰性删除——没人访问的过期 key 可能一直躺着，事件延迟不可控
2. **不保证送达**：过期事件走 pub-sub，**发后即忘不落盘**，订阅端恰好断线 = 事件永久丢失
3. **无法重试**：pub-sub 没有消费确认，丢了就是丢了

> [!CAUTION]
> 网上大量教程用过期通知做延迟队列，**生产环境照抄就是事故**。它唯一合理的用法是"丢了无所谓"的通知（如缓存失效提示）。

## ⑤ RabbitMQ TTL+DLX：本工作区主线

```
                    TTL 沉睡                      死信转发
下单 ──→ order.delay.queue ──────30min──────→ (x-dead-letter-exchange)
              （消息躺着不消费）                        │
                                              order.timeout.queue → 消费者关单
```

- **原理**：消息设 TTL，到期没人消费 → 变死信 → 被队列配置的 DLX 转发到真正的工作队列（[stage3/05 详解](stage3-问题解决/05-延迟消息与死信队列.md)）
- **优势**：复用 MQ 全套可靠性（持久化/Confirm/重试/死信）——[learn-center 的超时取消延迟链](../learn-center/README.md)、[mq-mall 的关单](mq-mall/README.md) 都是这套
- **经典坑——队头阻塞**：TTL 在**队列级别**时，队列只看队头。先进一条 TTL=30min 的消息，后面 TTL=1min 的全部被它挡住 ❌。**解法**：①每个延迟等级一条队列（10s/30s/5min/30min 各一条，都指向同一个 DLX）✅；②或用官方 `rabbitmq_delayed_message_exchange` 插件（消息级 TTL，内部定时器）✅

## ⑥ RocketMQ 延迟消息：精度与量级的王者

```java
Message msg = new Message("order-timeout", orderNo.getBytes());
msg.setDelayTimeLevel(16);                    // 4.x：18 个固定等级，16=30min
// 5.x：任意精度 → msg.setDeliverTimeMs(System.currentTimeMillis() + 30 * 60_000);
producer.send(msg);
```

- **原理**：Broker 内部 `ScheduleMessageService` 按等级建 Schedule Queue（本质是**时间轮思想**），到点把消息转投真实队列——**精度和可靠性都比 TTL+DLX 高**（无队头阻塞，Broker 持久化）
- **限制**：4.x 只能 18 个固定等级（1s~2h）；5.x 才支持任意毫秒级
- 详见 [RocketMQ 专篇 01](stage6-RocketMQ专篇/01-RocketMQ架构与事务消息.md)

## 补充：时间轮（海量任务的终极答案）

单机要挂**百万级**定时任务（如每个 TCP 连接一个超时检测）？ZSet/扫描都不够快——**时间轮**：

```
        ┌───┬───┬───┬───┬───┬───┬───┬───┐
        │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │   8 格 × 1s/格，指针每秒走一格
        └───┴───┴───┴───┴───┴───┴───┴───┘
          ↑                                    任务哈希到 (当前格+延迟格数)
         指针走到哪格，执行该格挂的所有任务          同一格多条任务 = 链表
```

- **O(1) 添加/取消**（哈希定位），指针 tick 驱动——Netty `HashedWheelTimer` 看门狗、Kafka 延迟操作（purgatory）、RocketMQ 定时轮都是它
- 多层级时间轮解决"超过一圈"（秒轮→分轮→时轮，钟表时分秒指针同构）
- 参见 [Netty 入门篇](../java-core/07-网络基础/05-Netty入门.md)——RPC 框架的请求超时检测就是 HashedWheelTimer

## 问题与解法（各方案的坑汇总）

| 坑 | 现象 | 解法 |
|----|------|------|
| TTL+DLX 队头阻塞 | 短 TTL 消息被前面的长 TTL 挡住不投递 | 每等级独立队列 / 延迟插件 / 换 RocketMQ |
| ZSet 抢占遗漏 | 捞到但执行前崩溃，任务卡死 | **ZREM 成功才执行**；恢复扫描 ZRANGEBYSCORE 补捞 |
| ZSet 多实例重复消费 | 两个实例同时执行同一任务 | ZREM 原子抢占（删成功者执行）/ Lua 打包捞+删 |
| 过期通知丢事件 | 消息静默丢失、无日志 | ❌ 弃用，换 ZSet 或 MQ 方案 |
| 延迟消息堆积 | 死信队列/延迟队列积压，消费打满 | 惰性队列（[stage3/04 堆积](stage3-问题解决/04-消息堆积怎么治.md)）+ 消费扩容 |
| 任务时间回拨 | 服务器 NTP 校时导致任务提前/延后 | 存"绝对时间戳"而非"剩余秒数"；执行端 CAS 幂等兜底 |

**统一心法**：延迟方案只是"到点提醒你一下"，**执行端必须自带幂等**（CAS 状态机）——消息重复投递、任务重复抢占、扫表与消息双路齐下，全都靠 `UPDATE ... WHERE status=10` 这种 CAS 保证不出错（[stage4/02 竞态核心](stage4-高并发实战/02-订单超时自动取消.md)）。

## 高并发实战：怎么选（决策树）

```
需要延迟执行？
├─ 单机内部零件（连接空闲/请求超时检测） → DelayQueue / 时间轮
├─ 业务任务，量小（<1w/天）、分钟精度够   → DB 扫表（最简单，别过度设计）
├─ 已有 Redis、没有 MQ                   → ZSet + ZREM 抢占
├─ 已有 RabbitMQ                         → TTL+DLX（分等级队列）或延迟插件
├─ 已有 RocketMQ / 大体量 / 秒级精度     → RocketMQ 延迟消息
└─ 以上任何方案                          → + 低频扫表兜底 + 执行端 CAS 幂等
```

**mq-mall 的答案**（生产标配，值得背下来）：**延迟消息为主（精准及时）+ 扫表兜底（防漏单）+ CAS 幂等执行（防重复）**——三层各司其职：

| 层 | 方案 | 防什么 |
|----|------|--------|
| 主路径 | TTL+DLX 延迟消息 | 让"及时关单"成为常态 |
| 兜底 | 5 分钟扫表（OrderSweepJob） | 延迟消息丢了/漏了的单 |
| 正确性 | CAS `WHERE status=10` | 重复投递、双路并发、时间回拨 |

这与支付系统的"回调为主 + 查单补偿 + 对账兜底"完全同构（[15-支付系统](../java-core/15-系统设计·支付系统.md)）——**异步主路径 + 定时补偿 + 幂等执行**是处理一切"第三方不可靠"的通用范式。

## 面试问法

**Q: 订单超时自动关闭有哪些实现方案？怎么选？**
A: 按场景分层：单机内部用 DelayQueue/时间轮；小体量直接 DB 扫表（简单可靠）；有 Redis 用 ZSet（score=到期时间戳，ZREM 原子抢占防多实例重复）；有 MQ 用 TTL+DLX（注意每等级独立队列防队头阻塞）或 RocketMQ 延迟消息（18 等级/5.x 任意精度，Broker 内部时间轮，精度最好）。Redis 过期通知不能当主方案——惰性删除不及时 + pub-sub 不落盘会丢事件。生产标配组合：**延迟消息为主 + 低频扫表兜底 + 执行端 CAS 状态机幂等**，三层分别保证及时性、完整性、正确性。
