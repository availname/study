# 04 · Kafka 与 RabbitMQ 选型对比

两套都学完了，最后回答终极问题：**什么时候用哪个**。

## 架构本质差异（一张表）

| 维度 | RabbitMQ | Kafka |
|------|----------|-------|
| 模型 | **消息队列**：Exchange 路由 → 队列 → 消费即删 | **分布式日志**：Topic 分区追加 → 消费组按位移读 → 保留可重放 |
| 路由 | 强（Exchange/绑定/Topic 通配/Headers） | 无路由概念（key 分区），路由在业务层 |
| 消息语义 | 单条 ACK，优先级/延迟/死信原生 | 批量拉取，保留重放，事务偏流处理 |
| 单机吞吐 | 万级 | **百万级**（顺序写+零拷贝+批量） |
| 延迟 | 微秒~毫秒（推模式） | 毫秒~十毫秒（拉模式+批量） |
| 消息回溯 | ❌（消费即删） | ✅（重置 offset 重放） |
| 顺序 | 单队列有序 | 分区内有序 |
| 延迟队列 | 原生 TTL+DLX | 无原生（Kafka Streams 按时间轮/外置调度） |

## 选型决策表（背）

```
选 Kafka：
  ① 日志/埋点/大数据管道（吞吐百万级）
  ② 需要消息回溯/重放（数据修复、新服务补数据）
  ③ 流式计算对接（Flink/Streams 生态）
  ④ 事件溯源/审计日志（保留+回放）

选 RabbitMQ：
  ① 复杂路由需求（多交换机/优先级/延迟队列）
  ② 单条低延迟 + 任务队列语义（工作队列）
  ③ 需要原生死信/延迟/TTL 管理

两者都行：普通业务解耦/异步通知（按团队熟悉度）
```

## 你的项目该用哪个？（自问自答）

- mq-mall 订单链路（可靠+延迟取消+死信管理）→ **RabbitMQ 更顺手**（原生 TTL/DLX/Confirm 生态完整）
- 学习行为埋点（每天百万条点赞/浏览事件 → Flink 计算）→ **Kafka**（吞吐+生态）
- 结论：**两者并存按场景选择是常态**，不是二选一

## 面试问法

**Q: Kafka 和 RabbitMQ 怎么选？**
A: 按"日志 vs 队列"的本质差异选——Kafka 是分布式日志（保留可重放/分区并行/百万吞吐），适合大数据管道/事件溯源/流计算；RabbitMQ 是消息队列（复杂路由/原生延迟死信/低延迟单条语义），适合业务任务队列。混合并存按场景选择是常态：日志埋点走 Kafka、业务任务走 RabbitMQ。决策四问：吞吐？回溯？路由复杂度？延迟敏感度？
