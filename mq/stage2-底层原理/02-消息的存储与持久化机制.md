# 02 · 消息的存储与持久化机制

核心问题：**Broker 重启/宕机，消息会不会丢？**

## 先认识消息的两种状态

在队列里，每条消息只有两个状态：

```
Ready ──(推给消费者)──→ Unacked ──(收到ack)──→ [删除]
  │                          │
  └── 待消费，任何人可取        └── 已投给某个消费者，锁定（消费者断连则退回 Ready）
```

管理界面 Queues 页的两个数字 `Ready` / `Unacked` 就是这两列的总和。**持久化只保证 Ready 和 Unacked 的消息在重启后回来；只有"已删除"的才真的没了。**

## 持久化三件套：缺一个都白搭

要保证消息"落盘可恢复"，三个东西都必须持久化：

| 对象 | 非持久化 | 持久化 |
|------|---------|--------|
| Exchange | `new DirectExchange("x")` | `new DirectExchange("x", true, false)` |
| Queue | `new Queue("q")` | `new Queue("q", true)` |
| **Message** | deliveryMode=1 | **deliveryMode=2** |

Spring Boot 中持久化消息：

```java
rabbitTemplate.convertAndSend("biz.topic", "order.create", order,
    m -> {
        m.getMessageProperties().setDeliveryMode(MessageDeliveryMode.PERSISTENT);
        return m;
    });
```

> 好消息：Spring AMQP 里 `new Queue(name, true)` + 默认 `SimpleMessageListenerContainer` 时消息默认就是 PERSISTENT，很多教程因此没提 deliveryMode——**换成裸客户端时它默认是 1（非持久化）**，务必显式设置。

**三件套的陷阱**：

- 声明持久化队列时，如果 broker 上已存在**同名非持久化队列**，直接报错 `PRECONDITION_FAILED - inequivalent arg 'durable'`。解法：删掉旧队列再声明（管理界面 Delete）。
- 只持久化了队列没持久化消息 → 重启后空队列；只持久化消息队列没持久化 → 队列都没了消息更没了。

**动手验证**（README 的 Stage2 任务）：

```bash
# 1. 非持久化队列发 3 条消息 → docker restart rabbitmq → 队列和消息都没了
# 2. 持久化三件套发 3 条消息 → docker restart rabbitmq → Ready 还是 3
docker restart rabbitmq
```

## 落盘后性能掉了 10 倍，怎么办

持久化 = 每条消息写磁盘，吞吐从几万/秒掉到几千/秒。RabbitMQ 的存储结构和优化：

### 存储结构

```
 queues/  每个队列一个目录：
    queues.idx   ─ 队列索引：每条消息在 msg_store 里的位置 + 属性（小而频繁）
    queues.jif/journal
 msg_store/   全局消息存储（所有队列共享）：
    .rdq 文件    ─ 消息 body（4MB 一段，追加写）
```

- 索引和正文**分开存**：同一队列大量消息内容相似时，msg_store 可去重压缩。
- 写入策略是**组提交（batch fsync）**：攒一小批一起刷盘，这是"可靠"与"吞吐"之间的平衡点。

### Lazy Queue（惰性队列）——堆积大时的救命稻草

默认模式下：新消息**先驻留内存**，内存紧张才换页（page out）到磁盘。堆积百万条时，换页会把 CPU/IO 打满，集群假死。

**Lazy Queue（3.6+）**：消息**直接写磁盘**，内存里最多留 2MB 缓存，消费时才加载。适合"队列可能积压几十上百万条"的场景：

```java
@Bean
public Queue bigBacklogQueue() {
    return QueueBuilder.durable("big.queue")
            .lazy()                        // x-queue-mode: lazy
            .build();
}
```

代价：单条消费延迟略增（要读盘）。**"流量平滑消费"场景必配 lazy**；"秒级实时"的小队列不必。

### 内存与磁盘告警

Broker 内存使用达到阈值（默认 40% 物理内存）或磁盘剩余低于 50MB 时：

- **暂停所有生产者连接**（block），消费者照常跑——这就是天然的削峰自保。
- 表现为：生产端突然发不进去，Channel 被 block。监控里要有这两项告警。

## 集群与高可用：持久化 ≠ 高可用

**这是本章最重要的一句话**：持久化只解决"单机磁盘在"，解决不了"这台机器炸了"。

RabbitMQ 三种集群模式：

| 模式 | 机制 | 现状 |
|------|------|------|
| 普通集群 | 只同步元数据（交换机/绑定），**消息实体只存在一个节点**，消费者到别的节点取会拉取转发 | 消息单点，节点挂则消息不可用 |
| 镜像队列（Mirrored Queue） | 每条消息同步复制到 N 个节点的镜像 | 官方已标记**废弃**（性能差，大型集群不稳定） |
| **Quorum Queue（仲裁队列）** | 基于 **Raft** 共识算法，3/5 节点多数派写入才算成功，自动选主 | **官方推荐，3.8+ 生产标配** |

```java
// Quorum Queue：durable 必须 true，x-queue-type=quorum
@Bean
public Queue orderQueue() {
    return QueueBuilder.durable("order.queue").quorum().build();
}
```

理解 Quorum Queue 就理解了 Kafka/RocketMQ 的副本思想：**单机持久化 + 多副本共识 = 数据可靠性的完整答案**。

## 顺便看看另两家怎么存（对比记忆）

| | RabbitMQ | RocketMQ | Kafka |
|--|----------|----------|-------|
| 存储粒度 | 每队列索引 + 全局 msg_store | **统一 CommitLog**：所有 Topic 的消息顺序追加写同一个大文件，再按队列建索引（ConsumeQueue） | 每个 **Partition** 一个顺序追加的日志段文件 |
| 写入模式 | 组提交 fsync | 顺序写 + 可配刷盘（同步/异步） | 顺序写 + **页缓存 + 零拷贝**（sendfile） |
| 为什么快 | Erlang 轻量进程 + 组提交 | CommitLog 顺序写（磁盘顺序写 ≈ 内存随机写速度） | 顺序写 + 零拷贝不进用户态 |
| 消费进度 | 消费即删（队列中移除） | 消息保留按时间，按 **ConsumeOffset** 消费 | 消息保留按时间/大小，按 **Offset** 消费 |

**RabbitMQ 是"消费即删"模型**（没有 offset、不能回溯重放历史），Kafka/RocketMQ 是"日志 + 消费位点"模型（消息是文件里的记录，读哪个位置由消费者自己决定）。这个差异决定了：**想"重新消费昨天的消息"做数据修复，RabbitMQ 做不到，Kafka/RocketMQ 天然支持**。

## 面试问法

**Q: 持久化了就一定不丢吗？**
A: 不一定。消息写入 OS 页缓存还没 fsync 时断电仍可能丢（RabbitMQ 组提交有一定窗口）；且单机持久化不抗机器故障，需要 Quorum Queue/副本。完整方案 = 持久化 + 刷盘策略 + 多副本，生产端 Confirm 是最后一道验证（下一章）。

**Q: 什么时候用 Lazy Queue？**
A: 可预见大堆积的场景（削峰、批量导入）。它让消息常驻磁盘，避免默认模式下内存挤爆触发大规模换页导致集群卡顿。
