# 04 · 三大 MQ 底层对比：RabbitMQ vs Kafka vs RocketMQ

Stage 3/4 的很多方案在不同 MQ 里实现方式不同，先把三家的"性格"摸清。

## 一句话人设

- **RabbitMQ**：精细的**路由管家**——交换机+绑定规则，把消息准确送达；消费即删，不存历史。
- **Kafka**：高速的**分布式日志**——消息是追加到分区文件里的记录，靠 offset 消费，为吞吐而生。
- **RocketMQ**：**Java 版全能交易选手**——借鉴 Kafka 存储思想，补齐事务消息、延迟消息、顺序消息，为电商而生。

## 架构图对比

**RabbitMQ**（2-01 已讲）

```
Producer → Exchange ──Binding──→ Queue(消费即删)
                      ↑ 路由规则丰富（direct/topic/fanout/headers）
```

**Kafka**

```
                 ┌→ Partition0 [msg,msg,msg...] ──→ ConsumerGroup-A (offset=123)
Producer ──→ Topic ┼→ Partition1 [msg,msg,msg...] ──→ ConsumerGroup-B (offset=88)
（按key/hash分区） └→ Partition2 ...
```

- Topic 只是一个名字，物理上**分片为多个 Partition**，分布在多台 Broker。
- **生产者自己决定消息进哪个分区**（按 key hash / 轮询）——没有交换机，路由逻辑在生产者手里。
- 消息**不删**（保留 N 天），消费者组各自维护 offset，想重放就把 offset 拨回去。
- 同一消费组内，一个 Partition 同一时刻只被一个消费者消费 → **分区内天然有序、天然并行单元**。

**RocketMQ**

```
Producer ──→ BrokerA/B/C（NameServer 做无状态路由发现）
                  └→ CommitLog（所有 Topic 混写一个顺序大文件）
                       └→ ConsumeQueue（每 Topic 每 Queue 一个索引：offset/size/hash）
                            └→ Consumer 按 offset 消费
```

- 架构上像 Kafka（分区/offset/消费组），但**借鉴了 RabbitMQ 的队列概念**（MessageQueue）。
- 独有组件 **NameServer**：无状态注册中心，Broker 上报路由，客户端拉取——不像 Kafka 依赖 ZooKeeper/KRaft。
- 独有设计 **CommitLog**：所有 Topic 混流顺序写同一个文件（磁盘顺序写性能拉满），再由 ConsumeQueue 索引定位——**用一次读盘换全量写盘性能**。

## 底层机制逐项对比

| 维度 | RabbitMQ | RocketMQ | Kafka |
|------|----------|----------|-------|
| 协议 | AMQP 0-9-1 | 私有协议（RocketMQ Remoting） | 私有协议（TCP） |
| 拉还是推 | **推**（Broker 主动推，prefetch 背压） | **长轮询拉**（Pull，无消息时 hold 住请求） | **拉**（Consumer 主动 fetch） |
| 路由能力 | ★★★ 交换机+通配符 | 一般：Topic/Tag（二级过滤） | 无路由概念，纯分区 |
| 顺序消息 | 单队列天然有序（并发受限） | **MessageQueueSelector + 顺序消费锁** | **分区内有序**（同 key 同分区） |
| 延迟消息 | TTL+DLX / 插件 | ★ **原生 18 个等级，5.x 任意时间** | 无（要自建） |
| 事务消息 | 无（要自己搞本地消息表） | ★ **半消息 + 回查** | 无（exactly-once 是别的语义） |
| 消息回溯/重放 | ❌ 消费即删 | ✅ 按 offset/时间 | ✅ 按 offset/时间 |
| 死信队列 | 原生 DLX | 原生 %DLQ% 主题 | 无原生（自建） |
| 堆积能力 | 一般（Lazy Queue 撑百万级） | 强（磁盘存储，亿级） | 极强 |
| 吞吐量级 | 1w~10w/s | 10w+/s | 百万/s |
| 延迟 | 微秒~毫秒（**最低**） | 毫秒 | 毫秒（攒批时略高） |
| 语言/运维 | Erlang（运维门槛高） | Java（可读源码、好二开） | Scala/Java |

## 存储 vs 消费模型深入对比

### "消费即删" vs "日志 + 位点"

```
RabbitMQ:  Queue 是个"传送带"——消息被取走就消失，队列天然空
Kafka/RMQ: Log 是个"账本"——消息永远躺在文件里，每个消费者拿个书签(offset)
```

**后果**：

| 能力 | 传送带（RabbitMQ） | 账本（Kafka/RocketMQ） |
|------|-------------------|----------------------|
| 消费后重放历史 | ❌ 做不到 | ✅ 拨回 offset 即可（数据修复神器） |
| 多个系统独立消费同一份消息 | 每系统一条队列，消息复制多份 | 同一份数据多个消费组各记各的 offset，零复制 |
| 队列堆积的代价 | 内存/换页压力（要 Lazy Queue） | 只是磁盘占用，无额外压力 |
| 新消费者加入"从头消费历史" | ❌ | ✅ |

**所以 Kafka 能成为大数据事实标准**：flink 离线任务、实时任务、风控、数仓都从同一个 Topic 各取所需，还能随时重跑昨天的一批。

### Kafka 高吞吐三板斧（面试高频）

1. **顺序写**：每个 Partition 就是一个只追加的文件，磁盘顺序写速度接近内存随机写。
2. **页缓存 + 零拷贝**：消息写入 OS page cache 就返回；消费者读时用 `sendfile` 直接从页缓存送网卡，**数据不进 JVM、不拷贝两次**，GC 压力为零。
3. **批量与压缩**：生产者攒一批再发，Broker 攒一批再给消费者，网络与磁盘按批摊销。

RocketMQ 的 CommitLog 同样吃顺序写红利；RabbitMQ 的 msg_store 也有组提交，但"每队列一个索引 + 消费即删"的结构决定了它的量级上限。

### 可靠性/一致性对比

| | RabbitMQ | RocketMQ | Kafka |
|--|----------|----------|-------|
| 单机可靠 | 持久化三件套 + Confirm/ACK | 刷盘（同步/异步）+ 主从同步 | acks=all + min.insync.replicas |
| 多副本 | Quorum Queue（Raft） | 主从同步（Dledger = Raft） | ISR 多副本（Leader-Follower） |
| 生产确认 | Confirm | 同步发送 flush/等副本 | acks=0/1/all |

三家殊途同归：**都收敛到"多副本共识算法（Raft 或其变体）"**。

## 怎么选（决策树）

```
你的流量是什么？
├─ 日志/埋点/用户行为流 → 大数据管道 → Kafka
├─ 电商交易、订单、支付类（需要事务消息/延迟消息）→ RocketMQ
├─ 业务解耦、中小流量、需要灵活路由/快速上手 → RabbitMQ
└─ 拿不准：
    ├─ 团队是 SpringCloud Alibaba 系 → RocketMQ（生态无缝）
    └─ 小项目、内部系统 → RabbitMQ 最省事
```

现实里很多中大型公司**组合使用**：Kafka 承载日志/大数据流，RocketMQ/RabbitMQ 承载业务消息——各干各的强项。

## 面试综合题

**Q: 为什么 Kafka 快？**
A: 顺序写 + 页缓存/零拷贝 + 批量压缩，三层去掉了磁盘随机写、用户态拷贝、单条网络开销。

**Q: RabbitMQ 和 Kafka 消费模型最大区别？**
A: 推 vs 拉；消费即删 vs 日志位点。前者低延迟、简单，但不支持回溯、堆积成本高；后者支持多消费组独立消费和重放，吞吐上限高。

**Q: 为什么 RocketMQ 混用一个 CommitLog？**
A: 把所有 Topic 的写入合并为单个顺序追加文件，磁盘只做顺序写，避免多 Topic 多文件随机写；读性能靠 ConsumeQueue 索引 + 少量随机读弥补，对交易类"写多读也频繁"的场景整体最优。
