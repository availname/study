# 04 · 失败语义与场景方法论

对应代码：`MediaPipelineConsumers`（FAIL 分支）· `VideoController.retry/audit` · [踩坑实录](../踩坑实录-完整复盘.md)坑九

## 两种失败，两种语义

管道里"失败"不是一个东西，demo 用同一个消费者演示了两种语义：

### 语义 A：可重试错误（偶发）→ 重试 + 死信

DB 瞬时抖动、下游 RPC 超时——**同样的输入再跑一次可能就成功**。

```
抛异常 → spring-retry 本地重试 3 次（0.5s/1s/2s）→ 耗尽 → DLX → 死信落库 → 告警
```

### 语义 B：任务失败（确定性/需人工修复）→ 标记 FAILED + 人工重提

转码遇到损坏的视频文件、审核材料缺失——**重试多少次都一样，需要人先修复输入**。

```
catch 里 markFailed(videoId, reason)  → 状态变 FAILED（用户可见："处理失败，可重试"）
       → dedup.fail(messageId)        → 回滚幂等键（重提才能被处理）
       → throw                        → 触发重试/死信链路（消息本身也要体面收场）
```

人工修复后 `POST /api/videos/{id}/retry`：状态回 UPLOADED + 清幂等键 + 重发消息，管道重新流动。

| | 语义 A（重试型） | 语义 B（人工型） |
|--|---------------|----------------|
| 典型原因 | 瞬时故障 | 坏输入/业务规则不满足 |
| 自动手段 | 指数退避重试 | 无法自动修复 |
| 最终归宿 | 死信落库人工兜底 | FAILED 状态 + 用户可见 + 重提入口 |
| 消息结局 | 死信队列 | 消费掉（状态机已记录事实） |

**判断口诀：重试能好的用重试，重试不好的要"留一个让人介入的把手"**——FAILED 状态和 retry 端点就是把手。

## ⚠ 两种语义混用时的防线交互陷阱（真实踩坑）

demo 里 FAIL 视频第一次重提后卡死，排查发现了一个隐蔽 bug（[踩坑实录坑九](../踩坑实录-完整复盘.md)）：

```
第 1 次尝试：tryConsume 写键 → 业务失败 → catch 里 dedup.fail 删键 → throw ✓
第 2 次尝试：tryConsume 写键（键已删，成功）→ casStatus 返回 0（状态已是 FAILED）
            → 走"状态不对，跳过"分支 return ←←← 这条路不经过 catch！
            → 幂等键残留 Redis 24h
人工 retry：重发消息 → tryConsume 撞上残留键 → "重复消息跳过" → 任务永远卡死
```

**教训（元教训"防线交互"的实例）**：两道各自正确的防线（状态机 CAS + 幂等键）叠加后，会产生谁都没设计过的第三种路径。修复：retry 端点重发前**显式 `dedup.fail` 清键**——人工重提的语义本来就是"覆盖历史"。

**推论**：给系统加第二道防线时，必须把"两道防线同时触发"的矩阵场景过一遍（都放行/都拦截/A拦B放/B拦A放）。

## 管道可观测性：从状态看健康

`/api/videos/stats` 的状态分布就是管道的心电图：

| 分布形态 | 诊断 |
|---------|------|
| UPLOADED 大量堆积 | 转码能力不足或转码消费者挂了 |
| TRANSCODING 长期不动 | 转码卡死（线程死锁/FFmpeg 僵尸进程） |
| HUMAN_AUDIT 增长 | 审核员不够——是业务问题不是技术问题 |
| FAILED 增长 | 输入质量恶化（上传源损坏率高）或转码版本 bug |
| PUBLISHED 正常增长，其他都很小 | 健康 |

加上每级队列的 Ready/Unacked（RabbitMQ 管理界面）和死信数，**管道的健康 = 状态分布 + 队列深度 + 死信量**三张图。

## 扩展场景速览（同一思想的更多落地）

| 场景 | MQ 用法 | 要点 |
|------|---------|------|
| 播放/点赞计数 | 点击事件进队列，消费者攒批 `INCR` 后定时刷 DB | 削峰 + 批量合并；Redis 为准、DB 异步追平 |
| 弹幕 | 弹幕消息 → fanout → 房间广播服务 | 低可靠性（丢了无所谓）+ 高吞吐；与订单场景完全相反的配置 |
| 用户行为日志埋点 | Kafka：前端 SDK → Kafka → Flink/数仓 | 日志型消息天然可回溯（stage2/04 的"账本模型"） |
| 自动生成字幕 | 转码完成事件的第二个消费者（并行而非串联） | 管道分叉：一条事件触发多个并行任务，全部完成后才可发布（组合状态机） |
| 内容热点自动运营 | 播放量超阈值发"热点事件" → 运营队列 | 阈值判断放消费者里，运营人工复核（又一个 HUMAN_AUDIT 形态） |

## 场景方法论总结（stage4 + stage5 合璧）

到这里，你已经用 MQ 解决了两类典型业务。以后遇到任何新场景，按这张表走：

```
1. 识别 MQ 在这里的三种角色中占哪种（可叠加）：
   削峰（秒杀/推送/计数）│ 解耦广播（事件通知/下游接入）│ 任务管道（流水线/工作流）
2. 画状态机：任务/实体有哪些状态？哪些流转？谁推流转（消息 or 人工）？
3. 定失败语义：哪些错误重试型、哪些人工型？留"人工把手"（状态+端点）。
4. 配可靠性档位：按"丢了会怎样"分级，别全套上保险（stage3/01 分级原则）。
5. 想幂等键：全局唯一业务 ID + 两层防线 + 防线交互矩阵过一遍（坑九教训）。
6. 规划可观测：状态分布 + 队列深度 + 死信量 + 幂等跳过计数。
```

**面试综合题**：设计 B 站式的视频发布系统。
答案骨架 = 本阶段四章：上传受理（本地消息表秒回）→ 管道串联（转码/审核/上架，状态机 CAS，独立扩容）→ 审核三态（AI+人工卡点用状态表达而非阻塞）→ fanout 广播下游（推荐/推送，推送分批限速幂等）→ 失败分级（重试+死信 / FAILED+人工重提，防线上注意防线交互）→ 可观测三件套。
