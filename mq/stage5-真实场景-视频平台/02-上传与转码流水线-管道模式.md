# 02 · 上传与转码流水线：管道模式

对应代码：`media/MediaPipelineConsumers.onSubmitted` · `config/MediaTopologyConfig`

## 什么是管道模式（Pipeline）

多个消费者**串联**起来，每个消费者处理完自己那一步，把"下一站消息"发到下一个队列：

```
队列A → 消费者1(干第一步) ─发消息→ 队列B → 消费者2(干第二步) ─发消息→ 队列C → ...
```

它本质是**用 MQ 实现的责任链/工作流**：每一步是独立部署、独立扩容、独立故障的节点。

## 为什么不写"一个大消费者全干了"

```java
// 反面教材：一个消费者把所有活干完
public void handle(Video video) {
    transcode(video);      // 90s
    audit(video);          // 30s
    publish(video);        // 10s
    notifyFans(video);     // ???s
}
```

问题随着规模逐个爆出来：

| 问题 | 管道模式的解法 |
|------|--------------|
| 转码 90s 占住线程，审核闲置 | 每级独立队列+消费者，**独立扩容**：转码慢就只加转码实例 |
| 审核服务挂了 → 全管道停摆 | 故障隔离：审核挂了只积压 `media.transcoded.queue`，转码照常 |
| 想在转码和审核之间加"抽封面" | 插一个队列+消费者，上下游代码零改动 |
| 某一步失败，整条重来还是跳过？ | 每级独立重试/死信/人工兜底，失败精确到步骤 |
| 排查"哪个环节慢" | **看每级队列的 Ready 数**：哪级堆积哪级是瓶颈，一目了然 |

> 队列长度即瓶颈仪表盘——这是管道模式运维上最大的红利。

## mq-mall 的实现细节

### 消息串联：每级消费完发下一级消息

```java
// ① 转码消费者
@RabbitListener(queues = "media.submitted.queue")
public void onSubmitted(VideoEvent event) {
    String messageId = "media-submitted-" + event.videoId();
    if (!dedup.tryConsume("media-transcode", messageId)) return;   // 幂等（stage3/02）

    taskDao.casStatus(videoId, UPLOADED, TRANSCODING);   // 状态机 CAS（stage4/02 纪律）
    Thread.sleep(1500);                                  // 模拟 FFmpeg
    taskDao.casStatus(videoId, TRANSCODING, TRANSCODED);
    // 干完发下一站消息（用独立 messageId："media-transcoded-{id}"）
    publisher.sendFast("media.events", "media.transcoded", "media-transcoded-" + videoId, event);
}
```

**两个工程要点**：

1. **每级消息的 messageId 前缀不同**（`media-submitted-` / `media-transcoded-` / `media-audited-`）——因为每级的幂等是独立的：同一条"转码完成"消息重投只需跳过审核级，不该把转码级也拦了。
2. **管道内消息用 sendFast**（提交入口才用本地消息表）：中间环节失败可整任务重提，不需要每级都上全套保险——**可靠性和成本按位置分级**（stage3/01 的原则）。

### 状态机 CAS：管道的"防重入闸门"

```java
// MediaTaskDao
UPDATE t_media_task SET status = :next WHERE video_id = :vid AND status = :expect
```

返回 0 行 = 状态不是预期的（重复消息/乱序/人工已干预）→ 消费者直接跳过。**一个 SQL 同时解决了幂等、乱序、并发三类问题**——这就是为什么状态机是异步系统的第一道防火墙。

### 上传入口：本地消息表 + 秒回

```java
// VideoController.submit（@Transactional）
taskDao.insert(videoId, title);          // 任务表 + 消息表 同事务
publisher.sendInTransaction(...);        // 提交后发 media.submitted
return ApiResponse.ok(videoId);          // 用户 50ms 拿到 videoId，前端开始轮询状态
```

用户不等转码——**异步边界画在"重活开始之前"**，接口只负责"受理"。

## 管道各级的容量规划思维

| 环节 | 真实耗时 | 扩容手段 |
|------|---------|---------|
| 转码 | 30s~30min（CPU 密集） | 消费者实例数 ≈ CPU 核数；Flink/分片转码 |
| AI 审核 | 5~30s（GPU 推理） | GPU 池扩容；低峰期批量补审 |
| 上架/CDN | 秒级 | 一般不需要特别扩容 |
| 粉丝推送 | 分批长任务 | 限速消费（见 03 篇） |

**管道的节奏由最慢的一级决定**（木桶原理）。转码是最慢的，所以转码队列的 prefetch 要小（实例数×1~2），避免"抢了一堆任务却干不完"；快环节的 prefetch 可以大。对照 demo：转码消费者默认 prefetch=10 够用，因为只有一级是慢的。

## 面试问法

**Q: 视频上传后的处理流程怎么设计？**
A: 上传接口只受理并返回 videoId，后续转码→审核→上架用 MQ 管道串联：每级独立队列+消费者+状态机 CAS 推进任务状态，独立扩容、独立故障隔离；发布完成用 fanout 广播给推荐/推送等下游。失败分级：可重试错误走重试+死信，任务级失败标记 FAILED 供人工修复后重提；用户侧靠轮询任务状态获得进度。
