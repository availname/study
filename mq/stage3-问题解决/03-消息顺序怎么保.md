# 03 · 消息顺序怎么保

场景：同一笔订单的消息 `创建 → 支付 → 发货`，如果消费顺序乱了（先收到"支付"再收到"创建"），下游按消息更新缓存/表结构就会错乱。

## 先搞清楚为什么会乱

**RabbitMQ 里**，队列本身是 FIFO 的——**单个队列内消息绝对有序**。乱序发生在这些地方：

```
① 生产端分发了不同队列/交换机
   order.create → queue-A     order.pay → queue-B
   → 两个队列谁先被消费不确定！

② 同一队列多个消费者并发
   queue → Consumer-1（创建，处理 200ms）
        → Consumer-2（支付，处理 10ms）
   → 支付先完成！轮询分发不看你先来后到

③ 消费失败重投
   创建 失败 requeue → 排到队头 → 但 支付 已经被取走了

④ prefetch > 1 时批量预取后多线程处理
```

**一句话：队列内有序 ≠ 消费有序。消费有序 = 同组消息进同一队列 + 该队列同一时刻只有一个消费者在处理。**

## 重要认知：只要局部有序，别要全局有序

全局有序 = 整个队列串行消费 = 吞吐直接归 1，任何系统都承受不起。

正确目标：**同一业务键（同一订单）的消息有序**，不同订单之间随意并发。这叫**分区有序**，Kafka/RocketMQ 的默认设计哲学。

```
订单1001: create → pay → ship        串行 ✓
订单1002: create → pay → ship        串行 ✓
订单1001 和 1002 之间：随便谁先        并行 ✓
```

## RabbitMQ 实现：路由到同一队列 + 单消费者

**生产端**：用同一个 routing key（或交换机 key 映射），让同一订单进同一队列：

```java
// routing key 直接用 orderId，声明成 direct 交换机 + 每队列绑 N 个 key
// 或者 topic 交换机 + 队列绑定特定范围
rabbitTemplate.convertAndSend("order.direct", "order-" + orderId, msg);
```

**消费端**：该队列**只起一个消费者，且串行处理**：

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 1          # 单消费者
        prefetch: 1             # 处理完才给下一条，彻底串行
```

**代价**：单队列吞吐 ≈ 单机处理能力（几百~几千/s）。所以：

- 有序队列要**按业务拆分**：`order-1001~2000` 一个队列、`order-2001~4000` 一个队列……把"订单空间"分片到多个队列，每个队列内部有序。有点像 Kafka 分区的手工版。
- 如果业务允许，**优先考虑改成幂等 + 状态机方案**：消息带版本号/序列号，乱序到达时旧版本直接丢弃——**能不排队就不排队**：

```java
// 乱序兜底：消息自带 sequence，旧事件直接丢
if (msg.getSequence() <= currentOrderStatus.getSequence()) {
    log.info("过期消息，丢弃。seq={}", msg.getSequence());
    return;
}
```

**这个"版本号丢弃"方案在实际工程里的价值常常高于严格排队**——它没有吞吐代价，还顺便解决了重投乱序。

## RocketMQ 实现：MessageQueueSelector + 顺序消费

RocketMQ 原生支持，最优雅：

```java
// ① 生产端：同一订单 hash 到同一队列（和 Kafka 按 key 分区一模一样）
SendResult result = producer.send(msg, (mqs, message, arg) -> {
    Long orderId = (Long) arg;
    int index = (int) (orderId % mqs.size());
    return mqs.get(index);
}, orderId);

// ② 消费端：MessageListenerOrderly——对队列加锁，单线程消费
consumer.registerMessageListener((MessageListenerOrderly) (msgs, context) -> {
    // 同一队列的消息到这里，保证按发送顺序逐条处理
    for (MessageExt m : msgs) { handle(m); }
    return ConsumeOrderlyStatus.SUCCESS;
});
```

`Orderly` 模式内部对每个队列做**分布式锁**（Broker 级）+ 消费者本地锁，保证同一队列同时只有一个线程消费。失败时会**挂起当前队列**稍后重试同一批，而不是跳过去消费后面的——代价是失败会阻塞该队列。

> RocketMQ 5.x 还支持 `MessageGroup`（消息组），发送时指定同一 group 有序，语义更明确。

## Kafka 实现：分区内天然有序

Kafka **分区内绝对有序**，生产端按 key 分区即可：

```java
// key = orderId → 相同 key 必进同一分区 → 分区内有序
producer.send(new ProducerRecord<>("order-topic", String.valueOf(orderId), msg));
```

**但有一个经典坑**：`max.in.flight.requests.per.connection > 1`（批量发送提速）时，如果第 1 批失败重试、第 2 批成功，重试的第 1 批会**插到第 2 批后面**——分区内乱序了！

堵法（二选一）：

```properties
# 方案A：最多 1 个在途批次（损失吞吐）
max.in.flight.requests.per.connection=1

# 方案B（推荐）：开幂等生产者，Broker 会拒绝乱序批次
enable.idempotence=true    # Kafka 保证 in-flight ≤5 时也严格有序
```

消费端注意：**重试不能乱序**——失败的消息不能丢回队列稍后再来（那样后面的先处理了），要么阻塞该分区（类似 RMQ Orderly），要么进"重试主题"但接受该 key 暂停（pause partition）。

## 三家对比总结

| | RabbitMQ | RocketMQ | Kafka |
|--|----------|----------|-------|
| 原生支持 | ❌ 靠拓扑设计 | ✅ Orderly 消费 | ✅ 分区天然有序 |
| 生产端 | 同 key 路由同队列 | MessageQueueSelector | key 分区 |
| 消费端 | 单消费者+prefetch=1 | MessageListenerOrderly | 正常消费即可 |
| 性能代价 | 大（队列并行度=1） | 中（队列级锁） | 小（本来就是分区并行） |
| 坑 | 拓扑改错就乱 | 失败阻塞队列 | in-flight 重试乱序 |

## 决策：真的需要顺序吗？

多数"以为需要顺序"的场景，用**状态机/版本号幂等**就够了：

```
真需要（下游无法幂等，如同步 binlog 到 ES、缓存重建）→ 队列内有序方案
可改造（业务状态可判断新旧）→ 版本号丢弃，性能更好
```

## 面试问法

**Q: 如何保证消息顺序消费？**
A: 首先明确只需业务分区有序。RocketMQ 用 MessageQueueSelector 按 orderId hash 到同一队列，消费端 MessageListenerOrderly 队列加锁串行；Kafka 天然分区内有序，生产按 key 分区，注意开启幂等生产者防止 in-flight 重试乱序；RabbitMQ 靠拓扑——同一业务键路由到同一队列并单消费者串行，代价是并行度，一般还会加版本号幂等做乱序兜底。
