# 02 · 消息重复怎么幂等

先接受一个事实：**重复不可避免，不要试图消灭它，要让系统"重复了也没事"**。

## 为什么重复无法避免

RabbitMQ 的投递语义是 **at-least-once（至少一次）**——保证不丢，代价就是可能重复：

| 重复来源 | 场景 |
|---------|------|
| Confirm 超时 | 消息实际已到 Broker，但 Confirm 回执丢失/超时，生产者重发 |
| 消费超时/崩溃 | 消费者拿到消息（Unacked）处理到一半崩溃 → 消息退回队列 → 重投给别的消费者 |
| 消费重试 | 处理失败 requeue，或网络闪断 Broker 没收到 ack → 重投 |
| 人为重发 | 补偿任务重发（stage3/01 的本地消息表）、管理界面手动 Get+Republish |

想做到 exactly-once（精确一次）？**端到端不可能**——网络分区下"成功但确认丢失"无法区分。所以业界的正确姿势：

> **MQ 保证 at-least-once，业务自己实现幂等（idempotent），合起来等价于 exactly-once。**

幂等 = 同一个操作执行一次和执行一百次，结果一样。

## 幂等方案全家桶（按优先级）

### 方案 0：业务天然幂等（零成本，先检查这个）

- `UPDATE account SET balance = 100 WHERE id = 1`（设值，不是加减）
- `INSERT ... ON DUPLICATE KEY UPDATE`
- 查询类操作

凡是能改成天然幂等的，优先改，不要上技术方案。

### 方案 1：数据库唯一索引（最可靠，必配兜底）

给业务唯一键加唯一索引，重复插入直接报错，catch 掉即可：

```sql
ALTER TABLE t_order ADD UNIQUE KEY uk_order_no (order_no);
```

```java
try {
    orderMapper.insert(order);   // 重复消息 → DuplicateKeyException
} catch (DuplicateKeyException e) {
    log.info("重复消息，已存在，忽略。orderNo={}", order.getOrderNo());
    return;                       // 正常 ack，当成功处理
}
```

**优点**：数据库层面强保证，不依赖 Redis、不怕服务重启。
**缺点**：只适合"插入型"业务；异常当流程走，性能略差（每次都试）。

### 方案 2：状态机（更新型业务的唯一索引）

用状态流转约束代替插入约束：订单只能 `10待支付 → 20已支付`，**只能前进**：

```sql
-- 幂等的关键在 WHERE 条件：只有待支付状态才会被更新
UPDATE t_order SET status = 20, pay_time = NOW()
WHERE order_no = #{orderNo} AND status = 10;

-- affectedRows = 0 说明已经不是待支付（重复消息/已取消）→ 直接放弃
```

支付回调、超时关单（stage4/02）都靠这一招解决并发竞态。

### 方案 3：Redis setnx 去重（性能最好，第一道闸）

高并发场景在业务执行前先抢锁，挡住绝大多数重复：

```java
@RabbitListener(queues = "points.queue")
public void handle(PointsMsg msg, Channel channel,
                   @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    String dedupKey = "mq:dedup:" + msg.getMessageId();
    // setIfAbsent = setnx：第一次插入成功返回 true，重复返回 false
    Boolean first = redisTemplate.opsForValue()
            .setIfAbsent(dedupKey, "1", Duration.ofHours(24));
    if (Boolean.FALSE.equals(first)) {
        log.info("重复消息，直接跳过 id={}", msg.getMessageId());
        channel.basicAck(tag, false);
        return;
    }
    try {
        doBusiness(msg);
        channel.basicAck(tag, false);
    } catch (Exception e) {
        // 关键：失败了要删掉去重键，否则下次真重投时会被误杀
        redisTemplate.delete(dedupKey);
        channel.basicNack(tag, false, false);   // 进死信
        throw e;
    }
}
```

**三个坑必须懂**：

1. **过期时间**：不设过期 → Redis 塞满；设太短 → 长延迟重投穿透。应 ≥ 消息最大重投周期（通常 24h）。
2. **Redis 单点/挂了**：去重键丢失 → 重复穿透。所以 **setnx 只是第一道闸，唯一索引/状态机是最后防线**，两层都要有。
3. **setnx 成功但业务失败**：必须回滚删除键（上面代码的 catch），否则"占坑不做事"。

### 方案 4：去重表（把 setnx 搬进数据库，可靠但慢）

```sql
CREATE TABLE mq_dedup (
    message_id VARCHAR(64) PRIMARY KEY,      -- 唯一索引即去重
    created_at DATETIME,
    KEY idx_created (created_at)             -- 定期清理用
);
```

```java
// 与业务操作同一个本地事务，天然原子，不怕 Redis 挂
try {
    dedupMapper.insert(messageId);   // 重复 → DuplicateKeyException → 忽略
    doBusiness(msg);
} catch (DuplicateKeyException e) { return; /* 已处理过 */ }
```

适合：对一致性要求极高、又不想用 Redis 的场景。缺点：每条消息多一次 DB 写。

### 方案 5：乐观锁 version（防并发更新覆盖）

```sql
UPDATE t_stock SET count = count - 1, version = version + 1
WHERE id = #{id} AND version = #{version};
```

重复消息带着旧 version 来，UPDATE 不中。适合"多次修改同一行"的实体。

## 组合拳（生产标准姿势）

```
消息进来
  │
  ├→ ① Redis setnx 快速去重         ← 挡住 99% 重复，性能无损
  │      重复 → ack 跳过
  │
  ├→ ② 业务执行
  │      插入型：唯一索引兜底
  │      更新型：状态机/乐观锁兜底
  │      （①被穿透时靠这两层兜住）
  │
  └→ ③ 确认 ack / 失败进死信
```

## 每条消息要带什么：messageId 的约定

幂等的前提是**能识别"同一条消息"**。发送时必须带业务唯一 ID：

```java
Message msg = MessageBuilder.withPayload(order)
        .setHeader("messageId", "order-create-" + order.getOrderNo())  // 业务键，不用 UUID
        .build();
```

> 用**业务键**（订单号+动作）而不是随机 UUID：重发的是"同一件事"，业务键天然相同；UUID 每次重发都变，去重就失效了。本地消息表重发时尤其要注意——复用第一次的 messageId。

## 面试问法

**Q: 如何保证消息不被重复消费？**
A: 重复无法根治，MQ 是 at-least-once，正确做法是消费端幂等。方案分层：Redis setnx 用业务 messageId 做第一道快速去重（注意过期时间和失败回滚键）；数据库唯一索引/状态机作为强一致兜底；天然幂等的操作优先改写为幂等写法。两层配合，Redis 挂了也有数据库兜底。
