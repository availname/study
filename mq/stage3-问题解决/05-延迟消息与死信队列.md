# 05 · 延迟消息与死信队列

两个绑在一起的机制：**死信队列（DLX）**是基础设施，**延迟消息**是它的头号应用。

## 死信队列（Dead Letter Exchange）

**死信** = 消息在队列里"以三种方式死亡"：

| 死法 | 触发条件 |
|------|---------|
| 被拒绝 | `basicNack/basicReject` 且 `requeue=false` |
| 过期 | 消息 TTL 到期，或队列 `x-message-ttl` 到期 |
| 超长 | 队列达到最大长度 `x-max-length`，最老消息被挤出去 |

**死信不会消失**——给队列配置 `x-dead-letter-exchange` 后，死掉的消息被转发到指定的死信交换机，再路由到死信队列，由专门消费者处理。

```
order.queue ─(死亡: nack/过期/超长)─→ [dlx.exchange] ─→ order.dlq ─→ 死信处理消费者
                                                                          │
                                                        记日志/告警/人工兜底/延迟重试
```

### 代码实现

```java
@Bean
public Queue orderQueue() {
    return QueueBuilder.durable("order.queue")
            .deadLetterExchange("dlx.exchange")        // x-dead-letter-exchange
            .deadLetterRoutingKey("order.dead")        // 死信的 routing key（省略则沿用原 key）
            .build();
}

@Bean
public DirectExchange dlxExchange() { return new DirectExchange("dlx.exchange"); }

@Bean
public Queue orderDlq() { return QueueBuilder.durable("order.dlq").build(); }

@Bean
public Binding dlqBinding() { return BindingBuilder.bind(orderDlq()).to(dlxExchange()).with("order.dead"); }
```

```java
// 死信处理消费者：stage3/01 重试耗尽的消息最后都到这里
@RabbitListener(queues = "order.dlq")
public void handleDeadLetter(OrderMsg msg) {
    log.error("收到死信: {}", msg);
    // 保存到人工处理表 + 告警，或触发兜底逻辑
    deadOrderService.saveForManual(msg);
    alertService.notify("死信告警", msg.getMessageId());
}
```

**死信监控是可靠链路的最后一环**：重试耗尽、无法自动处理的失败，全部在死信里可见可控。没有 DLQ 的系统，失败消息就是"无声失踪"。

## 延迟消息：订单 30 分钟未支付自动取消

经典需求。MQ 的解法：下单成功后发一条 **30 分钟后才被消费**的消息，消费时检查订单，未支付则关单。

### 方案一：TTL + 死信队列（RabbitMQ 原生，不用插件）

思路：消息先进一个**没有消费者的 TTL 队列**，到期"过期死亡"→ 被 DLX 转到真正的消费队列。

```
Producer → [order.delay.queue] (x-message-ttl=30min, x-dead-letter-exchange=dlx.exchange)
                │ 30分钟无消费者，消息过期
                ↓ 死信
           [order.dead.queue] → 消费者：查单，未支付则关单
```

```java
@Bean
public Queue orderDelayQueue() {
    return QueueBuilder.durable("order.delay.queue")
            .ttl(30 * 60 * 1000)                 // x-message-ttl
            .deadLetterExchange("order.close.exchange")
            .deadLetterRoutingKey("order.close")
            .build();
}
// 发送：rabbitTemplate.convertAndSend("", "order.delay.queue", orderId);
```

**⚠ 致命缺陷：队头阻塞（Head-of-line blocking）**

TTL 队列只检查**队头**消息。先发的"30 分钟"没死，后面的"5 秒"也出不去：

```
队列: [TTL 30min] [TTL 30min] [TTL 5s] ←  5s 的消息排在 30min 后面，要等 30min 才死！
```

补救：**每种延迟时间一个队列**（`delay.5s`、`delay.1min`、`delay.30min`……）。固定几档延迟时可用；任意时间延迟不行。

### 方案二：延迟插件（RabbitMQ 官方插件，推荐）

安装 `rabbitmq-delayed-message-exchange`：

```bash
# 插件下载放进容器后启用，或换带插件的镜像
docker exec rabbitmq rabbitmq-plugins enable rabbitmq_delayed_message_exchange
```

原理：自定义 `x-delayed-message` 类型交换机，消息带 `x-delay` 头，插件内部用 **Mnesia 表 + 定时器**暂存，到点投递——**没有队头阻塞，任意延迟时间**。

```java
@Bean
public CustomExchange delayExchange() {
    return new CustomExchange("delay.exchange", "x-delayed-message",
            true, false, Map.of("x-delayed-type", "direct"));
}

// 发送：30 分钟后投递
rabbitTemplate.convertAndSend("delay.exchange", "order.close", orderId, m -> {
    m.getMessageProperties().setDelay(30 * 60 * 1000);   // 毫秒，任意值
    return m;
});

@RabbitListener(queues = "order.close.queue")
public void closeOrder(Long orderId) { /* 查单未支付则关单 */ }
```

**注意**：插件暂存消息在**单个节点内存+Mnesia**，集群中该节点挂了未到期消息会丢——交易级场景要么接受（配合定时扫表兜底），要么用 RocketMQ。

### 方案三：RocketMQ 原生延迟消息（交易场景首选）

```java
// 4.x：18 个固定等级 1s 5s 10s 30s 1m 2m ... 30m 1h 2h ...（30m=等级16）
message.setDelayTimeLevel(16);           // 30 分钟

// 5.x：任意时间戳（底层时间轮）
message.setDeliverTimeMs(System.currentTimeMillis() + 30 * 60 * 1000);

producer.send(message);
```

Broker 内部有 `SCHEDULE_TOPIC_XXXX` 延迟主题 + 定时调度，到期才转回真实主题投递。**无队头阻塞、Broker 持久化、可靠性高**——所以电商订单超时取消几乎都用它。

## 方案选型对比

| 方案 | 延迟精度 | 可靠性 | 复杂度 | 适用 |
|------|---------|--------|--------|------|
| TTL+DLX（每档一队列） | 秒级 | 高（持久化） | 低，但档位固定 | 固定几档延迟 |
| RabbitMQ 延迟插件 | 毫秒级 | 中（单节点） | 低 | RabbitMQ 技术栈通用 |
| RocketMQ 延迟消息 | 秒级/精确 | 高 | 零配置 | 交易场景首选 |
| Redis 过期监听 | - | **低**（过期事件不可靠，可能丢/晚） | 低 | ❌ 只能辅助，不能主方案 |
| 定时任务扫表 | 分钟级 | 高 | 低 | 数据量小/兜底（下面说） |

**生产实践：延迟队列 + 定时扫表双保险**——延迟消息负责及时性，每小时扫表兜底（防消息丢失/插件故障导致漏关），两道网都不漏单。

## 延迟消息的其它用途

| 场景 | 用法 |
|------|------|
| 失败重试退避 | 消费失败后发一条 5s/30s/5min 的延迟消息做梯度重试（比 requeue 死循环优雅） |
| 预约提醒 | 会议开始前 15 分钟推送提醒 |
| 限时优惠自动过期 | 发到期消息触发状态更新 |
| 流程编排超时 | 审批 48h 未处理自动升级 |

## 面试问法

**Q: RabbitMQ 怎么实现延迟队列？**
A: 两种：TTL+死信队列，利用消息过期死信转发，但 TTL 队列有队头阻塞，只能按延迟档位拆队列；或者官方延迟插件，x-delayed-message 交换机带 x-delay 头任意延迟，注意插件单节点可靠性。交易场景建议 RocketMQ 原生延迟消息（4.x 固定 18 档、5.x 时间轮任意延迟），再加定时扫表兜底防漏单。

**Q: 死信队列有什么用？**
A: 承接三类死信：消费拒绝且不重入队、TTL 过期、队列超长。核心价值是让"失败"可见可控——重试耗尽的消息进死信，记录告警人工兜底，而不是无声丢弃；同时是实现延迟消息的机制之一。
