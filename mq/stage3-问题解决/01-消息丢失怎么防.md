# 01 · 消息丢失怎么防

> 🎬 **配套交互演示**：[diagrams/reliability.html](../../diagrams/reliability.html)——四大故障场景单步动画：Confirm 失败→补偿重发、消费失败→重试3次→死信落库、应用重启丢 Confirm→补偿捡回。

面试第一高频。"消息丢了"不是一句话的事——**三个环节各有各的丢法，各有各的堵法**。

## 全链路丢失地图

```
Producer ──①──→ Broker ──②──→ Queue ──③──→ Consumer
   ① 生产端丢：网络失败/进程崩溃，消息没到 Broker
   ② Broker 丢：消息在内存没落盘，宕机没了
   ③ 消费端丢：拿到消息还没处理完就丢了（或处理失败但已确认）
```

## ① 生产端：别"以为"发出去了

**丢法 A：`convertAndSend` 不报错就当成功**

`basicPublish` 是异步的——方法返回时消息只是**塞进了网络缓冲区**。此后进程崩溃/网络闪断/Broker 宕机，消息无声消失。

**堵法：Confirm 确认 + 失败补偿**（原理见 stage2/03）：

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    template:
      mandatory: true
```

```java
rabbitTemplate.setConfirmCallback((data, ack, cause) -> {
    if (!ack) {
        // 消息没到 Broker：记入"发送失败表"，由定时任务重发
        msgRecordService.markFail(data.getId(), cause);
    }
});
```

**丢法 B：Confirm 回调还没回来，应用挂了**（进程被 kill -9、发布重启）

Confirm 是异步的，发出到收到确认之间有几十毫秒窗口。这个窗口内的崩溃，你连"失败"都不知道。

**堵法：本地消息表（业务库兜底，面试加分项）**

```
1. 业务事务内：INSERT 订单 + INSERT 待发送消息表(status=待发送)   ← 同一个本地事务，原子
2. 事务提交后发 MQ
3. Confirm 回调成功 → 更新消息表 status=已发送
4. 定时任务扫描：status=待发送 且 超过 30 秒 → 重发（带同一 messageId，幂等兜底）
```

```sql
CREATE TABLE mq_send_record (
    id BIGINT PRIMARY KEY,
    message_id VARCHAR(64) UNIQUE,     -- 幂等键
    payload TEXT,
    status TINYINT,                    -- 0待发送 1已发送 2失败
    retry_count INT DEFAULT 0,
    created_at DATETIME
);
```

本质：**把"MQ 发送"这个不可靠操作，变成数据库事务内的一条记录 + 可重试的补偿任务**。代价是多一次 DB 写 + 一张表，所以只用于**必须不丢**的消息（订单、支付），普通通知类消息 Confirm 重试即可。

> RocketMQ 直接内置了这套逻辑的升级版——事务消息（stage4/03 详解），这就是电商公司偏爱它的原因。

## ② Broker 端：持久化 + 多副本

**丢法：消息在内存页缓存，还没 fsync 到磁盘，机器断电。**

堵法（stage2/02 详解）：
1. **持久化三件套**：durable exchange + durable queue + persistent message；
2. 关键队列用 **Quorum Queue**（Raft 多副本，多数节点落盘才算成功）；
3. 磁盘、内存监控告警（Broker 达阈值会 block 生产者，表现像"丢消息"其实是堵消息）。

## ③ 消费端：处理完再确认

**丢法：autoAck=true，消息一投递就从队列删除。消费者拿到消息后：处理抛异常 → 消息没了；进程崩了 → 消息没了。**

堵法：

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto          # 抛异常不确认（或 manual 手动 ack）
        default-requeue-rejected: false # 重试耗尽不重回队列
        retry:
          enabled: true
          max-attempts: 3
```

铁律：**先做业务，后确认；处理不确定成败（比如下游 RPC 超时），不能确认**——此时留着 Unacked，消费者重启后消息会重投。配合幂等（stage3/02），宁可重，不可丢。

## 完整加固代码（demo 的 reliable 包）

```java
// 生产端三保险发送
public void sendReliable(OrderMsg msg) {
    // 1. 本地消息表记录（与业务同事务）
    msgRecordService.savePending(msg);
    // 2. 带幂等 ID 发送
    rabbitTemplate.convertAndSend("biz.topic", "order.create", msg,
            new CorrelationData(msg.getMessageId()));
}
// 3. Confirm 成功回调 → msgRecordService.markSent(msgId)
// 4. XXL-Job/定时任务 → 扫描超时未确认的记录重发
```

## 不需要 100% 不丢的消息，别过度设计

| 消息类型 | 级别 | 方案 |
|---------|------|------|
| 订单创建、支付成功 | 绝不能丢 | 本地消息表 + Confirm + 持久化 + 手动ACK |
| 积分变动、优惠券发放 | 允许极小概率丢 | Confirm + 持久化 + AUTO ack + 重试 |
| 实时弹幕、在线提醒 | 丢了无所谓 | 默认配置，性能优先 |

**架构原则：可靠性和成本成正比，按业务分级投入，别所有消息都上全套保险。**

## 面试满分模板

> "消息丢失要分三段看：生产端用 Publisher Confirm 确认到达，失败进补偿；对强可靠消息用本地消息表，业务和消息记录同一事务，定时补偿重发；Broker 端持久化三件套，高可用用 Quorum Queue 多副本；消费端关闭自动 ack，业务成功后再确认，失败重试耗尽进死信人工处理。同时配合幂等设计容忍重发，最终达到不丢。"

## 检查清单（上线前过一遍）

- [ ] `publisher-confirm-type: correlated` + `publisher-returns: true` + `mandatory: true`
- [ ] Confirm 失败回调里**真的有**补偿动作（很多项目只打了个 log，等于裸奔）
- [ ] 队列 durable、消息 persistent、（关键队列）quorum
- [ ] 消费端非 autoAck（AUTO + retry 或 MANUAL）
- [ ] 消费者幂等已实现（下一章）
- [ ] 死信队列已配置 + 有监控（重试耗尽的消息去了哪，看得见）
