# 04 · 消息堆积怎么治

凌晨告警：`order.queue` 的 Ready 从 200 涨到 200 万。怎么办？

## 第一步：判断"堆积"是不是真问题

先看业务：

- **可追赶型**：活动结束洪峰过去，消费速率 > 生产速率，几小时能消化完 → 不用慌，确认内存/磁盘没爆即可。
- **追赶不上型**：消费速率 < 生产速率持续存在，或积压的是"有时效的消息"（如订单超时取消）→ 必须立刻处理。

判断依据（管理界面 + 监控）：

```
Queues 页：
  Ready ↑ Unacked = prefetch 满额 → 消费者活着但处理慢/卡住
  Ready ↑↑ Unacked = 0            → 消费者挂了/断连
  Publish rate vs Ack/Deliver rate 曲线 → 谁快谁慢一目了然
```

## 堆积的四大根因（先诊断再动手）

| 根因 | 特征 | 药方 |
|------|------|------|
| 1. 消费者挂了/断连 | Unacked=0，无消费速率 | 拉起消费者，看崩溃日志 |
| 2. 消费逻辑慢 | Unacked 满额，单条耗时高 | 优化下游：DB 慢查询、外部 RPC 超时 |
| 3. 消费能力不足 | 速率比 1:N，就是不够快 | **扩容消费者/批量消费** |
| 4. 生产暴涨 | 生产曲线陡增（大促/爬虫/事故） | 限流 + 上面三条一起上 |

**经典真实案例**：消费者每处理一条消息同步调用一次风控接口（200ms），风控系统一慢，队列秒堆 50 万。这时候疯狂扩消费者没用——**瓶颈在风控接口**，扩的消费者只会把它打得更死。先看瓶颈在哪一跳。

## 应急预案（生产事故 SOP）

### 场景 A：消费者挂了 → 修复 + 自动恢复

Spring AMQP 自带重连，但代码 bug 导致消费者反复崩溃时，消息会因 nack 反复重投。先看日志定位 bug，必要时**临时降级**：把消费逻辑改成"快速 ack + 存库延后处理"，先止血让队列动起来。

### 场景 B：消费太慢，紧急扩容（经典面试题）

**难点：RabbitMQ 消费者的并行度上限 = 队列数**（一个队列同一时刻最多一个消费者持锁干活，多消费者只是竞争分发）。队列只有 1 个，起 10 个消费者也没用，得先**扩队列**。

标准三步（RocketMQ 官方同款思路，RabbitMQ 也适用）：

```
第 1 步：新建 10 倍数量的队列（如 1 个 → 10 个）
第 2 步：写一个"搬运工"程序：只消费不处理，从老队列原样转发到 10 个新队列
第 3 步：部署 10 倍消费者去消费新队列，消费能力 ≈ ×10
```

```
[老队列 200w条] ──搬运工(只转发)──→ queue-1 ──→ consumer ×10
                                  queue-2 ──→ consumer ×10
                                  ...
                                  queue-10 ──→ consumer ×10
```

注意事项：
- 搬运工用 `basicGet` 拉取 + 转发，消息属性（messageId、持久化标记）要原样带上，否则丢失幂等键。
- 这是**临时架构**，消化完堆积后回收，长期仍是正常队列数。
- 换成 Kafka/RocketMQ：直接**加分区/队列 + 加消费者实例**即可，不需要搬运工——这是日志型 MQ 运维上省心的地方。

### 场景 C：消息过期无价值 → 跳过

积压的是"3 小时前的库存变更通知"，业务上已经没有意义：

- 配置队列 `x-message-ttl` 让旧消息自动过期进死信（不进消费者）；
- 或临时写个消费者 `basicAck` 丢弃（务必记录日志/存档，事后可补偿）。
- **能重建的数据直接重建**：堆积的是"缓存刷新通知"→ 放弃消费，直接全量刷一遍缓存更快。

## 治本：让堆积不再发生

### 1. 消费端提速（性价比最高）

```java
// 批量监听：一次拿一批，DB 用批量 SQL
@RabbitListener(queues = "log.queue", containerFactory = "batchFactory")
public void handleBatch(List<LogMsg> msgs) {
    logMapper.insertBatch(msgs);    // 一次网络往返处理 100 条
}

// 容器配置
factory.setBatchListener(true);
factory.setConsumerBatchEnabled(true);
factory.setBatchSize(100);

// 并发扩容（多队列时有效）
spring.rabbitmq.listener.simple.concurrency: 8
spring.rabbitmq.listener.simple.max-concurrency: 16
```

- 单条处理里的**同步 RPC 改并行/异步**、**DB 逐条改批量**，通常能提 5~20 倍。
- prefetch 调大（如 50~250）减少网络往返。

### 2. 队列容量规划：Lazy Queue + 磁盘

可预见堆积（大促）的队列提前配置 lazy（stage2/02），容量按"峰值生产速率 × 预计追赶时间 × 消息大小"估算磁盘。

### 3. 生产端限流（从源头削峰）

大促前给生产入口加限流（Sentinel/网关限流），超出的直接拒绝/降级——**永远比事后治理堆积便宜**。

### 4. 消费也要保护下游（新手盲区）

**消费者太快也会制造事故**：堆积 100 万条，你起 50 个消费者全速消化，下游 DB 被打挂 → 处理失败 → requeue → 恶性循环。

```yaml
# 消费限速：控制消费者并发 + prefetch
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 4       # 别开太多
        prefetch: 10
```

必要时在消费逻辑里加 Semaphore/RateLimiter，**把消费速率匹配到下游能力**，而不是"能消费多快就多快"。

## 监控告警（事前 5 分钟，事后 5 小时）

必须配的三个告警：

| 指标 | 阈值示例 |
|------|---------|
| 队列 Ready 数 | > 1 万 告警，> 10 万 电话 |
| 消费延迟（最老消息年龄） | > 5 分钟 告警 |
| 消费者掉线 | 即时告警 |

RabbitMQ 自带 Prometheus 插件（`rabbitmq_prometheus`），配 Grafana 大盘即可。

## 面试问法

**Q: 几百万消息堆积怎么处理？**
A: 先诊断根因——消费者挂了、消费慢还是生产暴涨。修复消费者或优化消费瓶颈（往往在下游 DB/RPC）。扩容走"扩队列+搬运工+扩消费者"三步，并行度受队列数限制。有时效的消息可放弃过期数据事后补偿。治本靠批量消费、合理并发、Lazy Queue、生产限流，且消费速率要匹配下游能力，避免把下游打挂造成二次事故。
