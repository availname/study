# 01 · 削峰填谷：秒杀系统

> 🎬 **配套交互演示**：[diagrams/seckill-funnel.html](../../diagrams/seckill-funnel.html)——设定用户数与库存，看四层漏斗逐层过滤的动态数字（10w 用户 → DB 只收 1000 单）。

终极场景：10 万人抢 1000 件商品。数据库写能力 ~3000/s，流量是它的 30 倍。看 MQ 在整个漏斗里怎么用。

## 全景架构：四层漏斗

```
   10w 用户点击
        │
┌───────▼─────────────────────────────────────────┐
│ ① 接入层：按钮置灰/答题/验证码 → 流量先散开 30%    │  剩 7w
├──────────────────────────────────────────────────┤
│ ② 网关层：Sentinel/Nginx 限流 2w QPS             │  剩 2w
├──────────────────────────────────────────────────┤
│ ③ Redis 预扣库存（Lua 原子）：库存没了直接拒绝     │  剩 1000+并发竞争
├──────────────────────────────────────────────────┤
│ ④ MQ 异步下单：抢到资格的请求发进队列              │
│      DB 消费者按 3000/s 匀速创建订单 ← 削峰核心！   │
└──────────────────────────────────────────────────┘
```

**MQ 的角色精确地说是第 ④ 层**：让"下单写库"这个最重的动作，以数据库能承受的速率进行，洪峰被队列吸走。

**没有 MQ 会怎样？** 即使 Redis 挡住了库存，通过预扣的 1000+ 个请求仍会瞬间打到 DB：1000 个 INSERT 同时来，连接池爆、锁竞争、超时雪崩。MQ 把"瞬间 1000"抹成"每秒 3000 内"，DB 从容创建订单。

## 关键设计一：Redis 预扣库存（Lua 原子）

判断"能不能买"用 Redis，判断"买成功"用 DB——中间靠 MQ 连接：

```lua
-- seckill.lua：判断+扣减必须是原子的，否则并发下超卖
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil then return -1 end           -- 活动不存在
if stock <= 0 then return 0 end              -- 已售罄
redis.call('decr', KEYS[1])
return 1                                      -- 预扣成功
```

```java
public Result seckill(Long userId, Long skuId) {
    // ① 限流（注解/网关层）
    // ② 一人一单判断（setnx userId）
    if (!redisTemplate.opsForValue().setIfAbsent("seckill:user:" + userId, "1").equals(true)) {
        return Result.fail("重复抢购");
    }
    // ③ Lua 原子预扣
    Long r = script.execute(seckillScript, List.of("seckill:stock:" + skuId));
    if (r != 1) {
        redisTemplate.delete("seckill:user:" + userId);   // 没抢到，放开限制
        return Result.fail("已售罄");
    }
    // ④ 发 MQ，异步创建订单。到此接口返回"排队中"，总耗时 <50ms
    SeckillMsg msg = new SeckillMsg(snowflake.nextId(), userId, skuId);
    rabbitTemplate.convertAndSend("seckill.exchange", "order.create", msg,
            new CorrelationData(String.valueOf(msg.getOrderId())));
    return Result.queuing(msg.getOrderId());   // 返回订单号，前端轮询结果
}
```

## 关键设计二：消费端落库（削峰的"放水口"）

```java
@RabbitListener(queues = "seckill.order.queue")
public void createOrder(SeckillMsg msg) {
    // ① 幂等：订单号唯一索引（消息重投不重复下单）
    // ② DB 扣库存 + 建订单，同一事务：
    //    UPDATE seckill_stock SET stock = stock-1 WHERE sku_id=? AND stock>0
    //    affectedRows=0 → Redis 和 DB 不一致（如 Redis 被回滚过），补偿修正
    orderService.createWithStock(msg);
}
```

要点：

- 消费速率被 `concurrency`/`prefetch` 天然限制，**DB 永远只承受这个速率**；
- DB 库存 `WHERE stock > 0` 是**最后一道防超卖**（Redis 层防 99%，DB 层兜底防 100%）；
- 消费失败（如 DB 瞬时抖动）：重试 → 死信 → **人工补发**；同时**归还 Redis 库存**（ incr 回去，让用户还能抢）。

## 关键设计三：用户如何知道结果

接口返回"排队中"，前端轮询（或 SSE/长连接推送）：

```java
@GetMapping("/seckill/result/{orderId}")
public Result result(@PathVariable Long orderId) {
    Order order = orderService.findByOrderId(orderId);
    if (order == null) {
        // 队列还没消费到：继续轮询（前端一般轮询到 5~10 秒超时判负）
        return Result.queuing();
    }
    return Result.ok(order);   // 有订单 → 抢到了，跳转支付
}
```

**体验设计**：抢购按钮点击后变"排队中…"动画，多数用户 2~5 秒内拿到结果。这 2~5 秒就是 MQ 消化的时间——**用几十秒的排队体验，换来系统不崩**。

## 为什么不用同步扣 DB？

算一笔账（1000 件商品，10w 并发）：

| 方案 | DB 压力 | 结果 |
|------|---------|------|
| 同步 DB 扣库存 | 10w 请求全打 DB | 连接池爆，全站雪崩，可能超卖 |
| Redis 预扣 + 同步 DB 落库 | 1000 请求瞬间打 DB | 不崩但瞬时毛刺，依赖 DB 抗住峰值 |
| **Redis 预扣 + MQ 异步落库** | 匀速 ≤3000/s | **平稳，DB 玩的一样** |

## 兜底与收尾

- **活动结束**：队列里剩余消息快速批量落库/直接按 Redis 数据结算（部分系统允许最终以 Redis 为准 + 对账修正）。
- **Redis 与 DB 对账**：活动结束后跑对账 job，比对预扣数/实建订单数/DB 库存，差异补偿。
- **降级预案**：MQ 挂了 → 降级为"直接同步落库 + 网关强限流到 DB 可承受 QPS"，牺牲成功率保可用。

## 面试问法

**Q: 秒杀系统怎么设计？MQ 的作用是什么？**
A: 分层漏斗——前端/网关限流挡量，Redis Lua 原子预扣挡库存，MQ 承接预扣成功的请求异步落库。MQ 的作用是削峰：把瞬时写请求以 DB 可承受的速率匀速消费，接口立即返回排队号，前端轮询结果。可靠性上：订单号唯一索引防重复下单，DB 层 stock>0 兜底防超卖，消费失败进死信并归还 Redis 库存，事后 Redis/DB 对账。
