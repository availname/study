# 02 · 订单超时自动取消（延迟队列实战）

> 🎬 **配套动画**：[diagrams/delay-task.html](../../diagrams/delay-task.html)——四种真实结局逐帧推演：消息准时关单 / 消息丢了扫表兜 / 双路同时到 CAS 仲裁 / 用户先支付两路落空。

需求：下单 30 分钟未支付 → 自动取消订单、释放库存。日订单百万级，谁也扛不住"每分钟扫全表"。

## 三种方案对比

| 方案 | 原理 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| ① 定时任务轮询 | 每分钟扫 `status=待支付 AND created_at < now-30min` | 简单 | 扫描压力大、延迟最高 1 分钟、分页扫不全风险 | 数据量小可用，大促必挂 |
| **② 延迟队列** | 下单时发 30min 延迟消息，到点消费关单 | 精准、即时、无扫描压力 | 依赖 MQ 可靠性 | **主流方案** |
| ③ Redis 过期监听 | key 过期事件回调 | 简单 | **过期事件不保证及时、不保证送达**（Redis 惰性删除） | ❌ 不能当主方案 |

生产标配：**② 延迟队列为主 + ① 低频扫表兜底**（每 5~10 分钟扫一次小批次，防延迟消息丢失导致的漏单——两层防御，都不重）。

## 完整链路

```
下单成功
   │
   ├─→ [DB] 订单 status=10(待支付)，锁定库存
   │
   └─→ 发延迟消息(orderId, delay=30min)
              │
        30 分钟后消费者收到
              │
              ├─→ 查订单：status 还是 10？
              │       ├─ 是 → 关单：CAS UPDATE status 10→50(超时关闭) + 释放库存 + 通知
              │       └─ 否(已支付/已取消) → 什么也不做（延迟消息天然幂等）
              │
用户支付回调（任意时刻可能与关单并发！）
              │
              └─→ CAS UPDATE status 10→20(已支付)
                    ↑ 两个操作只有一方能成功，这就是并发安全
```

## 核心代码

**下单后发延迟消息**（RabbitMQ 延迟插件版，demo 用 2 分钟方便演示）：

```java
@Transactional
public void createOrder(Order order) {
    orderMapper.insert(order);                          // status=10
    stockService.lock(order.getSkuId(), order.getCount()); // 锁库存
    rabbitTemplate.convertAndSend("delay.exchange", "order.timeout",
            order.getOrderId(), m -> {
                m.getMessageProperties().setDelay(2 * 60 * 1000);
                return m;
            });
}
```

**关单消费者**：

```java
@RabbitListener(queues = "order.timeout.queue")
public void onTimeout(Long orderId) {
    // 关键：CAS 状态机更新，只有"待支付"才能被关
    int updated = orderMapper.closeIfPending(orderId);
    if (updated == 1) {
        stockService.release(orderId);                  // 释放库存
        notifyService.orderClosed(orderId);             // 通知用户
    }
    // updated=0：订单已被支付/已取消 → 正常情况，什么都不做
}
```

```sql
-- 状态机 CAS，幂等且并发安全
UPDATE t_order SET status = 50, close_time = NOW()
WHERE order_id = #{orderId} AND status = 10;
```

## 最精彩的部分：关单 vs 支付的并发竞态

用户在第 30 分钟的最后一秒点了支付——**支付回调**和**关单消费者**同时处理同一订单：

```
时间线（没保护时的事故）：
t0: 关单消费者查到 status=10，准备关单
t1: 支付回调也查到 status=10，准备置为已支付
t2: 支付成功：status=20，钱已扣
t3: 关单执行：status=50，释放库存！
→ 灾难：用户付了钱，订单被关了，库存放给别人买了
```

**有 CAS 状态机时**：`WHERE status=10` 保证两条 UPDATE 只有一条 affectedRows=1：

| 顺序 | 结果 |
|------|------|
| 支付先赢（status=20） | 关单 UPDATE 不中 → 关单方放弃，订单正常 |
| 关单先赢（status=50） | **支付回调 UPDATE 不中 → 必须触发退款流程！** |

```java
// 支付回调里
int updated = orderMapper.markPaid(orderNo);
if (updated == 0) {
    // 订单已被关单 → 自动退款
    refundService.refund(orderNo, payAmount);
    alertService.notify("关单后支付竞态，已自动退款: " + orderNo);
}
```

> 这个竞态是**订单系统的必考题**。核心武器就是 stage3/02 的状态机 + 幂等。延迟消息本身有天然幂等性（到点查状态），真正要防的是"关单和支付互相踩"。

**RocketMQ 版**：关单消费者收到的是延迟消息，代码逻辑完全一样，只是发消息方式不同：

```java
Message msg = new Message("order-timeout", orderId.toString().getBytes());
msg.setDelayTimeLevel(16);                       // 4.x：等级16 = 30min
// 或 5.x 任意延迟：msg.setDeliverTimeMs(now + 30*60*1000)
producer.send(msg);
```

## 库存释放的细节

- 释放必须幂等：`release` 内部记录 `order_id` 是否已释放（去重表/Redis），防延迟消息重复消费导致库存被多放。
- 释放量与锁定单对应，用"库存流水表"（lock/release 各记一笔）可对账。

## 扫表兜底

```java
@Scheduled(cron = "0 */5 * * * ?")
public void sweepExpiredOrders() {
    // 只捞最早的一小批，避免大事务
    List<Order> expired = orderMapper.findPendingBefore(LocalDateTime.now().minusMinutes(30), 100);
    expired.forEach(o -> closeConsumerLogic(o.getOrderId()));   // 复用同一关单逻辑（幂等）
}
```

与延迟消息互为冗余：消息丢了扫表捡回来；扫表漏了消息及时关。两边都幂等，重复执行无害。

## 面试问法

**Q: 订单 30 分钟未支付自动取消怎么实现？**
A: 下单时发 30 分钟延迟消息（RocketMQ 延迟等级或 RabbitMQ 延迟插件），消费者到点查单，仍是待支付则 CAS 关单（UPDATE ... WHERE status=10）并释放库存。重点是关单与支付回调的并发竞态：靠状态机 CAS 保证只有一方生效，关单后支付则自动退款。同时用低频定时扫表兜底防漏单，关单逻辑全链路幂等。
