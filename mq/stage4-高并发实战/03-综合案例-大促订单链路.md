# 03 · 综合案例：大促订单链路与最终一致性

把前三个阶段的所有技术拼成一个真实的大促订单系统。这是面试系统设计的"终极合体题"。

## 业务全景

用户支付成功后，系统要：更新订单状态、扣真实库存、加积分、发优惠券、发短信/推送、通知仓储发货。

```
                    ┌──→ order-service   （订单置为已支付）
                    ├──→ stock-service   （扣库存）
支付成功事件 ──MQ──┼──→ points-service  （加积分）
                    ├──→ coupon-service  （发券）
                    ├──→ notify-service  （短信/推送）
                    └──→ wms-service     （通知仓库发货）
```

7 个服务，一条事件。**没有 MQ 的同步版本要 700ms+ 且任何一处挂掉全链路失败**——MQ 是这类系统的必然选择。

## 难点：分布式一致性——"支付成功"和"消息发出"必须同生共死

两个经典事故：

```
事故A：订单服务本地事务先提交（订单已支付），发 MQ 时网络失败 → 消息没发出去
      → 库存没扣、积分没加、仓库不知道发货。数据不一致，客服投诉。

事故B：先发 MQ 再执行本地事务，本地事务回滚（如后续校验失败）
      → 下游全都消费了"支付成功"，实际订单是失败的。更严重。
```

要"本地事务"和"发消息"**原子**——但它们跨了 DB 和 MQ 两个系统，没有分布式事务协议帮我们一把就做不到。两个主流解法：

## 解法一：本地消息表（任何 MQ 都能用）

stage3/01 讲过的方案在订单场景的完整形态：

```
┌─ 本地事务 ─────────────────────────────┐
│ 1. UPDATE 订单 status=已支付             │
│ 2. INSERT local_msg(id, payload,        │
│    status=待发送, next_retry=now+30s)   │
└────────────────────────────────────────┘
3. 事务提交后异步发 MQ（不阻塞主流程）
4. Confirm 成功 → 标记已发送
5. 补偿任务扫描超时未发送的记录 → 重发（同一 message_id）
```

- **原理**：把"发消息"降级为"本地库里的一行数据"，与业务同事务，天然原子；发送变成可无限重试的补偿任务。
- **保证**：最终一定发出（不丢），配合消费端幂等（不重）→ 最终一致。
- **代价**：每单多一次 DB 写 + 一张表 + 一个补偿 job。

## 解法二：RocketMQ 事务消息（内置解法一，电商首选）

RocketMQ 把"本地消息表"做成了 Broker 内置功能，业务代码只写两个回调：

```
① 发送半消息（half message）——对消费者不可见，先落库在 Broker
② 执行本地事务（订单状态更新）
③ 本地事务成功 → commit 半消息（消费者可见）；失败 → rollback 删除
④ 若 ③ 的确认丢了（如应用崩溃），Broker 定时"回查"：
   调业务的 checkLocalTransaction() 查本地事务状态 → 据此 commit/rollback
```

```java
TransactionMQProducer producer = new TransactionMQProducer("order-group");
producer.setTransactionListener(new TransactionListener() {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderService.markPaid((String) arg);   // 本地事务
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 回查：查订单到底支付成功没有
        return orderService.isPaid((String) msg.getKeys())
                ? LocalTransactionState.COMMIT_MESSAGE
                : LocalTransactionState.ROLLBACK_MESSAGE;
    }
});
// 发送：producer.sendMessageInTransaction(msg, orderNo);
```

**和本地消息表的本质等价**：半消息 = 消息表的一行（存在 Broker 而不是业务库），回查 = 补偿任务。好处是省掉业务库的表和 job；代价是绑死 RocketMQ。

## 下游消费端的设计约定（每条消费链路都要有）

| 环节 | 约定 | 出处 |
|------|------|------|
| 幂等 | 所有消费者 message_id 去重 + 状态机 | stage3/02 |
| 重试 | 本地重试 3 次（退避） | stage2/03 |
| 死信 | 重试耗尽进 DLQ，落人工处理表 + 告警 | stage3/05 |
| 失败语义 | 只能"处理成功"或"进死信"，**不允许静默丢弃** | — |
| 限流 | 消费速率匹配自身 DB 能力，防被上游洪峰打挂 | stage3/04 |

## 大促前 Checklist（真实公司的预案清单）

**容量与扩容**
- [ ] 压测：预估峰值 QPS × 1.5 倍压测生产与消费链路
- [ ] 队列容量：Lazy Queue + 磁盘按"峰值×预计追赶时长"规划
- [ ] 消费者扩容提前完成（扩实例、concurrency 调优）
- [ ] RocketMQ/Kafka：分区数按消费并行度提前建好（事后扩分区影响顺序路由）

**可靠性**
- [ ] 事务消息/本地消息表生效，回查逻辑测试过
- [ ] 全链路幂等验证（重投 10 次无副作用）
- [ ] 死信监控告警配好，人工处理工具/流程就绪
- [ ] 对账 job：订单↔库存↔积分↔券 每小时核对，差异自动补偿

**降级预案（每个都要演练过）**
- [ ] MQ 集群故障 → 核心链路降级同步调用 + 网关限流，非核心（积分/短信）直接降级关闭、事后补偿
- [ ] 消费者大面积失败 → 开关切"暂存不消费"（快速 ack 存库），事后批量补
- [ ] 下游服务挂 → 对应队列停消费（防止空转+重试风暴），恢复后再追

**监控**
- [ ] Ready 堆积 / 消费延迟 / 死信量 / Confirm 失败率 四大核心指标大盘
- [ ] 事务消息回查日志可查（回查即异常信号）

## 真实事故两则（改编，帮你记住为什么）

**事故一：重复发券**
双 11 夜，优惠券服务发布重启。重启瞬间 Unacked 的 3 万条"支付成功"消息全部重投，服务端 Redis 去重键因为 Redis 也在切换而失效——**同一用户领了 3 张 50 元券**。损失约 40 万。
复盘：Redis 去重是唯一防线，违反"两层幂等"原则。修复：发券表加 `user_id+coupon_type+activity_id` 唯一索引兜底。

**事故二：消费太快打挂下游**
积分服务堆积 200 万条，SRE 上来就是加机器：5 台 × 50 并发消费。积分库是共享的 MySQL，瞬时 250 并发写把 CPU 打满，**连带影响同库的优惠券服务**，两个业务一起瘫。
复盘：消费速率必须匹配下游能力；共享 DB 的服务扩容要联动评估。修复：消费限速 + 积分库独立。

## 面试终极题

**Q: 设计一个日订单千万级的电商订单系统，消息队列如何使用？**
A: 主链路同步（Redis 预扣库存 + 订单落库），支付成功发事务消息保证订单与消息原子；下游库存/积分/券/通知/仓储各自消费，幂等+重试+死信三件套，消费速率匹配下游能力；秒杀场景独立漏斗（限流→Redis→MQ→匀速落库）；订单超时用延迟消息+扫表兜底+CAS 防支付竞态；对账 job 保最终一致；大促前容量压测、扩容、降级演练齐全。
