# 04 · 五种工作模式与交换机类型

RabbitMQ 官方定义了 7 种模式，实际最常用 5 种。**本质上只有一条规则：消息按 Binding 规则从 Exchange 路由到 Queue。**所谓"模式"只是路由规则的不同玩法。

```
生产者 ──→ [Exchange] ──binding──→ [Queue] ──→ 消费者
              ↑ 所有模式的差异都在这个箭头上
```

## 1. Simple：一对一

上一节的 Hello World。一个生产者、一个队列、一个消费者。理解了队列就理解了它，不再展开。

## 2. Work Queues（工作队列）：多个消费者抢一个队列

**场景**：任务很重（如生成报表），一个消费者处理不过来 → 起多个消费者**竞争**同一个队列，MQ 天然实现了**负载均衡**。

```
Producer ──→ [ task.queue ] ──→ Consumer-1  ✓
                          └──→ Consumer-2  ✓
                          └──→ Consumer-3  ✓
```

### 轮询 vs 公平分发（重要）

| 分发策略 | 行为 | 问题 |
|---------|------|------|
| Round-Robin（默认） | 消息轮流分给每个消费者，不看死活 | Consumer-1 处理慢时，消息堆在它的 Unacked 里，别人闲死 |
| **Fair Dispatch（公平分发）** | 消费者处理完（ack）才给下一条 | 推荐，"能者多劳" |

开启公平分发只需一个参数 **prefetch**：

```java
// Spring Boot 配置：每个消费者最多同时持有 1 条未 ack 消息，处理完才给下一条
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 1
```

prefetch 的本质是**背压（backpressure）**：Unacked 数量上限。设 1 = 处理完才给；设 50 = 攒一批提吞吐。**不是越小越好**，网络来回有成本，一般业务设 5~50，重任务设 1。

demo 里 `work` 包有完整示例：两个消费者，一个 `Thread.sleep(1000)` 模拟慢消费者，观察公平分发效果。

## 3. Publish/Subscribe（fanout）：广播

**场景**：一条"用户注册成功"事件，短信服务、积分服务、推荐服务**都要**收到。一份消息，人人有份。

```
Producer ──→ [fanout exchange] ──→ sms.queue  ──→ 短信服务
                     │           coupon.queue ──→ 优惠券服务
                     │           points.queue ──→ 积分服务
                     └── 不看 routing key，绑了的队列全发一份
```

要点：
- **每个服务一个独立队列**，都绑定到同一个 fanout 交换机。
- 消息被**复制**进每个队列，各队列独立消费，互不影响（短信服务挂了不影响积分服务收到）。
- 这是"解耦"的最经典形态。

```java
// 声明
@Bean public FanoutExchange userEventExchange() { return new FanoutExchange("user.event"); }
@Bean public Queue smsQueue() { return new Queue("sms.queue"); }
@Bean public Binding smsBinding() { return BindingBuilder.bind(smsQueue()).to(userEventExchange()); }
// 发送：routing key 会被忽略
rabbitTemplate.convertAndSend("user.event", "", user);
```

## 4. Routing（direct）：按 routing key 精确路由

**场景**：日志系统，`error` 级别的进报警队列，`info` 的进普通日志队列，但都来自同一个"日志"交换机。

```
Producer ──→ [direct exchange] ──(error)──→ alarm.queue
                     │
                     └──(info)──→ log.queue

rabbitTemplate.convertAndSend("log.direct", "error", "数据库连不上！");
rabbitTemplate.convertAndSend("log.direct", "info", "请求处理完成");
```

一个队列可以绑多个 key（`alarm.queue` 同时绑 `error` 和 `warn`）。

## 5. Topics（主题）：通配符路由，最灵活

routing key 按 `.` 分词，绑定 key 支持两个通配符：

| 通配符 | 匹配 | 例 |
|--------|------|----|
| `*` | **恰好一个**词 | `order.*` 匹配 `order.create`，不匹配 `order.create.success` |
| `#` | **零个或多个**词 | `order.#` 匹配 `order.create`、`order.create.success` |

```
                 ┌─(order.*)────────→ 每次订单变动队列（create/cancel/pay...）
[topic exchange]─┼─(order.create)──→ 只关心下单的队列
                 ├─(user.*)────────→ 用户事件队列
                 └─(#.create)──────→ 所有实体的创建事件
```

**Topic 是业务系统最常用的模式**，它是 fanout（全匹配）和 direct（精确匹配）的统一抽象。

```java
rabbitTemplate.convertAndSend("biz.topic", "order.create", order);
rabbitTemplate.convertAndSend("biz.topic", "order.create.success", order);   // 只有 order.# 的队列收得到
rabbitTemplate.convertAndSend("biz.topic", "user.register", user);           // user.* 的队列收得到
```

demo 里 `topic` 包可动手验证：两个队列分别绑 `order.*` 和 `order.#`，发不同 key 观察谁收到。

## 6/7. RPC 与 Headers（了解即可）

- **RPC 模式**：发消息带 `replyTo` 回调队列，消费者处理后把结果发回去——用 MQ 模拟 RPC，实际工作基本不用（要 RPC 直接用 Feign/Dubbo）。
- **Headers 模式**：按消息头 KV 匹配路由，性能差，几乎没人用。

## 交换机类型总结

| 类型 | 路由规则 | 典型场景 |
|------|---------|---------|
| （默认） | routing key = 队列名，直投 | 简单队列 |
| fanout | 广播，忽略 routing key | 事件广播、缓存失效 |
| direct | routing key 精确相等 | 按级别分发（日志 error/info） |
| topic | 通配符匹配 | **业务事件总线（最常用）** |
| headers | 消息头匹配 | 少用 |

## 死记硬背版（面试口诀）

> 生产者发消息给**交换机**，交换机按**绑定规则**把消息路由到**队列**，队列推给**消费者**。
> fanout 全广播、direct 精确匹配、topic 通配符（`*` 一个词 `#` 一串词）。
> 多消费者抢一个队列 = 负载均衡；每服务一个队列绑同一交换机 = 广播解耦。
> **prefetch 控制背压，能者多劳。**

**消息没匹配到任何队列会怎样？** 默认直接丢弃！这是很多人第一次踩的坑（发错 routing key 消息凭空消失）——Stage 2 的 Return 机制就是给这种情况上保险的。

## 面试问法

**Q: RabbitMQ 五种工作模式各适合什么场景？**
A: 一条主线：消息从生产者到交换机，交换机按绑定规则路由到队列——模式差异全在路由规则上。Simple/Work 是"一队列一/多消费者"（Work 用 prefetch 公平分发做负载均衡，能者多劳）；fanout 广播（每服务独立队列绑同一交换机，一份消息复制多份，互不影响）；direct 按 routing key 精确匹配（日志按 error/info 分流）；topic 通配符匹配（`*` 一个词 `#` 一串词），业务事件总线最常用——它是 fanout 与 direct 的统一抽象。

**Q: prefetch 是什么？设多少合适？**
A: 消费者最多同时持有的 Unacked 消息数，本质是背压。默认轮询分发不看死活，慢消费者会堆消息；prefetch=1 即公平分发（处理完才给下一条）。不是越小越好——网络来回有成本，一般业务 5~50，重任务设 1。

**Q: 消息没匹配到任何队列会怎样？**
A: 默认直接丢弃——发错 routing key 消息凭空消失。生产上配 Return 机制（mandatory + 回调监听）+ 发送端 Confirm 才能发现（stage2/03 可靠性基石）。
