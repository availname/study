# 01 · 为什么需要消息队列

> 🎬 **配套交互演示（容易看懂版）**：[diagrams/why-mq.html](../../diagrams/why-mq.html)——快递柜比喻：切换"没有快递柜/有了快递柜"两种模式，外卖员、你、618 洪峰三种角色的差别一目了然。

## 从一个真实场景说起

用户注册成功后，系统要做三件事：发欢迎短信、送新人优惠券、给推荐人加积分。

**第一版：同步调用**

```java
public void register(User user) {
    saveUser(user);                    // 50ms
    smsService.sendWelcome(user);      // 300ms（调第三方短信网关）
    couponService.grantNewUser(user);  // 80ms
    pointsService.addPoints(user);     // 60ms
    // 总耗时：490ms，用户全程干等
}
```

三个致命问题：

1. **慢**：耗时是所有下游之和（490ms），任何一个下游变慢，注册就变慢。
2. **耦合**：以后加一个"发邮件"，就得改注册代码。积分服务改动接口，注册也跟着改。
3. **脆弱**：短信服务挂了 → 注册失败。用户会问：注册和短信有什么关系？凭什么短信挂了不让我注册？

**第二版：引入消息队列（MQ）**

```java
public void register(User user) {
    saveUser(user);                          // 50ms
    rabbitTemplate.convertAndSend("user.event", user); // 2ms
    // 总耗时：52ms。短信、优惠券、积分服务各自监听消息，自己处理
}
```

注册服务只负责"喊一声：有人注册了"，谁关心谁订阅。短信服务挂了？消息存在队列里，等它恢复再消费，注册完全不受影响。

## MQ 的三大作用

### 1. 异步提速

把"必须现在做完"和"可以稍后做完"分开：

```
同步：注册 ──→ 短信 ──→ 优惠券 ──→ 积分     490ms，串行等待
异步：注册 ──→ MQ（2ms）                   52ms，立刻返回
              ├─→ 短信服务（自己慢慢处理）
              ├─→ 优惠券服务
              └─→ 积分服务
```

用户响应时间只取决于核心链路，非核心链路全部后移。

### 2. 应用解耦

- 生产者**不知道**也不关心谁在消费，只发"事件"。
- 新增下游（比如加个"风控审计"服务）**不需要改动生产者一行代码**，订阅即可。
- 下游挂了不影响生产者，消息堆积在队列等它恢复——这叫**削峰也削故障**。

### 3. 削峰填谷

秒杀场景：瞬时 10 万请求打进来，数据库只能扛每秒 3000 写。

```
不削峰：10w QPS ─────────────────→ DB 直接被压垮
削峰：  10w QPS ──→ [MQ 水库] ──→ 3000/s 匀速放水 ──→ DB 稳定运行
```

MQ 像水库：洪峰时先蓄住，下游按自己的能力匀速消费。用户侧返回"排队中"，稍后查询结果。

> 一句话总结：**同步调用是"强绑定的接力赛"，MQ 是"松耦合的广播站 + 蓄水池"。**

## MQ 不是银弹：什么时候不该用

| 场景 | 要不要用 MQ | 原因 |
|------|------------|------|
| 转账扣款后必须立刻告知余额 | ❌ | 需要同步、强一致，MQ 是异步的 |
| 下单扣库存（超卖风险） | ⚠️ 慎用 | 核心链路一般同步扣（Redis 预扣），MQ 做后续异步落库 |
| 小项目、QPS 几十 | ❌ | 引入 MQ = 多一个组件要部署、监控、运维，得不偿失 |
| 需要"处理结果"才能继续 | ❌ | MQ 是发后即忘，要结果用 RPC/HTTP |

同时记住：**引入 MQ 会带来新的问题**——消息可能丢、可能重、可能乱序、可能堆积。这些正是 Stage 3 的主题。天下没有免费的架构午餐，MQ 用"最终一致 + 异步"换来了"高吞吐 + 解耦"。

## 主流 MQ 选型对比

| 维度 | RabbitMQ | RocketMQ | Kafka |
|------|----------|----------|-------|
| 开发语言 | Erlang | Java | Scala/Java |
| 单机吞吐 | 万级（1~10w/s） | 十万级 | 百万级 |
| 延迟 | 微秒~毫秒级（最低） | 毫秒级 | 毫秒级（批量时） |
| 事务消息 | ❌ | ✅ | ⚠️（弱） |
| 延迟/定时消息 | 插件支持 | ✅（原生，5.x 任意延迟） | ❌ |
| 顺序消息 | 单队列有序 | ✅ 分区有序 | ✅ 分区内有序 |
| 消息堆积能力 | 一般（需惰性队列） | 强（磁盘） | 极强 |
| 消息回溯 | ❌ 消费即删 | ✅ | ✅ 按时间/offset |
| 典型场景 | 业务解耦、中小流量 | 电商交易、订单链路 | 日志采集、大数据流、埋点 |

**怎么选（实用版）**：

- 学习概念、中小公司业务解耦 → **RabbitMQ**
- 电商交易链路、需要事务消息/延迟消息 → **RocketMQ**（国内大厂主流）
- 日志、埋点、大数据管道、超高吞吐 → **Kafka**
- 只有一个消息场景拿不定 → 小流量 RabbitMQ，大流量 RocketMQ

## 核心名词速查表

后面所有章节都会用到，先混个脸熟：

| 名词 | 一句话解释 |
|------|-----------|
| Producer | 生产者，发消息的程序 |
| Consumer | 消费者，收消息的程序 |
| Broker | MQ 服务器本身（RabbitMQ 的一个进程就是一个 Broker） |
| Queue | 队列，消息存放的地方，先进先出 |
| Exchange | 交换机（RabbitMQ 特有），生产者把消息发给它，它按规则路由到队列 |
| Binding | 交换机和队列之间的绑定规则 |
| Topic | 主题（Kafka/RocketMQ 的核心概念），逻辑上的消息分类 |
| ACK | 消费确认，消费者告诉 Broker"这条我处理完了" |
