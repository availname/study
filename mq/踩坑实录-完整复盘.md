## 第一部分：代码级深坑（5 个）

### 坑一：消息双重序列化，消费者反序列化炸掉

**涉及文件**：`order/OrderService.java` · `messaging/ReliableMessagePublisher.java`
**对应教程**：stage1/03（消息结构）、stage2/03（可靠性链路）

#### 现象

冒烟测试第一次下单+支付，消费者直接抛异常栈：

```
Caused by: com.fasterxml.jackson.databind.exc.MismatchedInputException:
Cannot construct instance of `Messages$OrderPaidEvent`
(although at least one Creator exists):
no String-argument constructor/factory method to deserialize from String value
('{"orderNo":"O202611021638532074","userId":1,...}')
```

注意错误信息里的诡异嵌套：`(String)""{\"orderNo\":\\\"...\\\"}"""` —— **JSON 字符串里包着一层转义的 JSON 字符串**。

随后本地重试 3 次（0.5s→1s→2s）全部失败，消息进入死信队列，`DeadLetterConsumer` 落库：

```
[死信] messageId=order-paid-O202611021638532074 queue=mall.order.paid.queue reason=rejected
```

**有趣的反面**：这次"事故"反而完整验证了可靠性链路——重试、死信、落库、告警日志全部按设计工作。**可靠性基建防住了我们自己写出来的 bug**，这正是它们存在的意义。

#### 排查过程

错误信息几乎直接给出了答案：消费者收到的是 String，期望的是对象。回看发送端代码：

```java
// 坏代码（OrderService，修复前）
publisher.sendInTransaction("mall.order", "order.paid",
        "order-paid-" + orderNo,
        toJson(new OrderPaidEvent(...)));   // ← 这里先 toJson 成了字符串
```

而 `ReliableMessagePublisher.doSend` 内部：

```java
byte[] body = om.writeValueAsBytes(payload);   // ← 又把字符串当对象序列化一次
```

结果：对象 → JSON 字符串 →（被当成 POJO 再序列化一次）→ "JSON 包 JSON" 的字节流。

#### 根因

**序列化职责没有收敛**：业务层和基础设施层各做了一次序列化，谁都不知道对方的存在。

#### 修复

- 业务代码**只传对象**，删除 `OrderService` 里的 `toJson` 方法和 `ObjectMapper` 依赖；
- 序列化**只发生在** `ReliableMessagePublisher` 一处（它同时负责本地消息表的 payload 落库序列化，一份数据两处使用）。

```java
// 好代码
publisher.sendInTransaction("mall.order", "order.paid",
        "order-paid-" + orderNo,
        new OrderPaidEvent(...));   // 直接传对象
```

#### 教训

1. **消息序列化必须全工程收敛到一个点**（转换器/发送门面），任何业务代码手动序列化消息体都是坏味道。
2. 反序列化报错先看**收到的原始字节长什么样**——"JSON 包 JSON" 这种嵌套形态，根因几乎必然在发送端多做了一次。
3. 死信队列 + 日志帮我们把一次失败的现场完整保留了下来。**没有死信链路的系统，这种 bug 只会表现为"下游没收到，但发送方说成功了"**，排查难度翻十倍。

### 坑二：内存发号器重启归零，新订单被自己的幂等层"误杀" ⭐

**涉及文件**：`seckill/SeckillService.java` · `messaging/MessageDedupService.java`
**对应教程**：stage3/02（幂等）—— 本坑是该章节最深刻的反面教材

#### 现象

第二轮压测（应用重启后）秒杀请求全部"成功入队"，RabbitMQ 管理界面显示消息**被正常消费**（Ready/Unacked 归零、无死信），但数据库里秒杀订单数是 **0**。消费端日志一片安静——没有任何报错、没有任何落库日志。

```
接入层：抢购成功_已入队=100           ← Redis 预扣正常
RabbitMQ：队列清空，消费完成           ← 消息被"消费"了
数据库：seckill_orders = 0            ← 但什么都没发生
日志：（一片安静）
```

#### 排查过程

1. 先怀疑应用是不是有幽灵旧实例在跑（旧代码监听同一队列）→ `netstat` 查 8090/5673 端口，确认单实例；
2. 查队列深度和消费者数量 → 全部正常，消息确实被 ack 了；
3. 应用和数据库两边同时查 → 一致地"没有"，说明不是视图问题；
4. 读消费代码，发现 `tryConsume` 返回 false 时会**静默 return**（没打日志）——立刻怀疑去重层；
5. 查 Redis：`redis-cli --scan --pattern "mq:dedup:*"` —— 输出里赫然躺着 `mq:dedup:seckill-1000036`，而新一轮压测的订单号恰好也是 `1000001` 起步。

#### 根因（两层缺陷叠加）

```java
// 缺陷 A：SeckillService 用内存计数器发订单号
private final AtomicLong orderIdGen = new AtomicLong(1_000_000);
long orderId = orderIdGen.getAndIncrement();
```

应用重启 → 计数器归零 → 新订单号 `1000001`、`1000002`… 与**上一实例**发出去的订单号完全相同。

```java
// 缺陷 B：幂等跳过路径静默 return，没有任何日志
if (!dedup.tryConsume("seckill-order", messageId)) {
    return;   // ← 消息被"合法"地吞掉了，无人知晓
}
```

而幂等键 `mq:dedup:seckill-{orderId}` 的 TTL 是 24 小时——旧实例留下的键还活着，新请求撞上去，被判为"重复消息"跳过。

**完整的因果链**：

```
重启归零的计数器 → 新单号撞旧幂等键 → tryConsume 返回 false
→ 静默 return → 消息 ack 删除 → 无死信无日志 → 数据静默丢失
```

#### 修复

```java
// 修复 A：全局唯一发号器（时间戳<<12 | 序列），重启绝不撞号
long orderId = Ids.nextId();
```

```java
// 修复 B：幂等跳过必须打日志（教学工程中保留；生产还可加"跳过计数"监控指标）
if (!dedup.tryConsume("seckill-order", messageId)) {
    log.info("[幂等] 重复消息跳过 messageId={}", messageId);
    return;
}
```

并清理了 Redis 里的全部残留去重键后重测：200/200 全部落库，对账一致。

#### 教训

1. **幂等键的唯一性必须由"全局唯一 ID"保证**（雪花/Leaf/DB 序列），内存计数器、随机数都不行——重启、多实例、时钟回拨都会破坏它。这是 stage3/02 "用业务键而非随机 UUID" 原则的延伸：**业务键不仅要语义正确，还要生成机制可靠**。
2. **幂等的反面是误杀**。幂等层挡掉的不一定真的是重复消息——键设计有缺陷时，它挡掉的是新消息。任何"看起来在正常工作"的防线，都要能回答"它会不会把不该挡的挡掉"。
3. **静默分支是排查噩梦的根源**。所有 `if (...) return;` 式的防御分支都应该留痕（日志/指标），否则系统"吞数据"时你连从哪查起都不知道。
4. 排查方法论价值：**"消息被消费了但数据没变化"** → 沿着消费代码里每一个"提前 return"的分支查，逐一问"什么条件下会走到这里"。

### 坑三：本地消息表 insertPending 被遗漏，可靠性基建形同虚设

**涉及文件**：`messaging/ReliableMessagePublisher.java`
**对应教程**：stage3/01（本地消息表）

#### 现象

排查坑二时顺带发现：`t_mq_send_record` 表**永远是空的**。按设计，每条走可靠链路的消息都应该先写一张"待发送"记录。

#### 根因

`sendInTransaction` 方法里我只实现了"事务提交后发送"（`afterCommit` 回调），**忘了写事务内的 `insertPending` 调用**：

```java
// 修复前：只注册了 afterCommit，消息表压根没写
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override public void afterCommit() { doSend(...); }
});

// 修复后：先写本地消息表（与业务同事务），提交后再发送
String payloadJson = toJson(payload);
sendRecordDao.insertPending(messageId, exchange, routingKey, payloadJson);  // ← 关键行
TransactionSynchronizationManager.registerSynchronization(...afterCommit → doSend...);
```

后果：Confirm 回调的 `markConfirmed/markFailed` 更新不到任何行；补偿任务 `SendRetryJob` 扫描不到任何待补偿消息——**本地消息表的"写记录 → 确认/补偿"闭环少了第一环，整个机制等于没建**。

#### 教训

1. **可靠性机制的每一环都要有"存在性验证"**。写完基建必须实际触发一遍：这条消息在表里有没有记录？状态有没有流转？——本次验证对账/补偿时顺手查了表，才暴露出来。
2. 闭环类设计（写记录→确认→补偿）**最怕中间少一环且不报错**。每一环都该有可观测信号：记录数、状态分布、补偿触发次数。本项目后来把 `send-records` 状态统计做进了 `/api/admin/stats` 正是为此。
3. "先写记录再动作"这个模式里，**写记录和动作必须由同一个入口保证**，不能依赖调用方记得。

### 坑四：扫表兜底误关秒杀单，制造 Redis/DB 库存漂移

**涉及文件**：`order/OrderDao.java` · `compensation/OrderSweepJob.java`
**对应教程**：stage4/02（超时关单双保险）、stage4/01（秒杀双库存）

#### 现象

重启应用后终端日志刷出一串：

```
[扫表兜底] orderNo=S1000491 ...
[扫表兜底] orderNo=S1000492 ...
（几十条秒杀单被逐一"超时关闭"）
```

秒杀单（演示版）没有支付环节，永远停在"待支付"状态——被扫表任务当成了普通超时单批量关掉。关单会执行 `release` 释放 **DB** 库存，但 **Redis** 预扣的库存和已购集合不会归还（那是消费失败路径的职责）→ 两套库存体系数据漂移。

#### 根因

扫表条件只筛了状态和时间，没筛业务类型：

```sql
-- 修复前
WHERE status = 10 AND created_at < NOW(3) - INTERVAL ? MINUTE

-- 修复后
WHERE status = 10 AND seckill_flag IS NULL
  AND created_at < NOW(3) - INTERVAL ? MINUTE
```

#### 教训

1. **兜底逻辑的筛选条件必须与业务语义对齐**。"超时未支付就关闭"对普通订单成立，对"演示版秒杀单"不成立——兜底任务跑得越勤快，错误放大得越快（20 秒一轮，瞬间关掉几百单）。
2. **双库存体系（Redis 预扣 + DB 真扣）里，任何"归还/释放"动作必须两边同步**，并且要有状态标记防止重复归还。真实的秒杀超时释放应该走"归还 Redis + 释放 DB + 记流水"的原子流程（已列入 README 扩展练习）。
3. 这也是 stage4/02 "延迟消息 + 扫表双保险" 设计的隐藏代价：**两道网都要独立正确**，一道网写错比没有这道网更糟。

### 坑五：对账公式写窄，明明数据正确却报"不一致"

**涉及文件**：`admin/AdminController.java`
**对应教程**：stage4/01（对账兜底）

#### 现象

秒杀测试数据完全吻合（Redis 800 = DB 订单 500 + 普通单 3...），但对账端点却报 `"一致": false`。

#### 根因

```java
// 修复前：DB 锁定总量 只和 秒杀订单数 比
view.put("一致", (total - remain) == dbSeckillOrders);

// 修复后：DB 锁定总量 = 秒杀订单 + 普通活跃订单（待支付+已支付 都占库存）
long normalCount = ...SELECT COALESCE(SUM(count),0) FROM t_order
                   WHERE seckill_flag IS NULL AND status IN (10, 20);
view.put("一致", (total - remain) == (dbSeckillOrders + normalCount));
```

另外秒杀消费建单时**没写库存流水**（`t_stock_log`），导致流水对账缺失秒杀部分——补上了 `stockDao.log("S"+orderId, ..., "LOCK")`。

#### 教训

1. **对账是"用代码表达业务恒等式"**。等式两边少了任何一项（普通订单占用的库存），对账就会对正确的数据报错误——**对账系统自己也要被验证**：先构造一个"应该一致"的场景确认它报 true，再构造"故意不一致"确认它报 false。
2. 库存流水是库存体系的"账本"。任何动库存的操作（锁/扣/放）都必须记流水，否则对账只能对结果不能对过程，出了差异无法定位是哪笔操作造成的。
3. 排查顺序意识：看到"不一致"先**手工验算一遍等式两边**（本次手工一算 503 = 500 + 3 立即明了），再怀疑数据真出了问题——多数时候是公式错，不是数据错。

### 坑六：Docker Desktop 崩溃后反复起不来（engine.sock 损坏）

**对应教程**：stage1/02（RabbitMQ 安装与 Docker 使用）

#### 现象

拉取镜像过程中 Docker Desktop 弹窗崩溃：

```
An unexpected error occurred
starting services: initializing Secrets Engine:
listening on unix:///C:/Users/C1668/AppData/Local/docker-secrets-engine/engine.sock:
rename ...engine.sock → ...engine.sock.stale:
The file cannot be accessed by the system.
```

此后每次启动都死在同一处，引擎反复不可用（`docker info` 报 `npipe ... dockerDesktopLinuxEngine` 连接失败）。

#### 根因

上次异常退出在 `%LOCALAPPDATA%\docker-secrets-engine\` 留下了一个 **NTFS 元数据损坏的 socket 文件**。Docker 启动时按惯例要把它改名成 `.stale` 再重建，但这个文件的 MFT 记录已损坏——所有访问都返回"系统找不到指定的文件/无法访问"，启动流程卡死。**目录项还在、文件已"不存在"**，所以连 `takeown` 都报"找不到路径"。

#### 排查与修复过程（一波三折，按时间线记录）

| 步骤 | 操作 | 结果 |
|------|------|------|
| 1 | git-bash `rm -f engine.sock` | 删不掉（`-?????????` 权限位异常） |
| 2 | `cmd del /f /a "\\?\...engine.sock"` | "系统无法访问该文件" |
| 3 | `takeown` + `icacls /reset`（修 ACL） | 目录 ACL 修复成功，文件本身仍拒绝访问 |
| 4 | `mv` / PowerShell `Rename-Item` 改名整个目录 | "访问被拒绝" |
| 5 | 写批处理脚本 + **UAC 提权**执行 `del` | ✅ 损坏文件删除成功 |
| 6 | 清理空的 `.broken` 残壳目录 | 完成 |
| 7 | 重启 Docker Desktop | ✅ 引擎 10 秒就绪，一切正常 |

注：过程中权限系统拦过两次"不可逆删除"操作，最终改为**用户亲自以管理员身份运行修复脚本**——这本身也是正确的安全实践：破坏性操作应当由人确认执行。

#### 教训与可复用解法

1. **Docker Desktop "unexpected error + secrets engine/engine.sock" 崩溃的标准解法**：
   1. 彻底退出 Docker Desktop（任务栏图标 Quit，确认无 `docker`/`com.docker` 进程）；
   2. **管理员** PowerShell 执行：
      ```powershell
      del /f /a "$env:LOCALAPPDATA\docker-secrets-engine\engine.sock"
      rd /s /q "$env:LOCALAPPDATA\docker-secrets-engine"
      ```
   3. 重启 Docker Desktop。**只删 socket 管道文件，镜像和卷在 WSL2 虚拟盘里，不受影响；切勿点弹窗里的 "Reset to factory defaults"**（那才会清空镜像）。
2. NTFS 元数据损坏的文件会出现"ls 看得见、一切操作都说不存在"的诡异状态，普通权限无法处理，**必须管理员提权**。
3. 诊断引擎状态用 `docker info` 退出码判断比 `docker ps` 更可靠（前者直接探引擎，后者混入镜像/网络因素）。

### 坑七：镜像拉取中断/奇慢（unexpected EOF + 20 分钟无进度）

**对应教程**：stage1/02

#### 现象

1. `docker compose up -d --wait` 拉镜像时连接中断：`unexpected EOF`，MySQL 断在 249MB；
2. 重试后另一个通道又超时；换 Docker Hub 直连拉 rabbitmq，**20 分钟停留在同一进度**；
3. 期间还被一个误判带偏：`docker images` 表格里的 `249MB` 是"去重后独占大小"而非下载进度——实际 MySQL 已完整下载（`SIZE` 列 1.1GB 才是全量）。

#### 排查

1. `docker images --format` 两次间隔 30 秒对比 → 大小没变，确认拉取停滞；
2. `docker compose ls` / `docker ps` → 发现另一个项目的容器（es/kafka/minio）在正常跑，证明引擎本身健康，问题纯粹在网络通道；
3. 检查后台任务输出文件 → 全空——因为把 pull 的输出管道给了 `tail`，进度被憋到进程结束才输出，**观察方法本身失效了**。

#### 修复

换国内镜像源直拉 + 打回原 tag（不动全局配置）：

```bash
docker pull docker.m.daocloud.io/library/rabbitmq:3.13-management
docker tag docker.m.daocloud.io/library/rabbitmq:3.13-management rabbitmq:3.13-management
```

镜像源通道秒级完成（此前直连的尝试已把大部分层预热进本地缓存）。若要长期解决，在 Docker Desktop → Settings → Docker Engine 加：

```json
{ "registry-mirrors": ["https://docker.m.daocloud.io"] }
```

#### 教训

1. **国内环境拉 Docker Hub 镜像，先配镜像源再开工**，能省掉大部分等待和排查。
2. 镜像源直拉 + `docker tag` 打回原名是**零侵入**方案：不改 daemon.json、不重启引擎、不影响其它项目。
3. 长时间命令的进度要**直接观察原始输出**（`docker pull` 不接管道），经 `tail`/重定向的中转会把流式进度憋没，让你误判"卡死"。
4. `docker images` 的 SIZE 列语义要清楚：两列分别是"全量大小/去重独占大小"，看下载进度别被后者骗了。

### 坑八：缺 spring-retry 依赖，消费重试配置被静默忽略

**涉及文件**：`demo/pom.xml`、`mq-mall/pom.xml`
**对应教程**：stage2/03（Spring 两套消费重试姿势）

#### 现象与根因

`application.yml` 里配置了：

```yaml
spring.rabbitmq.listener.simple.retry:
  enabled: true
  max-attempts: 3
```

但 classpath 上**没有 `spring-retry` 依赖时，这套配置会被静默忽略**——不报错、不告警，消费失败直接走"不重回队列 → 死信"。表现为：本该重试 3 次的消息"第一次失败就进死信"，重试形同虚设。

#### 修复

```xml
<dependency>
    <groupId>org.springframework.retry</groupId>
    <artifactId>spring-retry</artifactId>
</dependency>
```

#### 教训

1. **Spring Boot 大量"约定式开关"依赖条件装配**：配置写了 ≠ 生效，生效前提（依赖/类在 classpath）必须核实。"静默降级"是 Spring 生态的双刃剑——好用，但失效时毫无声息。
2. 可靠性参数（重试次数、ack 模式）上线前要**实测一次失败路径**：故意抛异常，数一数日志里到底重试了几次。本项目 `mq-mall` 的 pom 从一开始就带了这个依赖，`demo` 是测试中回查时补上的。
3. 与坑一互相印证：**失败链路的每个环节（重试次数、进死信时机）都要用一条毒消息实地验证**，这正是 `/api/admin/test-dlq` 端点存在的意义。

## 第三部分：工具与流程小坑

### 编译错误一批（Windows 中文 + UTF-8 混排）

首次编译 `mq-mall` 报 4 类错误，修复耗时主要在"看懂乱码报错"上：

| 错误 | 原因 | 修法 |
|------|------|------|
| `ApiResponse.error` 泛型不匹配 | `error` 返回 `ApiResponse<Void>`，lambda 推断成 `Map` 类型用不了 | 改成泛型 `error<T>`；`orElseGet` 处显式类型见证 `.<ApiResponse<Map<String,Object>>>map(...)` |
| `queryForList(sql)` 找不到合适重载 | `NamedParameterJdbcTemplate` 的无参重载歧义，无法推断 T | 统一传 `new MapSqlParameterSource()` 走 `(sql, SqlParameterSource)` 重载 |
| `MessageProperties` 找不到符号 | import 漏了 `org.springframework.amqp.core.MessageProperties` | 补 import |
| `SeckillOrderRequest`/`StringRedisTemplate` 找不到 | 拆分/重写类时 import 没跟上 | 补 import |

**教训**：①中文 Windows 的 git-bash 下 Maven 错误输出是 GBK 乱码，`mvn -q compile 2>&1 | grep -E "ERROR.*\.java"` 过滤出文件名行最省事；②JdbcTemplate 具名参数版所有查询都显式传 `MapSqlParameterSource`，规避重载歧义。

### @Transactional 自调用代理失效（设计期规避）

秒杀消费者最初把 `@Transactional doCreate` 和 `@RabbitListener` 写在同一类里自调用——**Spring 事务靠代理，自调用不走代理，事务会静默失效**。写的时候就拆成了 `SeckillOrderTxWorker` 独立 bean。**这不是踩坑而是规避，但值得记录**：它是与坑三同级别的"静默失效"家族成员。

### 冒烟测试的数据污染

中途多轮测试互相污染（上一轮的订单影响下一轮的对账），一度出现"代码是对的、数据是脏的"的假象（如对账 false 实际是早前手动 UPDATE 库存所致）。**修法**：写了一套完整重置脚本（清 8 张表 + Redis 键 + 秒杀状态），每次完整验证前先重置。**教训**：演示/测试环境要有"一键重置"，否则排查会在脏数据里打转；`/api/seckill/reset` 端点和本文的重置 SQL 都是为此。

### 终端日志中文乱码

Spring Boot 日志（UTF-8）在 GBK 终端显示成 `绉掓潃` 状乱码。不影响功能，排查时靠 logback 配置 `charset` 或读 `/actuator/logfile` 解决。**教训**：日志里给关键路径加上英文标签（如 `[seckill]`、`[dlq]`）能避免乱码干扰快速定位。

## 第四部分：Stage 5 扩建时新踩的坑（2026-11-04）

### 坑九：两道防线交互产生"谁都没设计过的第三种路径" ⭐

**涉及文件**：`media/MediaPipelineConsumers.onSubmitted` · `VideoController.retry`
**性质**：坑二的变体升级版——单个防线都对，叠加后出现死角

#### 现象

FAIL 视频转码失败后走 `/retry` 重提，消息发出去、队列清空、无报错——任务却永远卡在 UPLOADED。日志里只有一行：

```
[转码] 重复消息跳过 V7347301205897218
```

#### 根因：防线交互矩阵没过一遍

失败链路上有两道防线，它们的执行序列产生了一个隐藏分支：

```
第 1 次尝试：tryConsume 写幂等键 → cas 状态推进 → sleep → 业务失败
            → catch：markFailed + dedup.fail(删键) + throw        ✓ 设计内
第 2 次尝试（spring-retry）：tryConsume 写键（键刚删，写入成功）
            → casStatus(UPLOADED→TRANSCODING) 返回 0（状态已是 FAILED！）
            → 走"状态不对，跳过"分支 → return（正常 ack）
            → 此分支不经过 catch → dedup.fail 没执行 → 幂等键残留 24h   ← 死角
人工 retry：重发消息 → tryConsume 撞上残留键 → "重复消息跳过" → 永远卡死   ← 事故
```

状态机 CAS 和幂等键**各自都正确**：状态机挡重复推进 ✓，幂等键挡重复消息 ✓。但重试第 2 次时"状态已被上一轮标记为 FAILED"和"幂等键刚被清理又重写"两个事实组合出：**消息被正常 ack、键残留在 Redis、任务停在 FAILED**——三态组合谁都没设计过。

#### 修复

1. **retry 端点重发前显式 `dedup.fail` 清键**——人工重提的语义本来就是"覆盖历史"，这是最符合语义的位置；
2. `resetForRetry` 同时接受 FAILED 和 UPLOADED（覆盖"消息被拦导致卡在 UPLOADED"的中间态）。

#### 教训

1. **加第二道防线时，必须把"两道防线同时触发"的 2×2 矩阵过一遍**（A拦B放 / A放B拦 / 都拦 / 都放）。防线之间的"交接空白带"是 bug 温床。
2. "catch 里做清理"这种模式只覆盖**异常路径**——任何"提前 return 的正常路径"也要过一遍清理清单。与坑二同根源：**防御分支必须留痕 + 清理逻辑必须覆盖所有出口**。
3. 这个坑第一次没测出来，是因为第一轮测试只验证了"失败 → FAILED"，没验证"失败 → 重提 → 成功"的**完整往返**。可靠性链路的测试必须测到"从哪跌倒从哪爬起来"那一步。

### 坑十：事务纪律防御检查的"半覆盖"（防御检查也要配套设计）

**涉及文件**：`media/VideoController.submit`
**性质**：防御检查立功，但暴露检查时机的设计问题

#### 现象

提交视频报 `"sendInTransaction 必须在业务事务内调用"`——这正是 publisher 的强制事务纪律在起作用（防"业务提交了消息却没发"）。**但注意**：`taskDao.insert` 在异常抛出前已经执行，且当时方法上没有 `@Transactional`，**insert 已自动提交**——结果留下 4 个永远停在 UPLOADED 的僵尸任务（业务提交了、消息没发出去）。

防御检查**防住了消息侧，没防住数据侧**——因为它抛异常的时机在 insert 之后，而事务边界又没把两者包起来。

#### 修复

`submit` 方法加 `@Transactional`（注释注明生产中应下沉 Service 层），insert 和消息记录同事务——异常时一起回滚，僵尸任务不再产生。

#### 教训

1. **防御性检查防的是"下游动作"，防不了"检查之前已经发生的副作用"**。副作用（DB 写）必须在事务边界内，检查才有完整的回滚保护。
2. 好的防御检查会把问题"炸"出来而不是静默吞掉——这次直接靠报错定位到缺事务，是防御检查价值的正面示范。
3. 清理僵尸数据时用 `created_at` 时间戳圈定范围，避免误删正常数据。

### 坑十一：curl 中文参数不编码 → Tomcat 400（RFC 3986）

冒烟测试第一批请求全部 400。日志（DEBUG 级才可见）：

```
Invalid character found in the request target [/api/videos?title=Spring0xbd0xcc0xb3...]
```

git-bash 的 curl 把 GBK 中文字节原样塞进 URL，Tomcat 按 RFC 3986 拒绝非合法字符。**修法**：`--data-urlencode "title=中文"`（走表单体，curl 自动百分号编码）；别手拼 URL 查询串传中文。这个 400 是 Tomcat 层直接拒绝，**请求根本没进 Spring**，所以业务日志一片空白——又一个"日志安静但有问题"的案例，靠访问日志/抓包才能定位。

### 坑十二：git push 间歇性失败——本机代理截断 22 端口（Clash 环境）

**现象**：`git push` 到 GitHub 间歇性成功/失败，失败时报：

```
Connection closed by 28.0.0.7 port 22
fatal: Could not read from remote repository.
```

`28.0.0.7` 不是 GitHub 的 IP（GitHub 是 140.82.x.x）——**本地代理（Clash TUN）劫持了 22 端口的 SSH 长连接**，节点不稳时直接断开。同一仓库隔 1 分钟重试可能就成功，极难排查。

**根因**：GitHub SSH 默认走 22 端口，代理对 22 端口长连接的处理不稳定。

**修法（官方备用通道，一劳永逸）**：`~/.ssh/config` 强制 GitHub 走 443 端口：

```
Host github.com
    HostName ssh.github.com
    Port 443
    User git
    IdentityFile ~/.ssh/id_ed25519_github
    IdentitiesOnly yes
```

验证：`ssh -T git@github.com` 出现 `Hi <用户名>!` 即通。

**教训**：①`Connection closed by <可疑内网段IP>` = 中间设备/代理干预，不是对端问题；②凡是长期使用 GitHub SSH 的环境（尤其挂代理的开发机），**配置文件直接写 ssh.github.com:443**，别等间歇性失败折磨你；③同类问题对照：git https 推送失败则看代理的 http 端口配置。

## 总结：十二坑合四条的元教训

把上面所有坑收拢，其实是四条元原则：

1. **静默失效是最高危的故障形态**。
   坑二（幂等误杀吞数据）、坑三（消息表没写）、坑八（重试没生效）、坑九（防线交互死角）、`@Transactional` 自调用——全部**不报错、只丢失正确性**。对策：每一道防线都要有可观测信号（日志/表/指标），每一次"提前 return"都要留痕。
   **坑九补充**：加第二道防线时，两道防线同时触发的 2×2 矩阵必须过一遍——防线之间有交接空白带。

2. **收敛职责，别让两层各自聪明**。
   坑一（双重序列化）、坑五（对账公式与业务脱节）的根源都是"两个地方对同一件事各有一套理解"。对策：序列化收敛一处；对账恒等式由一个端点唯一定义并自我验证。

3. **防线本身也要被测试**。
   坑一反而证明了死信链路靠谱（因为它防住了 bug），坑三证明消息表没被验证（所以缺了一环没人知道）。对策：每条可靠性链路用"毒消息"实测——本项目 `/api/admin/test-dlq`、`/api/admin/reconcile` 就是为此而设。

4. **环境问题先分清"引擎坏了还是网络慢了"**。
   坑六七的排查都从"另一个项目的容器在正常跑"这个观察找到了分岔口。对策：环境排障先找"对照组"，再决定是修引擎还是换通道；国内环境拉镜像，镜像源是第一选项而不是最后手段。
