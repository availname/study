# 02 · 消费模式、重试与顺序消息

[01 篇](01-RocketMQ架构与事务消息.md)解决了"发得可靠"，这篇解决"收得可控"——消费模式怎么选、失败怎么重试、顺序怎么保证。三者都是面试必问，也都有现成的教学对照（你学过的 RabbitMQ 语义在这里逐条落位）。

## 一、消费模式：集群 vs 广播

```
集群模式（默认）          广播模式
Topic: 6 条消息           Topic: 6 条消息
ConsumerA ── 分摊消费      ConsumerA ── 全量 6 条
ConsumerB ── (各消费一部分) ConsumerB ── 全量 6 条
```

| | 集群模式 | 广播模式 |
|--|---------|---------|
| 语义 | 同组**分摊**（负载均衡） | 同组每台**全量** |
| 失败重试 | ✅ 进重试队列重投 | ❌ **不重试**，失败即丢 |
| 死信 | ✅ 有 %DLQ% 兜底 | ❌ 没有——**失败的消息就没了** |
| 消费位点 | 服务端记录（组维度） | 客户端各自记录 |
| 场景 | 绝大多数业务 | 配置刷新/本地缓存广播（发 mq stage1 fanout 的场景） |

**对照你学过的**：集群≈Kafka 消费组分摊（[stage5/03](../stage5-Kafka专篇/03-消费者组位移提交与Rebalance.md)）；广播≈RabbitMQ fanout 每个队列一份。**广播模式"失败即丢"是面试细节坑**——用它就得自己容错，所以默认无脑集群。

## 二、失败重试：内置的 16 级递增

```
消费抛异常 / 返回 RECONSUME_LATER
  → 消息进 %RETRY%消费组名（服务端帮你管的重试队列）
  → 按 10s 30s 1m 2m ... 2h 共 16 级间隔递增重投
  → 超过 maxReconsumeTimes（默认 16）→ 进 %DLQ%消费组名 死信队列 → 人工/补偿
每次重投 message.getReconsumeTimes() 递增——可用于"第 3 次还失败就转人工"的分池逻辑
```

**对照 RabbitMQ**：RabbitMQ 原生只有 nack 重入队（无限循环风险，要自己配死信，[stage3/05](../stage3-问题解决/05-延迟消息与死信队列.md)）；RocketMQ 把"**有限次递增重试 + 死信隔离**"做成了一等公民——重试消息在独立队列，**不阻塞正常消息消费**（这就是堆积治理里"毒丸消息隔离"的现成实现，[stage3/04](../stage3-问题解决/04-消息堆积怎么治.md)）。

**消费幂等照旧自己写**：RocketMQ 至少一次投递（重试机制必然产生重复）——两层防线（Redis setnx + DB 唯一键）原样搬，[stage3/02](../stage3-问题解决/02-消息重复怎么幂等.md)。**没有任何 MQ 替你幂等**，这是面试的标准答案句。

## 三、顺序消息：RocketMQ 的招牌能力

需求：同一订单的 创建→支付→发货 事件必须按序消费。RabbitMQ 的做法是"同一队列+单消费者"（[stage3/03](../stage3-问题解决/03-消息顺序怎么保.md)——**牺牲并行度**）；RocketMQ 给了更精细的两级控制：

```java
// ① 生产者：同一 key（订单号）路由到同一队列——顺序的物理基础
producer.send(msg, (mqs, msg1, arg) -> {
    long orderId = ...;
    return mqs.get((int) (orderId % mqs.size()));   // hash 选队列
}, orderId);

// ② 消费者：队列内单线程消费（MessageListenerOrderly）
consumer.registerMessageListener((MessageListenerOrderly) (msgs, context) -> {
    // 同一队列的消息串行处理；不同队列仍并行——顺序与吞吐兼得
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});
```

**原理一句话**：分区内有序（同 Kafka 分区语义）+ 队列内加锁串行消费。**代价**：①队列内慢消息会阻塞后续（毒丸又在同队列=顺序性防毒丸的两难）；②消费者变更时队列重分配瞬间可能短暂乱序——**关键业务仍建议消息体带序号，消费端校验兜底**（stage3/03 的"顺序性自防御"）。

## 四、堆积视角的三件套（对照 stage3/04 治堆积）

| 手段 | RocketMQ 现成能力 | RabbitMQ 对应 |
|------|------------------|---------------|
| 毒丸隔离 | 重试队列自动分流 | 需自配 DLX |
| 提高并行 | 加队列数+加消费者（顺序消息则受限） | 加消费者（预取） |
| 兜底回溯 | 消费位点可重置（重放历史消息） | ❌ 消费即删，无位点回溯 |

**位点可重置是 Kafka/RocketMQ 系的杀手锏**：消息消费后仍保留（CommitLog 按时间过期），出事故可以"把消费位点拨回去重放"——RabbitMQ 消费即删做不到，这也是选型表里"需要回溯选 Kafka 系"的原因（[stage2/04](../stage2-底层原理/04-三大MQ底层对比.md)）。

## 面试问法

**Q: RocketMQ 怎么保证顺序消费？**
A: 两级控制：生产端 `MessageQueueSelector` 把同一业务 key（订单号 hash）路由到同一队列——分区内天然有序；消费端 `MessageListenerOrderly` 队列内加锁单线程消费，队列间仍并行。代价是队列内慢消息阻塞与 Rebalance 瞬间乱序，所以关键业务消息体带序号、消费端校验兜底。

**Q: 消费失败怎么办？和 RabbitMQ 比呢？**
A: 返回 RECONSUME_LATER 进服务端管理的 %RETRY% 队列，16 级间隔（10s~2h）递增重投，超限进死信 %DLQ%，重试不阻塞正常消费。RabbitMQ 原生 nack 无限重入队要自配死信——RocketMQ 把"有限重试+死信隔离"内置了。重试必然产生重复，**消费幂等永远自己写**（Redis+DB 两层）。另外 RocketMQ 位点可重置支持历史回溯，RabbitMQ 消费即删做不到。
