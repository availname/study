# 简历项目话术：mq-mall 与 community 怎么写进简历

> 简历上项目描述只有 3~5 行，但**每一行都是面试追问的钩子**——你写的每个词都必须能经得起"怎么实现的？"、"为什么这么设计？"、"出了问题怎么办？"三连问。本文给出两个项目的简历话术 + 追问应对地图（全部链接回教程，追问前先复习）。

## 简历写法公式

```
一句话项目定位 + 2~3 条技术亮点（每条 = 难点 + 方案 + 结果数字）+ 技术栈行
```

**忌**：堆功能清单（"实现了登录、注册、发帖…"——这是需求不是简历）；**要**：写"难点是怎么解决的"。

## 项目一：mq-mall（订单消息系统）

### 简历描述（可直接抄，按真实情况微调）

> **mq-mall —— 基于 RabbitMQ 的订单消息系统**（个人项目）
> 技术栈：Spring Boot 3.2 / MySQL / Redis / RabbitMQ / MyBatis
> - 设计订单全链路异步化：本地消息表保证"订单落库与消息发送"的原子性，Confirm 回调+定时补偿重发兜底，配合消费端两层幂等（Redis setnx + DB 唯一索引），实现消息链路零丢失、幂等消费
- 实现订单超时自动关闭：延迟消息（TTL+死信）与定时扫表双保险，通过状态机 CAS（UPDATE…WHERE status=待支付）解决"关单与支付回调"的并发竞态
- 设计秒杀四层漏斗：Redis Lua 原子预扣（含一人一单）→ MQ 削峰匀速落库 → DB 条件更新兜底防超卖，压测 10w 请求下零超卖、DB 峰值写入压降至 ~3000/s
- 建立可观测闭环：死信落库告警、Redis/DB 计数对账任务、本地消息表状态大盘，故障"可见可控"

### 你的"王牌故事"（面试杀手锏，务必讲熟）

**踩坑实录坑二**：秒杀消息被幂等层"误杀"——内存发号器重启归零，订单号撞上 24h 内的幂等键，消息被静默跳过、无日志无死信、数据静默丢失。

讲法（三段式）：
> "排查这个问题时最难的点是**完全没有报错**——消息被正常消费、正常 ack，但数据库就是没有记录。最后定位到幂等键的生成逻辑：内存计数器在应用重启后归零，新生成的订单号撞上了 24 小时内旧幂等键。修复两件事：发号器换成雪花 ID（全局唯一），幂等跳过路径加了日志与指标。这件事让我把'幂等误杀'写进了 Code Review 清单——**幂等跳过必须有可观测信号**。"

一段话同时展示：排查能力（无报错定位）、根因分析（两层缺陷叠加）、修复与预防（发号器+可观测）。**这是面试的差异化王牌。**

## 项目二：community（Redis+MQ 联动社区）

### 简历描述

> **community —— Redis+MQ 联动的社区论坛**（个人项目）
> 技术栈：Spring Boot 3.2 / MySQL 8 / Redis 7 / RabbitMQ / Spring AI / Testcontainers
> - 设计内容审核异步管道：发帖限流（Lua INCR）与内容指纹去重 → MQ 管道 AI 审核（结构化输出+两级降级：重试→人工卡点）→ fanout 广播驱动 Feed 推送
- 实现 Write Behind 计数架构：阅读/点赞计数 Redis 削峰（INCR+Set 去重），定时任务以"DECR 已落库增量法"批量刷 MySQL 底账，保证增量不丢
- 用 Redis 多结构支撑业务：Bitmap 签到（含连签计算）、ZSet 热帖榜（热度算法+每小时衰减）、HyperLogLog UV、ZSet 积分榜
- 接入可观测性与 CI：Micrometer Tracing 全链路追踪（MQ 消息头自动传播 traceId）、GitHub Actions 自动构建并推送 GHCR 镜像、Testcontainers 真容器集成测试

## 项目三：learn-center（终极整合项目）

### 简历描述

> **learn-center —— 融合 Redis+MQ+AI 的在线学习平台**（个人项目）
> 技术栈：Spring Boot 3.2 / Java 17 / MySQL 8 / Redis 7 / RabbitMQ / Redisson / Spring AI
> - 设计限量抢课四层漏斗：Redisson 看门狗分布式闸门（两参 tryLock 自动续期，防多实例洪峰）→ Lua 原子预扣（名额+一人一课）→ MQ 异步建单削峰 → DB 唯一约束兜底正确性
> - 订单超时自动取消：TTL+DLX 延迟消息 → 消费端 CAS 状态机取消 → 超卖回补 DB+Redis 双账本对齐
> - 接入 Spring AI：题库智能生成（结构化输出）+ 学习工具 Agent（Function Calling 查课/查订单）

### 追问应对地图

| 简历关键词 | 必然追问 | 答案所在 |
|-----------|---------|---------|
| 看门狗锁 | 锁什么时候会自动续期？ | 只有**不传 leaseTime** 才启用：默认 30s 每 10s 续回；三参 tryLock 反而关闭（learn-center EnrollController） |
| 看门狗锁 | Lua 已经原子了为什么还要锁？ | 锁是多实例洪峰闸门（排队+快速失败挡峰值），Lua 保证 Redis 操作原子，正确性靠 DB 唯一约束——三层各司其职 |
| 抢课防重 | 拿不到锁的请求怎么办？ | 3 秒快速失败"人数过多"，前端轮询结果接口兜底体验 |
| 超时取消 | 消息重复消费/服务重启？ | CAS=1 才回补名额，重复消息 CAS=0 幂等跳过 |

## 通用亮点话术（三个项目都可讲）

**① 可靠性分级设计观**：
> "我不是所有消息都上全套保险——按业务分级：订单支付类用本地消息表全套；通知类只做 Confirm；弹幕类直接尽力而为。可靠性和成本成正比，这个分级标准我写进了团队规范。"

**② 防线交互意识**（踩坑实录坑九）：
> "我在加第二道防线（幂等）时踩过防线交互的坑：状态机短路 return 绕过了幂等键清理。之后我给团队定了规矩——**每加一道防线，必须过一遍'两道防线同时触发'的矩阵场景**。"

**③ 可观测三件套常态化**：
> "每个异步链路标配四指标：队列堆积、死信量、幂等跳过数、Confirm 失败率——消息系统的事故全都'静默'，指标是最早的哨兵。"
