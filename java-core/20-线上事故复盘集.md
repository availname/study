# 20 · 线上事故复盘集：三个完整故事线（MySQL/Redis/接口变慢）

> 🎯 **定位**：[05-常见OOM与线上排查](02-JVM虚拟机/05-常见OOM与线上排查.md) 有一段 JVM 事故故事线，[踩坑实录](../mq/踩坑实录-完整复盘.md) 有 12 个 MQ/Redis 方向的开发坑——但 **MySQL 死锁、Redis 内存打满、"接口变慢"这类运维级事故**没有完整复盘。本篇补齐：三个"从告警到修复"的完整故事，每个都按踩坑实录的体裁（现象→排查→根因→修复→教训），用的全是**你项目里真实存在的代码形态**。事故复盘是面试的王牌素材——"讲一次你印象最深的线上问题"出现率不亚于任何八股。

## 故事一：签到接口把数据库锁死了（MySQL 死锁 + 长事务）

> 场景原型：learn-center 的 `StudyController.checkin`——"SETBIT 防重 + UPDATE 积分"是正确版。下面是**教学简化版（先查再改）**在生产形态下会踩的事故。

### 现象

```
14:00 告警：签到接口 P99 从 50ms 涨到 5s；14:05 DB 连接池等待数飙满
      应用日志：大量 "HikariPool-1 - Connection is not available, request timed out"
      MySQL 侧：Threads_running 从 8 涨到 200+，签到成功率跌到 60%
      神秘点：只有签到接口报错，浏览课程一切正常
```

### 排查过程

```bash
# ① 是 MySQL 慢还是应用慢？先看谁在等
SELECT * FROM information_schema.innodb_trx ORDER BY trx_started;   -- 活跃事务
-- 发现：几十个事务卡在 LOCK WAIT，最老的事务已经跑了 40 秒（！）

# ② 看锁等待对（8.0）
SELECT * FROM sys.innodb_lock_waits;
-- waiting_pid=87 在等 blocking_pid=52；52 的 trx_query 是签到那条 UPDATE

# ③ 死没死锁？查最后死锁记录
SHOW ENGINE INNODB STATUS\G
-- LATEST DETECTED DEADLOCK：两条 UPDATE t_user SET points=points+1 WHERE id=?
-- 互相持有对方 userId 的记录锁 → 死锁，InnoDB 回滚了其中一个
```

### 根因（三层叠加）

```java
// 教学简化版签到的生产形态（错误示范）：
@Transactional   // ← 缺陷③：事务里混着 RPC/日志等慢操作，事务被拉长
public void checkin(long userId, LocalDate d) {
    Row r = jdbc.queryForObject("SELECT points FROM t_user WHERE id=?", ...);  // 缺陷①：先查
    if (r.firstSignToday()) {
        slowWechatNotify(userId);        // ← 在事务里调外部接口！200ms+ 白白持锁
        jdbc.update("UPDATE t_user SET points=points+1 WHERE id=?", userId);       // 缺陷②：热点行
    }
}
```

1. **先查后改**：读到的存在性到 UPDATE 之间有时窗，防重靠"查"靠不住（[锁体系篇](03-MySQL深入/03-锁体系.md) 间隙锁死锁案例的同族）；
2. **热点行**：同一个用户的 `points` 行被签到+支付+打卡三处并发 UPDATE，行锁排队；
3. **事务里有慢调用**：微信通知 RPC 200ms 全程持锁——40 秒长事务就是几十次重试叠加出来的。长事务还是 MVCC 天敌（undo 链不能清理，[02-事务与MVCC](03-MySQL深入/02-事务与MVCC.md) 的预告在这里应验）。

### 修复（三层防线，对应已有教学）

```java
// ① 防重换原子语义：SETBIT 旧值（learn-center 正确版）或 INSERT + 唯一索引兜底
Boolean firstTime = redis.opsForValue().setBit(signKey(userId, d), offset, true);
if (Boolean.FALSE.equals(firstTime)) { ... }          // 幂等在 Redis 层完成，不加锁

// ② 热点行消尖：积分改为 Redis INCR + 定时批量刷库（削峰，mq-mall CounterFlushJob 同款）
redis.opsForValue().increment("lc:points:" + userId);

// ③ 事务纪律：RPC/通知移出事务（先落库提交，再发通知；通知失败走 MQ 重试）
```

**教训**（可背的复盘结论）：
- **锁问题的第一现场不在代码在数据**——`innodb_trx` 里"最老事务跑了多久"是第一指标；
- **事务边界 = 锁持有边界**：事务里多一行慢调用，就多 200ms 全表级联等待；
- 防重永远用原子语义（SETBIT/唯一索引），"先查再改"在并发下既不防重又制造锁。

## 故事二：Redis 内存打满，榜单悄悄变成了"永久缓存"（淘汰策略事故）

> 场景原型：learn-center 的 `lc:rank:study`（ZSet 榜单）与 `lc:token:*`（登录态）共存一个实例。

### 现象

```
03:00 告警：Redis used_memory 达到 maxmemory 的 95%
08:30 用户反馈：登录频繁掉线（"早上还好的"）
      运维看到：evicted_keys 在涨，但没人知道哪些 key 被逐了
      神秘点：登录掉线是间歇性的——有人掉有人不掉
```

### 排查过程

```bash
# ① 谁把内存吃光了？
redis-cli --bigkeys                      # 抽样：lc:rank:study 是最大的 ZSet
redis-cli MEMORY USAGE lc:rank:study     # 确认：榜单 member 数 = 全站用户数
INFO memory | grep evicted               # evicted_keys=48213 —— 已经在逐 key 了

# ② 逐了谁？看淘汰策略
CONFIG GET maxmemory-policy              # → allkeys-lru（！）
# allkeys-lru：任何 key 都可能被逐 —— 包括 7 天 TTL 的登录态 token
# 间歇性掉线之谜：热用户常在（LRU 保住），冷用户 token 被"顺手"逐掉

# ③ 榜单为什么这么大？查写入侧代码
# StudyController: incrementScore("lc:rank:study", userId, minutes)
# —— 只增不减、无member上限、无过期：三年后它就是全站用户的全量清单
```

### 根因

| 缺陷 | 细节 |
|------|------|
| 榜单无界增长 | ZSet 只 `incrementScore`，从不清 member（毕业用户永远躺在榜上） |
| 淘汰策略一刀切 | `allkeys-lru` 让"可丢的缓存"和"不可丢的登录态"同池竞争 |
| 无内存水位告警 | 到 95% 才发现——[监控篇](13-运维部署实战/04-监控告警与Metrics.md) 说的"Redis 四指标"少了内存水位 |

### 修复

```
① 榜单瘦身：member 数设上限（只留 Top N 万）——ZREMRANGEBYRANK 砍尾部
   或按周期切键：lc:rank:study:20261110（日榜自然过期，总榜落 DB）
② 分池隔离：登录态单独实例（或至少 different db + noeviction 策略）
   —— 登录态被逐 = 用户被强制下线，这不是"缓存"，是状态，不允许淘汰
③ 监控补位：used_memory 水位 80% 告警 + evicted_keys 增速告警（03:00 的告警本该在这）
```

**教训**：
- **先分类再选淘汰策略**：key 分三类——可丢缓存（allkeys-lru）、可重建状态（volatile-lru + 带 TTL）、不可丢状态（noeviction + 单独实例）。`allkeys-*` 是把三类混在一起赌运气；
- **ZSet/Hash/Set 天然无界**：任何"只增不减"的集合都要回答"member 上限是多少、怎么退场"（大 Key 篇 [stage3/04](../redis/stage3-问题解决/04-大Key与热Key.md) 的预防章，这里给了不预防的下场）；
- `--bigkeys` 是免费的体检，上线前跑一次就能发现九成的无界集合。

## 故事三："接口变慢"——一次没有告警的退化（排查方法论）

> 没有明确报错、P99 缓慢爬升的问题最难查——这类题面试官最爱问"你怎么排查接口变慢"。

### 现象

```
三天内：订单列表接口 P99 从 120ms → 300ms → 800ms（没有台阶，是缓坡）
        CPU/内存/连接池全都正常；错误率 0%
        DB 慢查询日志：没有超过 1s 的查询（所以"不是 SQL 的锅"？——错）
```

### 排查过程（分层二分，每层只回答一个问题）

```
① 请求打到哪里变慢？—— Trace 链路（stage6/04 OTel）：网关 5ms → 应用 700ms → 拆应用内
② 应用内慢在哪一跳？—— Arthas trace（JVM 篇04 的灵魂用法）
   trace OrderController list
   → list 700ms：dao.queryForPage 680ms，其他都 <20ms → 锁定 SQL
③ SQL 明明有索引为什么慢？—— EXPLAIN 看真实执行
   EXPLAIN SELECT ... ORDER BY create_time DESC LIMIT 100000, 20
   → type=index，扫描了 10 万+ 行才取 20 行 —— 深分页！（性能优化篇的典型优化一）
④ 那为什么慢查询日志没抓到？—— long_query_time 默认 10s，680ms 根本不入日志
   → 改 long_query_time=0.2 才看清：是"每条都不算慢，但每条都在退化"
```

### 根因

业务三个月增长，订单表从 80 万行涨到 300 万行——**同一个深分页 SQL，数据量线性放大扫描量**。缓存挡住了一部分，但"跳到第 5000 页"的用户每次都回源。

### 修复（性能优化篇方案 + 工程化）

```sql
-- ① 游标分页（最优）：记住上一页末尾的 create_time/id
SELECT * FROM t_order
WHERE user_id = ? AND (create_time, id) < (?, ?)   -- 游标
ORDER BY create_time DESC, id DESC LIMIT 20;        -- 恒定扫描 20 行
-- ② 跳页需求保留时：延迟关联（先覆盖索引取主键，再回表 20 行）
SELECT t.* FROM t_order t
JOIN (SELECT id FROM t_order WHERE user_id=? ORDER BY create_time DESC LIMIT 100000, 20) x
  ON t.id = x.id;
-- ③ 兜底：产品侧限制最大跳页深度（Google 也只给你 10 页）
```

**教训**：
- **"慢查询日志没东西"≠"不是 SQL 的锅"**——`long_query_time` 默认 10s 会漏掉全部退化型慢查询，先调阈值再下结论；
- **退化型问题查"基线"**：没有台阶的变慢，几乎都是数据量/流量/统计信息漂移——问"这个 SQL 三个月前多快"，退化曲线自己会说话；
- 排查纪律：**每一层只回答一个问题**（哪一跳→哪个方法→哪条 SQL→哪个执行计划），别跳层。Trace（stage6/04）+ Arthas trace（JVM 04）+ EXPLAIN（MySQL 05）是这条链的三板斧，全部在教程里练过。

## 三个故事的公共骨架（面试收束）

```
发现（告警/用户反馈）→ 定位（分层二分，每层一个证据）→ 根因（代码/配置/容量三层各问一遍）
→ 修复（先止血再治本）→ 预防（规约 + 监控位 + 复盘文档）
```

| 故事 | 第一证据 | 根因层 | 预防位 |
|------|---------|--------|--------|
| 签到锁死 | `innodb_trx` 最老事务 40s | 代码（事务内慢调用+先查后改） | 事务纪律规约 + trx 时长监控 |
| Redis 打满 | `INFO memory` 水位 + `--bigkeys` | 配置（淘汰策略一刀切+集合无界） | 水位告警 + 上线前 bigkeys 体检 |
| 接口变慢 | Trace + Arthas trace 分层 | 容量（数据量增长放大扫描） | long_query_time 调低 + 索引评审 |

**面试问法**

**Q1: 讲一次你印象最深的线上问题？**
A: 讲故事一或故事三，按五段骨架讲（发现→定位→根因→修复→预防）。得分点不在事故多大，在**证据链是否完整**：每一步"看了什么、看到什么、推出什么"。结尾必须落在预防（规约/监控/复盘），说明形成闭环。

**Q2: 怎么排查接口变慢？**
A: 分层二分：Trace 定位慢在哪一跳（网关/应用/DB/下游）→ 应用内 Arthas trace 慢在哪一跳 → SQL 层 EXPLAIN 看执行计划 → 容量层问基线（数据量涨了多少）。注意三个易漏点：慢查询日志阈值会漏退化型慢查询；连接池等待会伪装成 DB 慢；缓存命中率下跌要先看（[监控篇](13-运维部署实战/04-监控告警与Metrics.md) 四黄金指标的延迟看 P99 不看均值）。

**Q3: 线上死锁怎么处理？**
A: `SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 看双方持锁与等待链（[锁体系篇](03-MySQL深入/03-锁体系.md)），8.0 用 sys.innodb_lock_waits 看实时等待对；先杀最老事务止血（KILL trx_mysql_thread_id），再治本：事务短、多行固定顺序、防重用唯一索引替代先查后改、RPC 移出事务。

**Q4: Redis 内存满了会发生什么？怎么防？**
A: 到 maxmemory 触发淘汰策略——allkeys-lru 会连登录态一起逐（强制下线事故）；volatile 系列只在有 TTL 的 key 里逐，无 TTL 的写直接报 OOM 错误。防：key 按可丢性分类分池、集合类型设 member 上限、水位 80% 告警、上线前 --bigkeys 体检。
