## 链 1：MQ 可靠性（从简历"消息零丢失"开始）

**Q1 简历上写了"消息零丢失"，怎么做到的？**
→ 三段答：生产端 Confirm+本地消息表（业务+消息同事务原子）/ Broker 持久化+副本 / 消费端手动 ACK+重试+死信。强调"分级"：不是所有消息都上全套。

**Q2 本地消息表？展开说说。**
→ 业务事务内 INSERT 发送记录（同事务原子）→ 提交后 afterCommit 发送 → Confirm 更新状态 → 定时补偿扫描重发（指数退避）。**主动提坑**：我们踩过 insertPending 被遗漏的坑（基建形同虚设），之后给消息表加了存在性回归测试。

**Q3 ⚠ 发送成功了，但 Confirm 回调没执行（应用重启了），消息表还是"待确认"，补偿会重发——下游不就重复消费了？**
→ 会。这正是设计意图：**宁可重复，不可丢失**（at-least-once），重复由消费端幂等拦截。两层防线：Redis setnx 快速去重 + DB 唯一索引兜底。

**Q4 🔺 幂等键怎么生成的？有没有踩过坑？**
→ **王牌故事时间**（踩坑实录坑二）：内存计数器重启归零 → 订单号撞上 24h 内旧幂等键 → 消息被静默跳过、无日志无死信、数据静默丢失。修复：雪花 ID（全局唯一）+ 幂等跳过加日志与指标。**主动总结**：幂等跳过必须有可观测信号，否则"吞数据"无从排查。

**Q5 补偿任务本身挂了呢？**
→ 补偿任务多实例部署会重复重发？→ 消息表扫描用 `SELECT FOR UPDATE SKIP LOCKED`（8.0）或分布式锁防多实例同时补偿；单实例挂了消息表记录还在（status=待确认），恢复后继续扫。**极限兜底**：消息表 + 死信都挂 = 业务库还在，靠 DB 与下游对账修复。

**Q6 那如果 MQ 集群整个没了呢？**
→ 接受"MQ 不可用"为降级场景：核心链路降级为同步调用 + 网关限流（写好的预案），恢复后**靠消息表重放**补发——这又回到"消息表是 DB 里的数据，天然可恢复"。

**面试官心里话**：这条链考的不是八股，是"你的可靠性方案在每一层失效时是否都想清楚了"。

## 链 2：幂等（从"防重复下单"开始）

**Q1 下单接口怎么防重复下单？**
→ 三层：前端按钮置灰（体验层）→ 网关/内容指纹去重（SET NX EX，入口层）→ DB 唯一索引（兜底层，如 uk_user_sku 一人一单）。

**Q2 Redis 去重的键怎么设计的？**
→ 业务语义键（`post-submitted-{postId}`），**不用随机 UUID**——踩过的坑：内存发号器重启归零，订单号撞上 24h 内旧键被误杀（静默丢数据）。教训：幂等键必须全局唯一业务 ID + 跳过路径打日志。

**Q3 🔺 幂等跳过和业务失败怎么区分？**
→ 跳过 = 正常 ack（业务上"已处理过"）；业务失败 = nack 重试 → 死信。**危险边界**：失败路径中"状态机短路 return"会绕过幂等键清理（踩坑实录坑九）→ 残留键把后续重试也误杀。修复：人工重提前显式清键 + 防线交互矩阵检查。

**Q4 Redis 和 DB 两层会互相干扰吗？**
→ 会（坑九），所以两层各自独立：Redis 挡第一波，DB 唯一索引最终兜底；Redis 键被误清只是"多查一次 DB"，不会错。顺序：先 Redis 后 DB（快），失败时两层都回滚（fail 与 rollback 对齐）。

## 链 3：秒杀（从"秒杀怎么设计的"开始）

**Q1 整体架构？**
→ 四层漏斗：前端（置灰/验证码）→ 网关（Sentinel QPS 限流）→ Redis Lua 原子预扣（判断+扣减+一人一单，打包原子）→ MQ 削峰匀速落库 → DB `WHERE stock>0` 兜底。接口立即返回"排队中"，前端轮询结果。

**Q2 🔺 为什么 Lua？不用会怎样？**
→ "查库存→判断→扣减"三步在并发下交错 → 超卖。Lua 把三步打包成服务端原子执行（等价服务端互斥）。不用 Lua 的替代：DECR 后判负回补（失败请求双倍写）。

**Q3 Redis 和 DB 的库存不一致了怎么办？**
→ 双保险哲学：Redis 挡效率（99%），DB `WHERE stock>=count` 兜正确性（affectedRows=0 = 漂移 → 归还 Redis + 记录差异）。**事后**：活动结束对账 job（Redis 扣减数 == DB 订单数 == DB 扣减数），差异自动补偿。

**Q4 消费者把 DB 打挂了怎么办？**
→ 消费限速保护下游（concurrency×速率匹配 DB 能力，stage3/04）；失败归还 Redis 预扣（防库存虚减）；死信人工兜底。**踩过的坑**：消费速率必须匹配下游，"能消费多快就多快"会把下游打挂造成二次事故。

**Q5 🔺 一人一单怎么实现的？lua 里做了什么？**
→ Lua 里 `SISMEMBER users:{sku} userId` 判断 + `SADD` 登记——判断和登记在同一个原子脚本里，无竞态窗口。DB 层 (user_id, sku_id, seckill_flag) 唯一索引兜底（Redis 集合丢失时仍拦截）。

## 链 4：缓存一致性（从"缓存怎么和 DB 保持一致"开始）

**Q1 用的什么模式？**
→ Cache Aside：读-未命中回写（带 TTL）；写-先更新 DB 再**删除**缓存（删除幂等，避免并发更新覆盖）。

**Q2 为什么是删除不是更新缓存？**
→ 更新有并发覆盖问题（A 后写覆盖 B 先写）且可能算的值很贵；删除后下次读自然重建。配合 TTL 保底。

**Q3 删除失败怎么办？**
→ 延迟双删（写后 500ms 再删一次，MQ 延迟消息驱动）；复杂系统 binlog（Canal）→ MQ → 删缓存（业务零侵入）。都失效的窗口极小且会被 TTL 兜底。

**Q4 🔺 先更新 DB 再删缓存——为什么不是反过来？**
→ 反推：先删缓存 → 并发读未命中查到**旧 DB 值**回写缓存 → 旧值长期停留（比方案 3 窗口大得多）。先更 DB 后删缓存的残留窗口需要"读在写前查库、写在读后删"这种苛刻交错，概率极小。

**Q5 强一致怎么办？**
→ 不用缓存（读 DB）。缓存天生服务"容忍毫秒级陈旧"的场景——**选型时想清楚业务要的是快还是准**。

## 链 5：分布式锁（从"分布式锁怎么实现"开始）

**Q1 实现？**
→ `SET key requestId NX EX 10` 原子抢锁（一条命令，避免 setnx+expire 非原子死锁）；释放 Lua 校验 requestId（防 A 超时后误删 B 的锁）；看门狗续期（Redisson）。

**Q2 🔺 主从切换锁丢了怎么办？**
→ 异步复制：主挂切换后新主可能没有锁 → 双持锁。RedLock 争议大（时钟安全）。**务实分层**：Redis 锁=效率层（防重复干活），正确性靠 DB 兜底（唯一索引/乐观锁 `WHERE stock>0`）——锁丢了最多重复执行，DB 约束保证不出错。

**Q3 超时了业务还没执行完？**
→ 看门狗（Redisson 默认 30s 每 10s 续）。自己写：后台线程校验 requestId 后 expire 续期（Lua）。

**Q4 生产用 Redisson 还是手写？**
→ Redisson（watchdog/可重入/tryLock 全内置）。手写版用于教学理解原理（三要点：NX EX 原子/requestId 校验/续期）。

## 链 6：JVM GC（从"你们 JVM 用什么收集器"开始）

**Q1 用 G1，为什么？**
→ Region 化堆（2048 块逻辑分代）+ 停顿目标模型（MaxGCPauseMillis，按收益挑 Region）+ 无碎片（复制/整理）。对比 CMS：碎片+并发失败退化 Full GC。

**Q2 停顿目标设多少合适？**
→ 默认 200ms。设太小 → 每次只收少量 Region → GC 更频繁、吞吐下降；太大 → 停顿变长。**压测找到业务可接受的平衡**。

**Q3 🔺 频繁 Full GC 怎么排查？**
→ 先看日志区分： promotion 失败（Old 不够/Survivor 溢出）→ 对象晋升太快（大对象/缓存无界）；Metaspace 涨（动态类）。jmap dump → MAT 看支配树。修复在代码不在参数（无界缓存/ThreadLocal）。

**Q4 大内存应用（16G+）追求低停顿呢？**
→ ZGC（着色指针并发转移，亚毫秒停顿与堆大小无关，吞吐 ~10% 代价）。JDK 15+ 生产可用。

## 链 7：线程池（从"线程池参数怎么配"开始）

**Q1 参数怎么设？**
→ 公式只是初值（CPU 密集 N+1 / IO 密集 N×(1+W/C)），**压测确定**。队列容量 = 峰值 QPS × 可容忍延迟。

**Q2 🔺 队列满了怎么办？你们用的什么拒绝策略？**
→ 自定义：日志 + 落库/MQ + 告警（不用 Discard 静默丢）。CallerRuns 用于可接受回压的场景。**主动讲坑**：Executors 快捷方法（无界队列 OOM / CachedThreadPool 万线程 OOM）。

**Q3 任务执行到一半应用重启，任务丢了怎么办？**
→ 重要任务**不进内存队列**——走 MQ（持久化）。线程池只放"可丢"任务。**判据**：任务丢了有后果吗？有后果 → MQ；无后果 → 线程池。这正是 mq-mall/community 的分工。

**Q4 虚拟线程要不要换？**
→ IO 密集换（一行配置，并发不再受池限制）；CPU 密集无益；JDK21 注意 synchronized pinning；**瓶颈会转移到 DB 连接池**——限流意识不变。

## 链 8：MySQL 事务与锁（从"事务隔离级别"开始）

**Q1 RR 怎么实现的？**
→ MVCC 三件套：隐藏列 + undo 版本链 + ReadView。RC 每次读新 ReadView（能看到新提交）、RR 复用首次的（可重复读）。当前读靠临键锁防幻读插入。

**Q2 🔺 RR 下幻读完全解决了吗？**
→ 部分解决：快照读靠 MVCC ✓、当前读靠临键锁 ✓；**先快照后当前读混用会出现幻读**（快照里没有的新行被当前读看见）。

**3 为什么 `WHERE` 条件不走索引会锁全表？**
→ 行锁锁的是**索引记录**——无索引可用时退化为锁全表记录+间隙。教训：更新条件必须走索引（锁层面+性能层面双重理由）。

**4 死锁怎么排查？**
→ `SHOW ENGINE INNODB STATUS` 的 LATEST DEADLOCK 段（双方持锁与等待链）；8.0 查 data_lock_waits。预防：短事务、固定顺序加锁、防重用唯一索引。

## 链 9：Spring 事务（从"@Transactional 失效场景"开始）

**Q1 八连背一下。**
→ ①自调用（没走代理）②非 public ③异常被 catch 吞 ④受检异常默认不回滚（rollbackFor）⑤事务内多线程（ThreadLocal 连接隔离）⑥传播误用 ⑦MyISAM ⑧类不受管理/注解在接口。

**Q2 🔺 自调用为什么失效？怎么修？**
→ 事务=AOP 代理拦截；this 调用走原始对象绕过代理。修复：拆独立 bean（mq-mall SeckillOrderTxWorker）、@Lazy 注入自己、getBean。**根因一句话**：事务=代理=ThreadLocal 连接绑定，绕过代理=绕过一切。

**Q3 🔺 事务里发 MQ，怎么保证事务提交后才发？**
→ `TransactionSynchronizationManager.registerSynchronization(afterCommit)`（mq-mall 的 sendInTransaction 实现）；更优雅：`@TransactionalEventListener(phase=AFTER_COMMIT)`。**否则**：事务回滚了消息却发出去了（下游消费了不存在的事务）。

**Q4 事务内多线程为什么失效？**
→ 事务绑定 ThreadLocal 连接；子线程新连接独立提交。修复：子任务各自小事务（独立提交）或改 MQ 异步化。

## 链 10：虚拟线程（从"虚拟线程了解吗"开始）

**Q1 原理？**
→ JVM 用户态线程：阻塞时 unmount 让出载体线程（=核数个平台线程），恢复时 mount。KB 级栈、百万级并发。写同步代码得异步性能。

**Q2 🔺 pinning 是什么？**
→ JDK21：synchronized 块内阻塞无法 unmount → 钉死载体线程。排查 `-Djdk.tracePinnedThreads=full`；规避：IO 场景改 ReentrantLock。JDK24 JEP 491 解决。

**Q3 会不会把 DB 连接池挤爆？**
→ 会——**瓶颈转移**（虚拟线程百万 → DB 连接几十）。虚拟线程不解决容量问题，只解决"线程贵"问题；容量治理（连接池上限/信号量限流）依然要做。

**Q4 和 WebFlux 怎么选？**
→ 新项目 IO 密集默认虚拟线程（一行配置+普通代码）；存量成熟响应式不迁移；网关/长连接/严格背压场景仍 WebFlux。混用合法。

## 链 11：支付系统（从简历"对接微信/支付宝"开始）

**Q1 支付流程怎么设计的？**
→ 渠道下单 → 跳渠道支付 → **异步回调**你的服务器 → 改订单状态（本地消息表发 order.paid 事件）。先立核心认知：**支付结果的唯一可信来源是异步回调 + 主动查单**，不是用户手机上的"成功"页——用户付完关页面/断网太常见。

**Q2 回调可能重复、乱序、不来，分别怎么防？**
→ 重复：回调流水表渠道流水号**唯一索引** + 状态机 CAS 双层幂等（j-core/15 四关卡②）；乱序：只认状态机 `WHERE status=10`，非法流转直接拒绝；不来（掉单）：定时扫"待支付超 5 分钟"的单**主动查单**补状态——异步主路径 + 定时补偿，与订单超时关单的"延迟消息 + 扫表"完全同构（mq stage4/02）。

**Q3 🔺 支付回调和超时关单同时到，怎么保证不出资损？**
→ **CAS 状态机**：`UPDATE SET status=20 WHERE order_no=? AND status=10`——行锁保证只有一个赢。支付赢：关单方 CAS 落空、什么都不做；关单赢：支付回调 CAS 不中 → 查状态确认已关闭 → **自动退款**。❌ 先查再改两边都查到"待支付"→ 又发货又放库存 = 双重资损。配套动画：[payment-state-machine.html](../diagrams/payment-state-machine.html)（mq-mall `OrderService.pay()` 是真实实现）。

**Q4 🔺 金额怎么处理？回调金额不一致怎么办？**
→ 三条铁律：①单位一律**分（long）**，禁 double（0.1+0.2≠0.3，钱上不允许浮点）；②回调金额与本地订单金额**比对一致**才处理——防"1 分钱下单回调改 100 元订单"；③**验签**（渠道签名校验）防伪造回调——对账里"平台有渠道无"多半是验签没做。

**Q5 查单补偿任务也挂了呢？**
→ 兜底链条再退一步：T+1 对账——平台支付流水 vs 渠道账单文件 vs 订单状态三方核对：渠道有平台无→补单；平台有渠道无→告警人工（严重，可能伪造）；状态没跟上→补状态。差错进"差错池"，能自动修的自动修（mq-mall reconcile 的生产版）。**心法**：可靠性不是保证单点不挂，是"任何一层漏了，下一层能兜住"。

**Q6 ⚠ 微信+支付宝多渠道怎么扩展？**
→ 渠道适配层 = **策略模式**（j-core/06 实际用途）：PaymentChannel 接口定义下单/查单/退款/对账下载，微信/支付宝各自实现，路由层按配置选渠道——新增渠道主流程零改动。

**面试官心里话**：这条链考的是"钱的链路你敢不敢负责"——CAS、幂等、验签、对账一个都不能含糊，答得含糊 = 上线资损。

## 链 12：接口设计（从简历"负责 XX 模块全部接口"开始）

**Q1 你设计接口有什么规范？**
→ URI 名词复数+层级从属（`/posts/{id}/comments`），非 CRUD 动作用"子资源+动词"（`/orders/{no}/pay`）；状态码保语义 + 业务层套 `{code,msg,data}` 统一响应体（j-core/16，community 的 `ApiResponse` 真实锚点）。**反例信手拈来**：`GET /api/getPosts?id=1`（URI 写动词）、`POST /api/posts/delete`（POST 干 DELETE 的活）。

**Q2 🔺 POST 不幂等，用户双击/网络重试怎么防重复下单？**
→ 三层：前端按钮置灰+防抖（体验层）→ 入口防重（`SET NX EX` 内容指纹，几秒内同参数只放一行）→ DB 唯一索引兜底（`(user_id, sku_id)` 一人一单，撞索引即返回已有订单）。**点破本质**：HTTP 层救不了 POST，幂等必须业务自建——支付回调用"渠道流水号唯一索引+状态机 CAS"是同一题的资金级版本（链 11 Q2）。

**Q3 错误码怎么设计？前端怎么区分"该弹窗"和"该跳登录"？**
→ 按模块分段防冲突：`1xxx 用户 / 2xxx 帖子 / 4xxx 支付`，段内细分；语义分层：401 跳登录、403 提示无权限、409 弹"重复提交"、业务 code 前端按映射表处理。❌ 全靠 500+message 字符串（前端没法编程式处理）。配合 BizException+`@RestControllerAdvice`，Controller 零 try-catch（j-core/00 异常篇）。

**Q4 ⚠ 接口怎么演进不破坏老客户端？**
→ 只加字段不删字段不改语义（向后兼容第一原则）；破坏性变更走版本：URI `/v2/` 或 Header 协商；下线走"标记废弃→监控老版本流量→流量归零再摘"。灰度发布配可观测（[17 日志篇](17-日志规范.md) traceId + 监控错误率）。

**Q5 接口安全做了什么？**
→ 鉴权（JWT/Session，网关统一校验）→ 授权（数据越权检查：A 的订单 ID 直接传给 B？先查归属）→ 防重放（timestamp+nonce+签名）→ 限流（[12 篇限流器](12-系统设计三题.md)，429 语义）→ 敏感字段脱敏返回（手机号 `138****8000`，与日志脱敏同规）。

**面试官心里话**：接口设计考的不是"背 REST"，是**并发意识（幂等）+ 演进意识（兼容）+ 安全意识（越权）**——三个意识都在，说明真上线维护过接口。

## 链 13：登录态与安全（从"你们的登录怎么做的"开始）

**Q1 为什么用 Redis 存 token 而不是 Session/JWT？**
→ Session 内存态：多实例要粘性会话/复制，移动端 Cookie 受限；JWT 无状态：签发后到期前收不回，踢人/改密后旧 token 仍有效。Redis Token 三优点：多实例天然共享、DEL 即刻踢人、TTL 管过期——单体到多实例零改造。升级路线明确：微服务化后换 JWT 短过期+网关统一验签（j-core/19）。

**Q2 🔺 JWT 到底解决了什么问题？它登出怎么办？**
→ 解决的是"服务端零查询"——验签即信，网关/下游都不用查存储。代价是可撤销性：黑名单（Redis 存到过期，退化回有状态）/ 短过期+refresh token（窗口压到 15 分钟）/ 用户级 tokenVersion（改密+1）。**点破本质**：无状态 vs 可撤销是根本矛盾，选型是选矛盾侧重。

**Q3 JWT 放什么信息？明文吗？**
→ Base64 只是编码不是加密——Payload 明文可读，只放 sub/角色/过期时间；签名防篡改不防读。密钥泄露=全线失守，生产 RS256 私钥签公钥验。**反例**：把手机号塞 Payload（日志脱敏白做了，j-core/17）。

**Q4 ⚠ 怎么防水平越权？**
→ 信任的只有登录态里的 userId——URL/Body 的任何 ID 都必须查归属：SQL 直接 `where user_id=?`（最优，一次查询天然隔离）或查出后比对 UserContext。**反例**：`selectById(orderId)` 直接返回——IDOR，改个数字就看别人订单。支付回调同思想：核对商户单号归属+金额（链 11）。

**Q5 密码怎么存的？**
→ BCrypt（每用户随机盐+慢哈希 cost≥10）——GPU 撞库从每秒 40 亿次降到每秒 4 次。❌ MD5（速度太快彩虹表秒破）、❌ 固定盐（全体共享拖库一破全破）。传输 HTTPS，前端预哈希无意义。

**Q6 拦截器校验完，用户信息怎么传给业务层？**
→ ThreadLocal UserContext（j-core/19）：preHandle 解析 token 放入，业务零感知。**⚠ 必须 afterCompletion 清理**——Tomcat 线程复用不清理就串用户（并发篇 07 ThreadLocal 泄漏的同族坑，面试主动提这个是高分点）。

**面试官心里话**：安全题考的是**"信任边界"意识**——什么可以信（登录态）、什么绝不能信（客户端传的 ID/参数）、什么矛盾要权衡（JWT 无状态 vs 可撤销）。有边界意识=碰过真实用户数据。
