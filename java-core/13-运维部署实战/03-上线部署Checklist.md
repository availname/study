# 03 · 上线部署 Checklist：发布流程、回滚与灰度

上线事故大多源于"跳过了检查"。这份 Checklist 来自真实发布事故模式，**每次发布过一遍**。

## 发布流程（标准五段）

```mermaid
flowchart LR
    A["① 发布前检查"] --> B["② 灰度发布<br/>（先 1~2 台或白名单流量）"]
    B --> C["③ 观察期<br/>（错误率/延迟/GC 30 分钟）"]
    C --> D{指标正常?}
    D -- 是 --> E["④ 全量发布"]
    D -- 否 --> F["⑤ 立即回滚<br/>（回滚永远比修复快）"]
    style F fill:#7f1d1d,color:#fecaca
```

## 发布前 Checklist（逐条过）

**代码与配置**
- [ ] CI 绿（编译+测试全过）——[GitHub Actions](../../stage6-新技术专题/05-GitHubActions-CICD.md) 已配
- [ ] 配置变更核对（数据库连接/开关/限流阈值）——**配置是事故高发区**
- [ ] 数据库变更脚本已执行且可回滚（DDL 逆向脚本备好）
- [ ] 涉及的 MQ 拓扑（新队列/交换机）已在环境预创建
- [ ] 新增配置项已加到 Nacos/配置中心（不要打在 jar 里）

**依赖与环境**
- [ ] 下游服务版本兼容性确认（接口变更同步了吗）
- [ ] Redis 大 Key/新缓存键位检查
- [ ] 磁盘水位检查（日志空间/堆 dump 空间）

**预案**
- [ ] 回滚脚本/镜像就绪（**回滚永远比修复快**）
- [ ] 降级开关就绪（新功能挂了能一键关闭）
- [ ] 监控大盘已含新指标

## 发布中：观察什么（30 分钟黄金观察期）

| 指标 | 阈值信号 |
|------|---------|
| 错误率 | 比发布前上涨 → 立即回滚 |
| P99 延迟 | 显著上涨（如 2 倍）→ 警惕 |
| GC 行为 | Full GC 出现 → dump + 回滚评估 |
| 业务指标 | 订单量/支付成功率断崖 → 立即回滚 |

## 回滚（Rollback）纪律

1. **回滚永远比修复快**——线上先止血（回滚），修复发布到测试环境慢慢来
2. **数据库变更与代码发布解耦**：加字段向后兼容（先加列发布代码，再删老代码）；**禁止发布时同时改表结构+改代码**
3. 回滚后复盘：Root Cause 写进踩坑实录（本工作区的 12 坑就是这么攒的）

## 灰度发布（金丝雀）

```
全量发布风险大 → 灰度：先放 1~5% 流量到新版本
  → 观察无异常 → 逐步放大（10% → 50% → 100%）
实现：网关按权重路由 / K8s Deployment 滚动更新 + 就绪探针
```

**数据库变更的灰度**：加列（向后兼容）→ 双写 → 切读 → 删旧列——**四步发布法**，每步独立可回滚。

## 监控告警（发布后的眼睛）

> 完整展开：[04-监控告警与Metrics](04-监控告警与Metrics.md)——Prometheus 链路/黄金指标/告警纪律。

| 指标 | 工具 |
|------|------|
| 系统层 | CPU/内存/磁盘/GC（Prometheus + Grafana） |
| 应用层 | QPS/错误率/延迟分位（Micrometer + actuator） |
| 中间件 | MQ 堆积/Redis 命中率/慢 SQL（各组件 exporter） |
| 业务层 | 订单量/支付成功率（业务大盘——**最重要也最常被忽略**） |

## 发布事故复盘模板（写进踩坑实录的格式）

```
1. 现象：什么时间、什么表现、影响范围
2. 时间线：告警→定位→止血→恢复的每一步时间
3. 根因：为什么（5 Why 追问到流程/机制层，不停在"手滑"）
4. 修复：怎么修的
5. 教训与预防：Checklist 加了什么、监控加了什么
——本工作区踩坑实录的 12 个坑就是这个格式
```

## 面试问法

**Q: 你怎么保证上线不出问题？**
A: 承认不可能绝对不出问题，靠三层降低概率与影响——①发布前：CI 门禁+Checklist（配置/依赖/回滚预案）+ 灰度发布（小流量先行）；②发布中：30 分钟黄金观察期盯错误率/延迟/业务指标，异常立即回滚（回滚预案先备好，回滚永远比修复快）；③发布后：复盘进踩坑实录，监控补新指标。另外 DB 变更与代码解耦（加列兼容四步法），大事务拆小。
