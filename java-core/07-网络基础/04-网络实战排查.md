# 04 · 网络实战排查：长连接、粘包拆包与抓包

把网络知识落到排查现场：三个最高频的问题 + 抓包工具入门。

## 一、粘包与拆包：TCP 字节流的"无边框"问题

TCP 是**字节流**协议，没有"消息"边界——发送方三次 write，接收方可能一次全收到（粘包）、或半次（拆包）：

```
发送方：write("HELLO")  write("WORLD")
接收方可能收到：  "HELLOWORLD"（粘） / "HEL" + "LOWORLD"（拆） / "HELLOW" + "ORLD"
```

> [!IMPORTANT]
> 这不是"bug"，是 TCP 的设计本意——它只保证字节顺序与可靠性，不保证消息边界。**消息边界是应用层协议的责任。**

### 四种常见的边界设计（Netty 内置解码器对应）

| 方案 | 应用层格式 | Netty 解码器 |
|------|-----------|-------------|
| 固定长度 | 每条 100 字节 | FixedLengthFrameDecoder |
| 分隔符 | 文本行 `\n` 结尾 | LineBasedFrameDecoder / DelimiterBasedFrameDecoder |
| **长度字段**（最通用） | `[4字节长度][内容]` | LengthFieldBasedFrameDecoder ★ |
| 协议自带 | HTTP/Redis 协议自带格式 | HTTP 编解码器 / RedisDecoder |

**踩坑实录坑十二的延伸**：你写 `Redis ` 协议客户端（RESP 协议按 `\r\n` 分隔）或自定义 TCP 协议时，粘包是第一课。

## 二、长连接与心跳：连接"假活"问题

长连接（网关/客户端→后端、MQ/Redis 长连接）必须配心跳，否则：

```
1. 中间设备（NAT/防火墙/代理——踩坑实录坑十二的 28.0.0.7）静默回收空闲连接
2. 对端"以为"连接还在 → 发消息 → 写超时/异常
3. 生产表现：连接半天没消息后，第一次发消息必失败
```

解法：**应用层心跳**（如 RabbitMQ 心跳 60s、Dubbo 心跳、Netty IdleStateHandler 空闲检测）：

```java
// Netty 的 IdleStateHandler：60 秒没读/没写就触发事件 → 发心跳/关闭重连
pipeline.addLast(new IdleStateHandler(60, 30, 0));
```

两层心跳（TCP keepalive 是内核级且默认 2 小时，太慢，应用层必须自己发）。

## 三、抓包排查入门：tcpdump 与 Wireshark

当"日志看不出问题"时，抓包是终极手段——**看网络上真实发生了什么**：

```bash
# 抓 8082 端口的 HTTP 流量（-A 以文本显示）
sudo tcpdump -i any port 8082 -A -c 100

# 抓与某主机的交互并存文件（Wireshark 打开分析）
sudo tcpdump -i any host api.github.com -w dump.pcap
```

排查实例复盘（连接踩坑实录）：

- **坑十二**（代理截断 22 端口）：抓包会看到 `RST` 包来自 28.0.0.7 而非 GitHub——一眼定位"中间设备干预"
- **坑十一**（HTTP 400）：抓包看到原始请求行里 GBK 乱码字节——一眼定位"未编码"

## 排查问题分层思维（网络篇收束）

```
应用层：看日志/traceId（stage6/04）      —— 业务问题
HTTP 层：状态码（400/401/429/502/504）   —— 接口问题
TCP 层：连接状态（TIME_WAIT/RST/重传）   —— 连接问题
抓包：看字节流                           —— 终极手段（以上全失效时）
每往下一层，工具更重、信息更原始——从最上层开始查
```

## 与踩坑实录的呼应总结

| 踩过的坑 | 网络篇知识点 |
|---------|-------------|
| 坑十一：中文参数 400 | HTTP 解析与 RFC 3986 合法字符 |

## 面试问法

**Q: TCP 粘包拆包怎么解决？**
A: TCP 是字节流无消息边界，粘包拆包是应用层未定义边界导致。四种方案：固定长度、分隔符（\n）、长度字段+内容（最通用，Netty LengthFieldBasedFrameDecoder）、复用自带边界的协议（HTTP/RESP）。本质是应用层协议设计问题。

**Q: 长连接为什么要心跳？**
A: 中间设备（NAT/防火墙/代理）会静默回收空闲连接且不通知两端，形成"假活"连接——发送时才发现失败。应用层心跳（短于设备空闲超时）保活+快速感知死链，配合重连机制。内核 TCP keepalive 默认 2 小时太久，必须应用层自己实现。
