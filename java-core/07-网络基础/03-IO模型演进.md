# 03 · IO 模型演进：BIO → NIO → epoll → Netty

Redis 教学 stage2/01 讲过 epoll 是它快的第二原因——本篇从 **Java 的视角**把 IO 模型演进补全，并解释 Netty 为什么存在。

## 四种 IO 模型（一条演进线）

### BIO：一个连接一个线程（同步阻塞）

```java
ServerSocket server = new ServerSocket(8080);
while (true) {
    Socket client = server.accept();          // 阻塞等连接
    new Thread(() -> handle(client)).start(); // 每个连接一个线程阻塞读写
}
// 1 万连接 = 1 万线程 ≈ 数 GB 栈内存 + 海量切换 → 系统压垮
```

### NIO：多路复用（同步非阻塞）

```java
Selector selector = Selector.open();                 // 多路复用器
serverChannel.register(selector, OP_ACCEPT);         // 注册关注事件
while (true) {
    selector.select();                               // 阻塞直到有就绪事件（返回数量）
    Iterator<SelectionKey> it = selector.selectedKeys().iterator();
    while (it.hasNext()) { handle((SelectionKey) it.next()); it.remove(); }
}
// 1 个（或少量）线程处理全部连接的就绪事件
```

**关键区别**：BIO 的线程"等数据"（阻塞在 read 上）；NIO 的线程"等事件"（数据到了才处理）——**等待被集中到一个 select() 调用里**。

### 多路复用的内核视角（epoll，呼应 Redis 篇）

```
BIO：read() 系统调用阻塞 → 内核切换 → 数据到了唤醒这一个线程
epoll：epoll_ctl 注册关注 fd → 内核事件表 → epoll_wait 返回就绪列表 → O(1) 事件驱动
       （select/poll 是老版本：每次全量传入+内核线性扫描 O(N)——连接多就慢）
```

Linux 的实现演进 select → poll → **epoll**；macOS 是 kqueue；Windows 是 IOCP。Java NIO 的 Selector 自动适配。

### AIO（异步 IO）：内核把数据读完直接回调你

Java 的 `AsynchronousSocketChannel`——理论上更彻底（连"处理事件"都不用你管），但 Linux 的真异步支持不完善，实际生产极少用，了解即可。

## Java NIO 的三件套

| 组件 | 作用 | 类比 |
|------|------|------|
| **Channel** | 双向数据通道（替代单向 Stream） |水管 |
| **Buffer** | 数据容器（position/limit/capacity 三指针） |水桶 |
| **Selector** | 注册+监听多通道就绪事件 |调度台 |

Buffer 的 flip()（读写模式切换）是 NIO 出名的反人类 API——**这正是 Netty 诞生的原因之一**。

## Netty：把 NIO 用出工业水准的框架

裸 NIO 的问题：API 复杂（Buffer 翻转/事件循环手写）、空轮询 bug、断线重连、拆包粘包全要自己处理。**Netty = 对 NIO 的工业级封装**：

```
Netty 架构 = 事件循环组(EventLoopGroup: boss 接连接 + worker 处理 IO)
           + ChannelPipeline 责任链（入站/出站 handler 依次处理）
           + ByteBuf（修复 Buffer 反人类设计）
           + 内置解码器（LengthFieldBasedFrameDecoder 解决粘包拆包）
           + 心跳/重连/内存池全套
```

**谁在用 Netty**：Dubbo（RPC 通信）、RocketMQ（通信层）、Elasticsearch、gRPC-Java、Spring WebFlux 底层（Reactor Netty）——**Java 高性能网络编程的事实标准**。

## IO 模型与你的知识地图

```
epoll（OS 层）  ← r-stage2/01（Redis 单线程快的原因②）
Java NIO（JDK 层） ← 本篇
Netty（框架层）  ← Dubbo/RocketMQ/gRPC 的地基
WebFlux/Reactor（应用层） ← stage6/08 路线之争的响应式底座
Spring MVC + 虚拟线程（stage6/01） ← 另一条路线
```

**同一个 epoll，四层包装**：OS 提供 → JDK 封装 → Netty 工业化 → 应用框架消费。理解了分层，"Netty 为什么快"="用了 epoll+零拷贝+责任链"。

## 面试问法

**Q: BIO/NIO/AIO 的区别？epoll 好在哪？**
A: BIO 同步阻塞（一连接一线程）；NIO 同步非阻塞+IO 多路复用（Selector 集中监听就绪事件，少量线程服务海量连接）；AIO 异步（内核完成读写后回调，Linux 支持不佳少用）。epoll 相比 select/poll：事件注册进内核红黑树、就绪列表直接返回，O(1) 事件驱动；Redis/Netty/Nginx 都基于它。Netty 是 NIO 的工业封装（解决粘包/空轮询/重连）。
