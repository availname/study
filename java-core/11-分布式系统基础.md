# 11 · 分布式系统基础：CAP、一致性哈希与分布式 ID

分布式理论的三个必考概念——**每个都能在你已学的内容里找到实例**。

## 一、CAP 定理

```
分布式系统三项不可兼得，最多取二：
  C 一致性（所有节点同一时刻看到相同数据）
  A 可用性（每个请求都能得到响应）
  P 分区容错（网络分区时系统仍工作）—— 分布式系统 P 必选（网络必然分区）
→ 实际选择只有 CP 或 AP
```

| 选择 | 含义 | 你学过的实例 |
|------|------|-------------|
| **CP** | 分区时拒绝写入保一致 | **ZooKeeper**（选主期间不可用）、etcd、Redis RedisLock（CP 倾向）|
| **AP** | 分区时继续服务，事后同步 | **Eureka**、Nacos 临时实例（Distro）、Cassandra |
| CA | 单机才有（无 P） | 传统单机数据库 |

**实例对照**（全部来自你的教学）：
- **Redis 主从异步复制** = AP（主挂切换可能丢尾部——并发/缓存篇都提过）
- **ZooKeeper** = CP（选主期间不可用）
- **RabbitMQ 镜像队列** = AP 倾向（异步镜像可丢）vs **Quorum 队列** = CP

> **思考题**：为什么分布式事务这么难？——因为在 P（网络分区）的前提下，C 和 A 不可兼得。你学的本地消息表/事务消息/TCC 全是在 C 和 A 之间找平衡点的工程方案。

## 二、BASE：AP 的工程化实践

```
BA  基本可用（Soft state 软状态 / Eventually consistent 最终一致）
→ 降级时响应变慢/数据延迟但不崩溃；写后短暂不一致但最终收敛
```

**你项目里的 BASE 实例**：本地消息表的最终一致（写后秒级收敛）、Redis 计数削峰后异步刷库（短暂偏差）、community 的 Feed 推送异步扩散（延迟可达）。

## 三、一致性哈希：数据分片的经典算法

**问题**：N 台缓存机器，`hash(key) % N` 路由——**扩缩容一台机器，几乎所有 key 的映射全部改变**（缓存雪崩！）。

**一致性哈希**：把哈希空间组织成环（0~2³²），节点与 key 都映射到环上，key 顺时针找第一个节点：

```
扩容/缩容只影响相邻区间的数据（其余映射不变）——缓存命中率保持 ~N/(N+1)
```

**进一步：虚拟节点**——每个物理节点映射多个虚拟节点（如 150 个），解决节点少时数据倾斜问题。

**你学过的实例**：
- Redis Cluster 的 16384 slot 是同类思想（哈希槽而非环，但目标一致：数据分布 + 平滑扩缩）
- Kafka 分区、Elasticsearch 分片——**所有分片系统都在解决同一问题**

## 四、分布式 ID：全局唯一发号器

**问题**：分库分表/多实例后自增 ID 冲突（mq-mall 坑二：内存计数器重启归零撞幂等键）。

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| **UUID** | 随机 128 位 | 简单无序，作索引有页分裂问题 |
| **雪花 Snowflake** | 64 位 = 时间戳+机器ID+序列号 | 有序、趋势递增；⚠ 时钟回拨/机器ID 分配（mq-mall Ids 的教学版） |
| **Leaf/号段** | DB 一次取一段号段内存分配 | 双 buffer 无阻塞 |
| Redis INCR | 简单但依赖 Redis 可用性 | 中小规模可用 |

**选型**：雪花是主流（mq-mall Ids 教学版即简化雪花）；生产用美团 Leaf/百度 UidGenerator 成熟实现。

## 面试问法

**Q: CAP 定理讲什么？你们项目怎么取舍？**
A: 分布式系统一致性/可用性/分区容错三者最多取二，P 必选故只有 CP/AP。实例：ZK/ZooKeeper 类选 CP（分区时拒绝服务保一致），Eureka/Nacos 临时实例选 AP（继续服务事后收敛）。**实践是 BASE 化**：基本可用+软状态+最终一致——本地消息表、Redis 计数削峰后异步刷库都是 BASE 的工程落地。
