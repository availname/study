# 02 · 事务与 MVCC

MySQL 并发读写的核心机制。学完能回答：四大隔离级别怎么实现的、RR 为什么"部分解决"幻读、RC 和 RR 的本质区别一句话是什么。

## ACID 与实现归属（每个字母谁保证的）

| 特性 | 含义 | 靠什么实现 |
|------|------|-----------|
| **A** 原子性 | 全成或全不成 | **undo log**（回滚日志） |
| **C** 一致性 | 数据从一个合法状态到另一个 | 是**目标**，由 A/I/D 共同保证 + 应用层约束 |
| **I** 隔离性 | 事务互不干扰 | **锁 + MVCC**（本章主角） |
| **D** 持久性 | 提交后断电不丢 | **redo log**（[04 篇](04-日志体系.md)详解） |

## 四大隔离级别与三个问题

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| 读未提交 RU | ❌ 会发生 | ❌ | ❌ |
| 读已提交 RC（Oracle 默认） | ✅ 防住 | ❌ | ❌ |
| **可重复读 RR（InnoDB 默认）** | ✅ | ✅ | ⚠️ **部分防住**（见下） |
| 串行化 | ✅ | ✅ | ✅（性能差到没人用） |

三个名词一句话：
- **脏读**：读到别人**还没提交**的数据（别人可能回滚）
- **不可重复读**：同一事务内两次**读同一行**，值变了（别人 update 并提交了）——针对 **update**
- **幻读**：同一事务内两次**范围查询**，行数变了（别人 insert 了符合条件的新行）——针对 **insert**

## MVCC：不加锁也能隔离（多版本并发控制）

MVCC = 每行数据保留**多个历史版本**，不同事务根据自己的"快照"看到不同的版本——读不加锁，读写不冲突。

### 三个零件

**① 隐藏列**（每行都有）：

```
trx_id      ：最近一次修改该行的事务 ID
roll_pointer：指向 undo log 里的上一个版本 → 串成版本链
```

**② undo log 版本链**（回滚日志串成链）：

```mermaid
flowchart LR
    NEW["最新版本<br/>trx_id=500<br/>余额=100"] --roll_pointer--> V2["trx_id=300<br/>余额=500"] --roll_pointer--> V3["trx_id=100<br/>余额=1000"]
    style NEW fill:#164e63
```

**③ ReadView（读视图）**：事务做快照读时拍的一张"当时活跃事务名单"：

```
m_ids      ：生成 ReadView 时，所有活跃（未提交）事务的 ID 列表
min_trx_id ：活跃列表中最小的
max_trx_id ：下一个将要分配的事务 ID（不是最大的！）
creator_id ：创建这个 ReadView 的事务自己
```

### 可见性判断算法（对版本链从新到旧逐个检查）

对版本链上某个版本（trx_id 记为 X）：

```
① X == creator_id        → 自己改的，可见 ✓
② X < min_trx_id         → 生成快照前已提交，可见 ✓
③ X >= max_trx_id        → 快照后才开启的事务，不可见 ✗（沿版本链找更旧的）
④ min ≤ X < max：
     X 在 m_ids 里（当时还没提交）→ 不可见 ✗，回溯上一版本
     X 不在 m_ids（已提交）       → 可见 ✓
不可见就沿 roll_pointer 找上一个版本，重复判断，直到找到可见版本或到链尾（返回 null）
```

## RC 与 RR 的本质区别：就一句话

| | 生成 ReadView 的时机 |
|--|---------------------|
| **RC** | **每次**执行快照读都生成新的 ReadView |
| **RR** | **只在事务第一次**快照读时生成，之后一直复用 |

**推演一遍就懂了**：事务 A 开启时事务 300 未提交，之后事务 300 提交了余额=500 的修改——

- **RC**：A 第二次读时**重新生成** ReadView → 300 已不在活跃名单 → 看到 500 ✗（不可重复读就是这么来的）
- **RR**：A 复用第一次的 ReadView → 300 仍在活跃名单 → 不可见，沿版本链读回 1000 ✓（可重复读）

**这就是 RC 和 RR 的全部区别**——一句话："ReadView 生成一次还是每次"。

## 快照读 vs 当前读

| | 读的是 | 加锁吗 |
|--|--------|--------|
| **快照读**（普通 SELECT） | MVCC 版本链里的历史版本 | 不加锁 |
| **当前读**（`SELECT ... FOR UPDATE` / UPDATE / DELETE / INSERT） | **最新已提交版本** | 加锁（行锁/间隙锁，下一章） |

**RR 防幻读的真相（部分防住）**：

- 快照读：靠 MVCC 版本链——新插入的行 trx_id 大于快照，看不到 ✓
- 当前读：靠**临键锁**锁住范围，别人插不进来 ✓（下一章）
- ⚠️ **混用会破防**：事务内先快照读、再当前读，会看到别人新插入的行（幻读出现）——这是"RR 部分解决幻读"的准确含义

## 实践提醒

- 长事务是 MVCC 的天敌：RR 下长事务复用老 ReadView，**undo 版本链不能清理**→ 堆积暴涨。监控 `information_schema.innodb_trx`，事务要短
- RC 没有间隙锁（并发更好）+ 语句级 ReadView——很多互联网公司线上用 RC 的原因
- 修改隔离级别：`SET SESSION transaction_isolation = 'READ-COMMITTED'`

## 面试问法

**Q: MVCC 的原理？RC 和 RR 的区别？**
A: MVCC = 隐藏列（trx_id/roll_pointer）+ undo 版本链 + ReadView。读时对版本链从新到旧按规则判断可见性：自己改的可见；trx_id < min 可见；≥ max 不可见；中间的看是否在活跃名单。**RC 每次读生成新 ReadView（能看到新提交），RR 只在首次读生成并复用（保证可重复读）**。RR 幻读部分防住：快照读靠 MVCC、当前读靠临键锁；先快照后当前读的混用仍会出现幻读。长事务会让版本链无法清理，undo 膨胀。
