# 03 · 锁体系：记录锁、间隙锁、临键锁与死锁排查

上一章的"当前读"靠锁防幻读。本章把 InnoDB 的锁展开：锁什么粒度、锁什么范围、以及最可怕的**死锁**怎么排查与预防。

## 锁的全景分类

```
全局锁        FTWRL：全库只读（备份用，生产禁用——用 mysqldump --single-transaction 替代）
表级锁
  ├─ 表锁        lock tables ... read/write（基本不用）
  ├─ 元数据锁 MDL  访问表自动加：增删改查加 MDL读，改表结构加 MDL写
  │                ⚠ 经典事故：长事务持有 MDL读 → DDL 加 MDL写被堵 → 后续所有查询排队！
  └─ 意向锁 IS/IX  表级的"旗子"：加行锁前先在表上插旗，让表锁判断更快
行级锁（InnoDB 独有，只在索引上加！）
  ├─ 记录锁 Record Lock      锁单条索引记录
  ├─ 间隙锁 Gap Lock         锁两条记录之间的"空隙"（防插入）
  └─ 临键锁 Next-Key Lock    记录锁+前面间隙 = (前一条, 本条]  ← RR 默认
```

**两个反直觉的要点**：

1. **行锁锁的是索引记录，不是数据行**——`WHERE` 条件没走索引时，行锁**升级为锁全表所有记录**（效果≈表锁）。这就是"更新条件必须走索引"的锁层面理由。
2. **间隙锁只防插入不防读**：两个事务可以同时持有**同一个间隙**的间隙锁（共用），但谁都不能往间隙里插入——它的唯一使命是防幻读插入。

## RR 下的加锁规则（简化版，足够应对 90% 场景）

对当前读（`SELECT ... FOR UPDATE` / UPDATE / DELETE）在索引上的加锁：

| 查询形态 | 加的锁 |
|---------|--------|
| 唯一索引**等值**命中 | 记录锁（只锁那一行） |
| 唯一索引等值**未命中** | 间隙锁（锁住它应该在的间隙，防插入） |
| 范围查询（> < between） | 临键锁逐个覆盖扫描到的区间 |
| 非唯一索引等值 | 临键锁 + 下一个间隙（多锁一个，防幻读插入） |
| 无索引可用 | **锁全表所有记录+所有间隙**（等于锁表，生产事故源头） |

## 死锁：经典案例与排查

### 案例一：互相等待（最经典）

```
事务A：UPDATE t SET ... WHERE id = 1;      持有 id=1 的记录锁
事务B：UPDATE t SET ... WHERE id = 2;      持有 id=2 的记录锁
事务A：UPDATE t SET ... WHERE id = 2;      等 B 释放 id=2 …
事务B：UPDATE t SET ... WHERE id = 1;      等 A 释放 id=1 …
→ 死锁！InnoDB 检测到后回滚代价小的事务（1213 Deadlock found）
```

### 案例二：间隙锁互斥陷阱（隐蔽版）

```
两个事务同时执行：SELECT ... WHERE id = 15 FOR UPDATE   （15 不存在）
→ 都获得 (10, 20) 的间隙锁（间隙锁可共存！）
事务A：INSERT id=15   → 要拿间隙的插入意向锁，被 B 的间隙锁堵住
事务B：INSERT id=15   → 被 A 堵住
→ 互等死锁（先检测到的回滚）
```

> [!CAUTION]
> "先 SELECT FOR UPDATE 检查存在性再 INSERT"的防重写法，在**值不存在**时恰好制造这种死锁。更稳的防重：直接 INSERT + 唯一索引兜底（DuplicateKeyException 处理），与 [Redis 幂等的两层防线](../01-并发编程/README.md)同一哲学。

### 排查手段

```sql
-- 看最近一次死锁（双方持锁与等待详情）
SHOW ENGINE INNODB STATUS\G      -- LATEST DETECTED DEADLOCK 段

-- 8.0 看当前锁与等待关系
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

-- 当前正在执行的事务（长事务/锁等待源头）
SELECT * FROM information_schema.innodb_trx ORDER BY trx_started;
KILL <trx_mysql_thread_id>;      -- 处理卡死事务
```

### 预防清单

- [ ] 事务尽量短，**一次只锁必要的行**
- [ ] 多行更新按**固定顺序**（如按 id 升序）访问——破坏循环等待
- [ ] 更新条件**必须走索引**（无索引=锁全表）
- [ ] 防重插入用唯一索引，不用 "先查再插"
- [ ] 合理的隔离级别（RC 无间隙锁，死锁概率显著降低，很多公司用 RC）

## 乐观锁 vs 悲观锁（概念辨析，易混）

| | 悲观锁 | 乐观锁 |
|--|--------|--------|
| 思想 | 先占住锁再操作（假设会冲突） | 不加锁，提交时检查冲突 |
| MySQL 实现 | `SELECT ... FOR UPDATE` + UPDATE | `UPDATE ... SET version=version+1 WHERE version=?` |
| 适用 | 冲突激烈（秒杀扣减） | 冲突少（后台编辑、低频更新） |
| 与 Redis 呼应 | 分布式锁（Redisson）= 分布式版悲观锁 | Redis Lua 预扣 = 分布式版乐观检查 |

**呼应已学**：Redis 教学的秒杀"双保险"（Redis Lua 预扣 + DB `WHERE stock>0`）里，DB 层就是**乐观锁思想**——`WHERE stock >= count` 的条件更新，affectedRows=0 即失败。

## 面试问法

**Q: InnoDB 有哪些锁？RR 下 SELECT FOR UPDATE 怎么加锁？**
A: 表级（MDL/意向锁）+ 行级（记录锁/间隙锁/临键锁）。RR 当前读规则：唯一索引等值命中→记录锁；未命中→间隙锁；范围→临键锁覆盖扫描区间；非唯一索引等值→临键锁+下一间隙；**无索引→锁全表**。间隙锁共存但堵插入——"先查后插"的防重写法在值不存在时会死锁。

**Q: 线上死锁怎么排查怎么防？**
A: `SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK（双方持锁与等待链）；8.0 查 data_lock_waits。预防四条：事务短、多行按固定顺序访问、更新条件走索引、防重用唯一索引替代先查后插。InnoDB 自动回滚代价小的事务打破死锁。
