# 01 · 索引：B+ 树、回表与索引失效

> 🎬 **配套交互演示**：[diagrams/bptree.html](../../diagrams/bptree.html)——两棵 B+ 树（二级索引/聚簇索引）并排，点按钮看 SELECT * 的"回表"路径 vs 覆盖索引的一步直达。

为什么"加了索引快 1000 倍"、"加了索引反而更慢"都真实存在——理解 B+ 树就能回答一切。

## 一、为什么偏偏是 B+ 树（排除法理解）

MySQL InnoDB 的索引结构是 **B+ 树**。用排除法理解它为什么赢：

| 候选结构 | 为什么不行 |
|---------|-----------|
| 哈希表 | 等值查询 O(1) 很快，但**不支持范围查询**（`WHERE age > 18` 哈希无序直接废）|
| 二叉搜索树 | 数据有序插入退化成**链表**（O(N)）；即使平衡，每个节点 2 分叉，**树高 = log₂(千万) ≈ 23 层 = 23 次磁盘 IO** |
| 红黑树 | 同样是二叉，树太高，磁盘 IO 次数是致命伤 |
| B 树 | 多叉矮胖了，但**数据存在每个节点**——非叶子节点也占空间，单页放的键更少，树更高；且范围查询要中序回溯 |
| **B+ 树** ✓ | 非叶子节点**只存键不存数据**（单页放更多键 → 3~4 层装千万行）；**叶子节点串成有序双向链表**（范围查询顺着扫） |

**磁盘 IO 是唯一敌人**：InnoDB 页大小 16KB，一次 IO 读一页。B+ 树 3~4 层意味着**千万级数据的查找只要 3~4 次页 IO**（根节点常驻内存，实际 2~3 次）。

## 二、聚簇索引 vs 二级索引：回表的由来

InnoDB 的表本身就是一棵 B+ 树（**聚簇索引**），**叶子节点存整行数据**：

```
聚簇索引（主键树）
  非叶子节点: (主键ID → 指向子节点)
  叶子节点:   [id, name, age, email, ...整行数据]

二级索引（比如给 name 建的索引）
  非叶子节点: (name → 指向子节点)
  叶子节点:   [name, id]        ← 只存"索引列 + 主键ID"
```

**关键推论——回表**：用二级索引查非索引列时，先在二级索引树找到 **id**，再拿 id 去**聚簇索引树再查一次**拿整行：

```sql
SELECT * FROM t_user WHERE name = 'zhangsan';
-- ① name 索引树找到 [zhangsan, id=5]     ← 1 次树查找
-- ② 拿 id=5 回聚簇索引树查整行           ← 又 1 次树查找 = "回表"
```

### 覆盖索引：免回表的性能技巧

查询的列**全部**在二级索引里 → 不用回表：

```sql
SELECT id, name FROM t_user WHERE name = 'zhangsan';
-- name 索引叶子节点里恰好有 [name, id] → 直接返回，Extra 显示 Using index ✓

-- 更狠：联合索引 (name, age) 后
SELECT id, name, age FROM t_user WHERE name = 'zhangsan';   -- 依然覆盖 ✓
```

**设计心法**：高频查询尝试用联合索引做到覆盖——少一次树查找就是实打实的性能。

## 三、最左前缀：联合索引的排序法则

联合索引 `(a, b, c)` 的排序规则：**先按 a 排，a 相同按 b 排，b 相同按 c 排**——像字典先按首字母排。由此推导：

```sql
KEY idx_abc (a, b, c)

WHERE a = 1                    ✓ 用到 (a)
WHERE a = 1 AND b = 2          ✓ 用到 (a, b)
WHERE a = 1 AND b > 2          ✓ 用到 (a, b)——b 范围查询后 c 断（范围内无序）
WHERE a = 1 AND c = 3          ⚠ 只用到 (a)，c 没用（中间断了 b）
WHERE b = 2                    ✗ 完全用不上（没有 a 打头）
WHERE a = 1 AND b = 2 AND c = 3 ✓ 全用到
```

**联合索引设计心法**：把**等值条件列放前面、范围条件列放最后、覆盖查询列跟在后面**。

## 四、索引失效清单（生产事故高发区）

> [!CAUTION]
> 以下任意一条都会让索引失效退化成全表扫描——大表上就是事故。上线前用 `EXPLAIN` 检查（type 列至少到 `ref`，出现 `ALL` = 全表扫描）。

| 场景 | 反例 | 修法 |
|------|------|------|
| 对索引列用函数/运算 | `WHERE YEAR(create_time) = 2026` | `WHERE create_time >= '2026-01-01' AND < '2027-01-01'`（把计算移到常量侧） |
| 隐式类型转换 | `WHERE phone = 13800001111`（phone 是 varchar，数字比字符串） | `WHERE phone = '13800001111'` |
| like 左模糊 | `WHERE name LIKE '%三'` | `LIKE '三%'`（前缀匹配用得上）；真要全文搜索用 ES |
| OR 两侧有非索引列 | `WHERE name='x' OR age=18`（age 无索引） | 拆成 union / 全部加索引 |
| != / not in | `WHERE status != 0`（优化器判断命中行太多，索引进价高于全表） | 业务上改写或接受（优化器有时"故意"不用索引是对的） |
| 优化器放弃索引 | 回表成本 > 全表（如命中 30% 行） | **这是优化器理性选择**——强制走索引用 FORCE INDEX，先想是否真该走 |

## 五、EXPLAIN 三分钟速查

```sql
EXPLAIN SELECT * FROM t_user WHERE name = 'zhangsan';
```

| 列 | 看什么 | 危险信号 |
|----|--------|---------|
| type | 访问类型：const > eq_ref > ref > range > index > **ALL** | ALL=全表扫描 |
| key | 实际用的索引 | NULL = 没用上 |
| rows | 预估扫描行数 | 百万级 = 危险 |
| Extra | `Using index`（覆盖索引✓）/ `Using filesort`（额外排序✗）/ `Using temporary`(临时表✗) | filesort/temporary 要优化 |

## 面试问法

**Q: 为什么 InnoDB 用 B+ 树？**
A: 磁盘 IO 是瓶颈，目标是减少树高。B+ 树非叶子节点只存键（16KB 页放更多键，千万行 3~4 层=3~4 次 IO）；叶子节点有序链表支持范围查询与排序；对比哈希（无范围）、二叉树（太高 IO 多）、B 树（非叶子带数据树更高）。

**Q: 什么是回表和覆盖索引？**
A: 二级索引叶子只存"索引列+主键"，查非索引列需拿主键回聚簇索引再查一次=回表（两次树查找）。查询列全被索引覆盖则免回表（Using index）。设计心法：高频查询建联合索引覆盖，等值列在前范围列在后。
