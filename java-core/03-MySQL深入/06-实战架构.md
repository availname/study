# 06 · 实战架构：读写分离、分库分表与高可用

单机 MySQL 的天花板：**写吞吐 ~5k/s、单表 2000 万行后索引变深、连接数上限**。架构演进的每一步都是为了打穿某个天花板——但每一步都有代价。

## 架构演进路线（从小到大的四步）

```mermaid

    A["单机<br/>QPS低/数据少"] --> B["主从+读写分离<br/>读扩展"]
    B --> C["缓存前置<br/>挡读(你的Redis教学)"]
    C --> D["分库分表<br/>写扩展+容量扩展"]
    D --> E["高可用+新SQL<br/>按需"]
    style A fill:#334155
    style B fill:#164e63
    style C fill:#14532d
    style D fill:#78350f
```

**演进顺序不可乱**：缓存（Redis 挡读）→ 读写分离（分散剩余读）→ 分库分表（最后才是写与容量）——**80% 的系统走到第三步就够了**，分库分表是"最后的大招"。

## 一、读写分离

```
写 → 主库 ──binlog──→ 从库1 / 从库2 ──→ 全部读请求走从库
```

### 主从延迟：读写分离的唯一大坑

从库回放 binlog 是单线程/有延迟的（大事务/大 DDL 会放大）。**写完立刻读**会读到旧值：

| 解法 | 做法 | 代价 |
|------|------|------|
| 关键读走主库 | 支付后查订单等强一致场景指定读主 | 主库压力回升 |
| 会话内粘性 | 写后 N 秒内该用户读主（网关/中间件标记） | 实现成本 |
| 等位点 | 写后记录 binlog 位点，读前 `SELECT MASTER_POS_WAIT()` 等追平 | 延迟敏感 |
| 业务设计规避 | "提交后跳转列表页"改为跳转详情页（详情从主读） | — |

ShardingSphere/MyCat 等中间件内置了读写分离+粘性方案。

## 二、分库分表

### 什么时候分（三条线，到了再分）

- 单表行数：**2000 万**级（B+ 树层高从 3 变 4，性能拐点）
- 单库写 QPS：持续逼近实例上限（~5k）
- 单实例磁盘/连接数告急

**别过早分**：分库分表引入的问题比它解决的问题多（见下"代价"）。

### 垂直 vs 水平

| | 拆法 | 例子 |
|--|------|------|
| **垂直分库** | 按业务域拆库：订单库/商品库/用户库 | 微服务化的配套（每个服务自己的库） |
| **垂直分表** | 宽表拆冷热：高频小字段一张表，大字段/低频字段另一张 | 商品表拆出详情大字段 |
| **水平分表/库** | 同结构数据按**分片键**拆到多表/多库 | 订单按 user_id hash 分 8 库 64 表 |

### 分片键选择（最重要决策）

| 分片键 | 好处 | 代价 |
|--------|------|------|
| **user_id**（按用户） | 一个用户的数据永远在一个分片 → 用户查自己的订单单分片搞定；买家维度查询完美 | 卖家维度查询要广播/冗余（订单表冗余 seller_id 分片） |
| **order_id**（按订单） | 订单号直查单分片 | 用户"查我的订单"要广播所有分片 |

**真实做法（冗余两份或更多）**：买家维度一张表（user_id 分片）+ 卖家维度一张表（seller_id 分片）+ 订单号一张表（order_id 分片）——**用空间换查询维度**，写入时三份同写（又是"冗余换性能"，与商品购物车存 ID 的思想同源）。

### 分库分表引入的四大问题（知道代价才算懂）

| 问题 | 解法 |
|------|------|
| **分布式 ID**（自增主键跨库冲突） | 雪花算法/Leaf/号段模式（你 mq-mall 里的 Ids.nextId 就是雏形） |
| **跨分片查询/聚合** | 广播+归并（中间件做）、冗余表、或走 ES/数仓 |
| **跨分片事务** | 优先避免（同分片事务）；必须跨 → Seata/MQ 最终一致（mq 教学 stage4/03） |
| **扩容数据迁移** | 双写迁移方案：新旧库双写 → 存量迁移 → 对账 → 切读 → 停旧 |

**中间件选型**：ShardingSphere-JDBC（应用内嵌入，无中间件瓶颈，Java 主流）/ MyCat（代理层，维护活跃度低）/ 云厂商分布式数据库（TiDB/OceanBase/PolarDB——兼容 MySQL 协议，免分库分表心智）。

## 三、高可用选型

| 方案 | 原理 | 适用 |
|------|------|------|
| 主从 + MHA/Orchestrator | 故障自动提从为主 | 传统方案 |
| **MGR / InnoDB Cluster** | 组复制（Paxos 变体），多数派提交 | 官方系，强一致 |
| **云 RDS/PolarDB** | 托管高可用+自动备份+只读实例 | **大多数公司的现实选择**（运维外包） |
| TiDB | 分布式 NewSQL（天然分片+强一致） | 超大容量想免分库分表 |

> [!TIP]
> 现实选型趋势：**能用云托管就别自建**——高可用、备份、监控、故障切换全部托管，工程师专注业务；分库分表之前先评估"分布式数据库"这条路。

## 面试问法

**Q: 什么时候分库分表？分片键怎么选？**
A: 三条线：单表 2000 万行、单库写 QPS 到顶、磁盘/连接告急——到了再分（先缓存后读写分离）。分片键决定查询能力分布：按 user_id 则用户维度单分片、卖家维度需冗余一份按 seller_id 分片的表；order_id 分片支持订单号直查。代价要背：分布式 ID（雪花/Leaf）、跨分片聚合（冗余/ES/数仓）、跨分片事务（避免/Seata/MQ 最终一致）、扩容双写迁移。

**Q: 读写分离的主从延迟怎么处理？**
A: 四选——关键路径强制读主；会话粘性（写后 N 秒读主）；`SELECT MASTER_POS_WAIT()` 等位点追平再读；业务设计规避（写后跳主读页面）。中间件（ShardingSphere）内置粘性与等位点方案。
