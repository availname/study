# 16 · 接口设计规范：写出面试官一看就"对"的 API

面试官看你简历项目的第一眼往往不是架构图，是 Controller。**接口设计是"没系统学过但天天在写"的典型**——本篇把 community/learn-center 里已经"写对了一半"的接口补全成体系。

## 一、URI：名词说资源，动词交给 HTTP

```
✅ GET    /api/posts            帖子列表
✅ POST   /api/posts            发帖
✅ GET    /api/posts/{id}       单帖详情（community PostController 真实写法）
✅ POST   /api/posts/{id}/like  点赞（like 是这个资源的"动作子资源"，非 CRUD 动词，允许）
✅ DELETE /api/posts/{id}/like  取消点赞（community 真实写法——对称美）
❌ GET    /api/getPosts?id=1    URI 里写动词 + 驼峰
❌ POST   /api/posts/delete     POST 干 DELETE 的活
❌ GET    /api/deletePost?id=1  双重作死
```

**三条命名铁律**：①资源名词复数（posts 不用 post/getPostList）；②层级表从属（`/posts/{id}/comments`——评论属于帖子）；③**非 CRUD 的动作用"子资源+动词"**：`/posts/{id}/like`、`/orders/{no}/pay`、`/orders/{no}/cancel`——这是"RPC 味"最少的动作表达法（你的 mq-mall 支付接口就是这么对的）。

## 二、动词与幂等（直接连支付回调那篇）

| 动词 | 语义 | **幂等？** | 对应 SQL |
|------|------|-----------|---------|
| GET | 读取 | ✅ | SELECT |
| POST | 创建 | ❌ | INSERT |
| PUT | 全量替换 | ✅ | UPDATE 整行 |
| PATCH | 部分更新 | ❌（一般） | UPDATE 部分列 |
| DELETE | 删除 | ✅ | DELETE/逻辑删 |

**幂等性表是面试高频**（"PUT 为什么幂等？"——重复执行结果不变，PATCH 第二次可能基于不同原值再变一次）。**设计启示**：超时重试只敢发生在幂等动词上——[OpenFeign 篇 03](05-微服务全家桶/03-OpenFeign.md) "写接口禁自动重试"的原因就在这；支付回调用"POST+幂等键"是因为渠道协议定的 POST，所以**幂等要自己建**（[15 篇](15-系统设计·支付系统.md)的两层防线）。

## 三、状态码：07 篇十个码的"接口视角"复查

```
200 GET/PUT 成功          201 POST 创建成功        204 DELETE 成功（无返回体）
400 参数错误              401 未登录                403 无权限（已登录但越权）
404 资源不存在            409 冲突（重复提交）       429 限流（[12 篇限流器](12-系统设计三题.md)的拒绝策略）
500 服务器异常（你不该主动返回它）
```

**实践中的一道选择题**：统一 200 + 响应体 code（国内主流，前端好统一拦截）vs 严格 HTTP 状态码（网关/监控按状态码统计错误率才准）。**折中主流解**：传输层保持语义（4xx/5xx 该用就用），业务层再套 `{code, msg, data}`——community 的 `ApiResponse(code, msg, data)` 就是这个模式，0=成功、非 0=业务错误码。

## 四、统一响应体与错误码分段

```java
// community 的真实基座（record 一行搞定——新特性篇 10 的 Record 实战）
public record ApiResponse<T>(int code, String msg, T data) {
    public static <T> ApiResponse<T> ok(T data) { return new ApiResponse<>(0, "ok", data); }
}
```

**错误码分段（追问必到）**：按模块分段防止冲突——`1xxx 用户` `2xxx 帖子` `3xxx 积分` `4xxx 支付`；段内再细分（4001=重复点赞）。❌ 全用 500 字符串 message 区分（前端没法编程式处理）；❌ 每处随手写错误码。配合 [04 异常篇](00-Java语言基石/04-异常体系与最佳实践.md)的 BizException + 全局异常处理器，Controller 里零 try-catch。

## 五、列表接口三件套：分页/排序/过滤

```
GET /api/posts?page=1&size=20&sort=created,desc&status=published
→ 响应带总数：{ data: { list: [...], total: 837, page: 1, size: 20 } }
```

- ❌ 不给分页的列表接口（上线三个月数据 10w 行，前端全量拉取打爆带宽）；❌ `pageSize=99999` 无上限（**恶意一次拉全表**——限流 12 篇的另一种"资源保护"）
- 深分页问题：`page=10000` 的 `LIMIT 200000,20` 越翻越慢——游标分页（`?after=最后一条id`，看最后 id 继续往后）是 Feed 流/评论区标准解（stage5/03 拉取同思想）
- learn-center/community 都用 MyBatis-Plus 分页插件——`Page<T>` 就是这套参数的现成实现（[09 篇](09-测试与MyBatis/02-MyBatis快速上手.md)）

## 六、其余四条纪律（速查）

| 纪律 | 要点 |
|------|------|
| **版本化** | URI 前缀 `/api/v1/`——破坏性变更升 v2，不逼所有客户端同步改 |
| **鉴权** | `Authorization: Bearer <token>` 头，❌ token 放 query string（会进网关日志/浏览器历史）；community 的 token 校验上移网关（[微服务 04](05-微服务全家桶/04-Gateway网关.md)） |
| **不泄漏内部** | ❌ 响应里吐 SQL 堆栈/表名/手机号明文——[08 篇](../stage7-AI应用开发/08-AI安全与评测.md)数据合规的同源意识 |
| **一致性 > 完美** | 团队内统一一种风格比"绝对 RESTful"重要——风格漂移的代码库比 RPC 风格更难读 |

## 面试问法

**Q: PUT 和 PATCH 的区别？接口设计注意什么？**
A: PUT 全量替换且幂等（重复执行结果不变），PATCH 部分更新一般不幂等；所以重试机制只敢套在幂等动词上。设计要点：URI 名词复数+层级从属，非 CRUD 动作用子资源表达（/orders/{no}/cancel）；状态码保语义+统一响应体双层（code/msg/data）；错误码按模块分段；列表必分页且设上限，深翻页用游标；token 走 Authorization 头不进 URL。我自己项目的 Controller 就按这套写的（community 的 like/取消 like 对称子资源 + ApiResponse 统一基座）。
