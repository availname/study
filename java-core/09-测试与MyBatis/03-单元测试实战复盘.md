# 03 · 单元测试实战：给两个真实项目补测试的踩坑复盘

[01 篇](01-JUnit5与Mockito单元测试.md)教了 Mockito 语法——这篇是**真写完 28 个用例后的坑账**：learn-center 17 个（AI 出题/抢课消费者/雪花 ID）+ community 11 个（幂等服务/热榜衰减/Write Behind 刷库）。测试代码在两个项目里，随时可跑。

## 一、先想清楚：测什么

❌ 追覆盖率（凑行数）；✅ **锁行为**——每个测试类是一份"行为合同"：

```
EnrollConsumersTest   → "重复消费会幂等跳过；已支付的订单超时取消不回补名额"
MessageDedupServiceTest → "DB 第二道防线冲突时要回滚 Redis 标记（坑九的回归）"
CounterFlushJobTest   → "刷库用 DECR 而不是 DEL——删了就丢刷库间隙的增量"
HeatDecayJobTest      → "热度 0.5×0.98 出榜，走 remove 不走 add"
```

**命名即文档**：用例名写场景（中文长名没关系——`DB唯一键冲突_第二道兜底_并回滚Redis标记`），半年后读测试像读需求。

## 二、五个真实踩过的坑（每坑配解法）

### 坑① MyBatis-Plus 的 LambdaQueryWrapper 在纯单测里抛异常

`new LambdaQueryWrapper<Question>().eq(Question::getTitle, ...)` 不起 Spring 就报 *can not find lambda cache*——**Lambda 列名解析依赖实体元数据**，运行时由 MP 注册，单测没有：

```java
@BeforeAll
static void initTableInfo() {
    TableInfoHelper.initTableInfo(
        new MapperBuilderAssistant(new MybatisConfiguration(), ""), Question.class);
}
```

### 坑② BaseMapper.insert 有两个重载，verify 直接编译错

MP 3.5.7 的 `insert(T)` 与 `insert(Collection<T>)` 并存——`verify(mapper).insert(any())` 报"调用不明确"：

```java
verify(questionMapper, never()).insert(ArgumentMatchers.<Question>any());  // 泛型消歧
```

### 坑③ stub 过的调用也算 interaction，verifyNoInteractions 误伤

HeatDecayJob 的"空榜不动作"用例先 `when(zset.rangeWithScores(...))` 打了桩，再 `verifyNoInteractions(zset)` → 失败（**打桩本身记录为一次交互**）。改语义化验证：

```java
verify(zset, never()).add(anyString(), anyString(), anyDouble());
verify(zset, never()).remove(anyString(), anyString());     // "没有写动作"才是真断言
```

### 坑④ verify 的对象搞错层级：delete 在 template 不在 ValueOperations

`redis.opsForValue()` 返回的 `ValueOperations` **没有 delete 方法**（在 `RedisOperations`/template 上）。先 mock 链头再 verify：

```java
when(redis.opsForValue()).thenReturn(valueOps);   // 链式 mock：先固定 opsForValue 返回同一实例
verify(redis, never()).delete(anyString());       // delete 是 template 的方法
```

### 坑⑤ 连续返回要用 thenReturn 的变参（Consecutive Stubbing）

消费者首次建单要两次 `update`（建单+扣名额），幂等场景返回 0：

```java
when(jdbc.update(anyString(), any(MapSqlParameterSource.class))).thenReturn(1, 0);
//                                            第1次调用→1，第2次→0，之后一直 0
```

## 三、难缠的依赖怎么 mock（本实战的三个模板）

**模板 A：SCAN 游标**（try-with-resources 包着的 Cursor）：

```java
Cursor<String> cursor = mock(Cursor.class);
when(cursor.hasNext()).thenReturn(true, false);   // 第一次 true，之后 false
when(cursor.next()).thenReturn(key);
when(redis.scan(any(ScanOptions.class))).thenReturn(cursor);
```

**模板 B：具体类包 mock**（NamedParameterJdbcTemplate 无接口但有薄封装价值）：

```java
JdbcTemplate template = mock(JdbcTemplate.class);
var jdbc = new NamedParameterJdbcTemplate(template);   // 真实例包 mock 底层——有接口的对象优先直接 mock
```

**模板 C：Map 入参的消费者**（@RabbitListener 方法签 `Map<String,Object>`）：

```java
consumers.onEnrollCreated(Map.of("userId", 9L, "courseId", 5L));   // 直接调方法=模拟消息到达
```

## 四、单测与集成测试的分工（两个项目已经跑通这套）

| | 纯 Mockito 单测 | Testcontainers 集成测试 |
|--|---------------|----------------------|
| 测什么 | 逻辑分支/边界/兜底 | **真 SQL 语义/真 Redis 行为**（SETBIT 旧值、唯一键冲突） |
| 环境 | 任何环境秒跑 | 需 Docker（`disabledWithoutDocker` 无则跳过） |
| 数量占比 | ~70%（金字塔底座） | ~10% 但锁"踩过的坑" |
| 归属 | `XxxTest` | `XxxIntegrationTest` |

**判据一句话**：mock 得掉、且失败能定位到代码分支的 → 单测；必须验证真实中间件语义（SQL 方言、Redis 返回值约定）的 → 集成。**别用单测模拟 Redis 的 SETBIT 语义**——mock 出来的"假 Redis"只会自欺（stage6/07 的原话）。

## 五、把测试写进 README（测试也是交付物）

两个项目的 README 都有"单元测试"节：**用例 ↔ 教学章节映射表**（`AiQuestionGeneratorTest → stage7/02 结构化输出`）+ 踩坑沉淀。写测试的收益复利：半年后改代码，`mvn test` 一键回归"当初为什么这么设计"。

## 面试问法

**Q: 你们项目的测试是怎么做的？**
A: 分工按测试金字塔：~70% 纯 Mockito 单测锁业务行为（幂等跳过、CAS 不回补、刷库不删 key——用例名即需求文档），每个测试类是一份行为合同；~10% Testcontainers 集成测试锁踩过的坑（SETBIT 旧值语义/本地消息表生命周期），disabledWithoutDocker 无 Docker 优雅跳过、CI 真跑。踩过的坑：MP 的 LambdaQueryWrapper 纯单测要先 initTableInfo 注册元数据；stub 本身算 interaction，"不动作"要用 never() 断言；重试路径用 consecutive stubbing（thenReturn(1,0)）。
