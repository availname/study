# 05 · 责任链与状态机：业务编排的两个骨架

前四篇的模式都有"标准教科书形象"——这两位没有：**责任链**藏在所有框架的 Filter/Pipeline 里，**状态机**藏在每个订单系统的 if-else 地狱旁。它们是后端业务代码里出现频率最高的两个骨架（你自己的 community/mq-mall 里都藏着它们的雏形）。

## 一、责任链：流水线上的一道道工序

**场景**：community 发帖要过三关——每日限 5 篇 → 内容 MD5 去重 → 审核队列。mq-mall 下单要过——参数校验 → 风控 → 库存检查。❌ 写成一个 200 行方法层层 if；✅ **每关一个 Handler，串成链，逐个放行**：

```java
interface PostHandler {
    boolean handle(PostRequest req);          // 返回 false = 拦截，链终止
    PostHandler next();
    default boolean proceed(PostRequest req) { // 模板方法：自己过了才叫下一个
        return handle(req) && (next() == null || next().proceed(req));
    }
}

class RateLimitHandler implements PostHandler {     // 关①：每日限 5 篇
    public boolean handle(PostRequest req) {
        return redisLua.allowPost(req.authorId());  // INCR+Lua（stage5/01 防刷同款）
    }
}
// 组装：limitHandler.setNext(dedupHandler); dedupHandler.setNext(auditHandler);
limitHandler.proceed(req);   // 一行发起整条链
```

**设计要点（追问区）**：①顺序敏感（限流要在最前，最便宜的判断先做——**快速失败前置**）；②拦截后要有"谁兜底"的约定（返回拦截原因，不是静默丢弃）；③数组版（`List<Handler>` 顺序遍历，Spring 注入后 `@Order` 排序——**最常用**）vs 链表版（每个 Handler 持有 next，可动态插拔）——面试写数组版更清晰。

## 二、状态机：给"状态的合法流转"立法

**场景**：帖子的一生（community README 画过的）：待审 → 通过/拒绝；订单：待支付 → 已支付/已关闭。❌ 每处修改状态的地方各自 `if (status == 0) ...`——三个月后没人说得清"哪些状态能到已关闭"；✅ **把合法转移收拢成一张表**：

```java
enum PostStatus {
    PENDING, PUBLISHED, REJECTED;

    // 转移表：状态 + 事件 → 新状态；不在表里的转移一律非法
    static final Map<PostStatus, Map<PostEvent, PostStatus>> TRANSITIONS = Map.of(
        PENDING,   Map.of(PostEvent.AUDIT_PASS, PUBLISHED, PostEvent.AUDIT_BLOCK, REJECTED)
    );
    PostStatus on(PostEvent e) {
        PostStatus next = TRANSITIONS.getOrDefault(this, Map.of()).get(e);
        if (next == null) throw new BizException("非法转移: " + this + " + " + e);
        return next;
    }
}
```

**三件配套武器（缺一不可）**：

1. **转移表即文档**——新增"撤回"功能？先在表里加一行，编译期就逼你想清楚影响面
2. **Java 侧守卫 + DB 侧 CAS 双保险**——枚举 `on()` 挡住业务代码写错顺序；[支付篇 15](../15-系统设计·支付系统.md) 的 `UPDATE ... WHERE status=10` 挡住并发双写。**两层管的是不同的敌人**：前者防"逻辑写错"，后者防"并发抢写"
3. **非法转移报错而不是静默**——`REJECTED + AUDIT_PASS` 必须炸出来，静默吞掉就是埋雷（踩坑实录坑二的"静默丢失"同款教训）

**Spring StateMachine 要不要用**？它重（依赖多、概念多），适合状态多（>10）、转移复杂（带守卫/动作/子状态）的场景；**业务系统三五个状态用 enum 转移表就够了**——不用为模式而模式（SOLID 篇的话）。

## 三、两个骨架经常连着用

```
community 帖子的一生：
  发帖请求 → 限流→去重→入审核队列        ← 责任链（每关独立、可插拔）
  待审 → AUDIT_PASS → 已发布            ← 状态机（合法转移收拢）
  审核管道 BLOCK→人工→通过               ← 责任链（stage5/02 同款）
  帖子状态每次变更 → CAS SQL + 事件发 MQ ← 状态机 + 本地消息表（stage3/01）
```

**判别口诀**：**"过五关斩六将"用责任链（要不要继续往下走），" lifecycle 人生阶段"用状态机（我现在是谁、什么事件能让我变成谁）**。写代码前先问：这段编排是"过滤流"还是"角色的一生"？

## 面试问法

**Q: 讲讲责任链模式在框架中的应用？**
A: 链上每个 Handler 处理后决定放行或拦截（Netty pipeline、Gateway 过滤器链、Servlet Filter 链都是）。我在发帖限流场景写过数组版：限流/去重/审核三个 Handler 顺序遍历，便宜且致命的判断前置（快速失败），拦截带原因不静默。相比 200 行 if-else 方法，职责单一可插拔、加一关不动老代码（开闭原则）。

**Q: 订单状态流转怎么设计？**
A: 状态机三层防：①enum 转移表把合法流转收拢成 Map，非法转移抛异常（表即文档）；②改状态的 SQL 带 CAS 条件 `WHERE status=旧值`，防并发双写（支付 vs 关单竞态的解）；③每次成功转移经本地消息表发状态变更事件给下游。状态少用 enum，状态多/转移复杂再考虑 Spring StateMachine。
