# 03 · 行为型：策略、模板方法、观察者

行为型模式关注"对象之间怎么分工协作"。三巨头全部在你学过的源码里出现过。

## 一、策略：同一件事的多种做法可互换

**痛点**：一堆 if-else 处理不同分支，每加一种就改一处（违反开闭原则）。

```java
// ❌ if-else 沼泽：拒绝策略如果这样写……
public void rejected(int mode) {
    if (mode == 1) throw new RejectedExecutionException();
    else if (mode == 2) { /* 提交者执行 */ }
    else if (mode == 3) { /* 静默丢弃 */ }
    else { /* 每加一种这里长一行 */ }
}
```

```java
// ✓ 策略模式：定义接口 → 各实现一个策略类 → 调用方注入策略
public interface RejectedHandler { void handle(Runnable task); }

@Component public class AbortHandler implements RejectedHandler { ... }
@Component public class LogAndStoreHandler implements RejectedHandler { ... }

// 调用方（或 Spring 注入 Map<String, RejectedHandler> 自动收集所有策略）
RejectedHandler handler = strategyMap.get(config.getMode());   // 运行时选择
handler.handle(task);
```

**你学过的策略实例（源码认亲）**：

| 策略接口 | 可互换的"做法" |
|---------|---------------|
| `RejectedExecutionHandler` | 线程池四种拒绝策略（并发篇05） |
| `LoadBalancer`（Spring Cloud） | 轮询/随机负载均衡（微服务03） |
| `KeyResolver`（Gateway 限流） | 按 IP/按用户/按接口限流（微服务04） |
| `MessageConverter` | JDK 序列化/JSON 序列化（stage1/05） |

**与 Redis 呼应**：`maxmemory-policy` 八种淘汰策略就是 Redis 内部的策略模式——C 语言都离不开它。

## 二、模板方法：父类定骨架，子类填血肉

**痛点**：多个类的流程一样、每一步细节不同——流程写在父类，步骤由子类实现。

**你学过的最伟大实例：AQS**（并发篇06）：

```java
// AQS 定死骨架：排队 → 阻塞 → 唤醒 → 再试（不可修改）
public final void acquire(int arg) {
    if (!tryAcquire(arg) &&            // ← 钩子：语义由子类定义！
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg))
        selfInterrupt();
}
protected boolean tryAcquire(int arg) { throw new UnsupportedOperationException(); }  // 留白
```

```
子类填血肉：
  ReentrantLock.tryAcquire  → state 从 0 到 1（可重入则 +1）
  CountDownLatch.tryAcquire → state == 0？
  Semaphore.tryAcquire      → state > 0 则减 1
```

**一个 AQS 骨架衍生出整个 JUC 协作家族**——这就是模板方法的威力。其它实例：

- `JdbcTemplate`：连接/异常/资源释放是模板，SQL 执行是钩子
- Servlet 的 `service()` → `doGet/doPost`：流程定死，方法留白
- Spring 的 `refresh()`：容器启动十三步定死，扩展点留白（BeanPostProcessor 生效处）

**与 Lambda 的关系**：模板方法的"子类填空"在 Java 8 后常用 **Lambda 替代**——`JdbcTemplate.query(sql, rowMapper)` 的 rowMapper 就是函数式钩子；更轻量，不用为每个变体建子类。

## 三、观察者：一对多的广播（你学得最深的一个）

```
被观察者（Subject）状态变化 → 自动通知所有观察者（Observer）
```

**三个层次的观察者，你全部用过**：

| 层次 | 实例 | 出处 |
|------|------|------|
| JDK 内置 | `PropertyChangeListener` / `Observable`（已废弃） | — |
| **Spring 进程内** | `ApplicationEvent` + `@EventListener`（Spring 核心 05） | — |
| **跨进程** | **MQ 的 fanout 广播**（mq-mall 发布事件→三个服务） | mq stage5 |

发布帖子的三层次演进（同一思想的升级）：

```
同步调用（耦合）→ Spring Event（进程内解耦）→ MQ fanout（跨进程解耦）
每升一级：可靠性↑、复杂度↑、边界从"方法"到"进程"——按规模选层
```

**观察者的坑**：①通知顺序不可控 ②同步观察者会阻塞发布者（Spring Event 默认同步！）③跨进程观察者需要消息可靠性（stage3/01）。

## 面试问法

**Q: 策略模式怎么消除 if-else？什么时候不该用？**
A: 定义策略接口 → 每个分支一个实现 → Map/容器收集（Spring 注入 Map<String, Strategy> 自动按 key 聚合）→ 运行时按参数选。JUC 拒绝策略、LoadBalancer、Gateway 的 KeyResolver 都是实例。**不该用时**：分支稳定只有两三个且逻辑极短——if-else 可读性更高，为两个分支建三个类是过度设计。

**Q: 模板方法和策略的区别？**
A: 模板方法 = **继承**（父类定骨架流程，子类填步骤，编译期确定）；策略 = **组合**（整个算法可替换，运行时切换）。JdbcTemplate 用函数式钩子（Lambda）兼得两者——模板定流程、策略化填步骤。
