# 02 · 类加载机制

Java 的"一次编译到处运行"和"动态性"（运行时才确定类）都建立在类加载机制上。核心考点：**五阶段、双亲委派、打破双亲委派的场景**。

## 类的生命周期

```
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
│←──────── 连接（Linking）────────→│
```

| 阶段 | 干什么 | 要点 |
|------|--------|------|
| **加载** | 读 .class 字节流 → 方法区存类元数据 → 堆里生成 Class 对象 | 字节流来源灵活（文件/jar/网络/动态生成——CGLib 就是运行时生成） |
| **验证** | 字节码合法性/安全性检查 | 防止恶意字节码搞崩 JVM |
| **准备** | 静态变量分配内存并设**零值** | `static int a = 1` 此时 a=0（不是1！）；`static final int A=1`（常量）此阶段直接是 1 |
| **解析** | 常量池符号引用 → 直接引用 | |
| **初始化** | 执行 `<clinit>`（静态变量赋值 + static 块） | **由 JVM 加锁保证单线程执行**——静态单例线程安全的原理 |

**经典题：`static int a = 1` 在准备阶段是 0 还是 1？** 准备阶段 0（零值），初始化阶段（`<clinit>`）才赋 1。所以"准备阶段能拿到 1 吗"是陷阱题；而 `static final int A = 1`（编译期常量）准备阶段就是 1。

## 什么时候触发初始化（主动引用六种）

1. new / getstatic / putstatic / invokestatic（四条字节码指令）
2. 反射调用（Class.forName）
3. 初始化子类时父类先初始化
4. main 所在的主类
5. JDK 7 动态语言 MethodHandle 指向的类
6. 接口带默认方法的实现类初始化

**不触发初始化（被动引用）**：通过子类引用父类静态字段（父类才初始化）、定义类数组（`new A[10]`）、引用编译期常量、`A.class`。

## 类加载器与双亲委派

三层加载器：

```
Bootstrap（启动类加载器，C++ 写）：JAVA_HOME/lib 核心类（java.lang.*）
   ↑ 委派
Extension/Platform（扩展）：lib/ext
   ↑ 委派
Application（应用类加载器）：你的 classpath   ← 大多数类由它加载
```

**双亲委派机制**：收到加载请求，**先委派给父加载器**，父加载不了才自己加载。

```
你要加载 java.lang.String → 一路委派到 Bootstrap → Bootstrap 加载了 rt 里的 String
→ 你的同名 String 类永远不会被加载（即使你写了同名的）
```

**为什么要有双亲委派（三个理由）**：
1. **安全**：防止核心 API 被篡改（你自己写个 `java.lang.String` 也上不了位）
2. **避免重复**：父加载器加载过的类，子类不重复加载
3. **层级清晰**：类在整个 JVM 里全靠"加载器+类名"唯一定位

## 打破双亲委派（什么场景需要 + 怎么破）

| 场景 | 为什么破 | 例子 |
|------|---------|------|
| JDBC SPI | 接口在 Bootstrap 的 rt.jar，**实现**（mysql 驱动 jar）在应用 classpath——父加载器看不到子加载器的类 → 用线程上下文类加载器反向委派 | `ServiceLoader` / `Class.forName(驱动类, true, ctxLoader)` |
| 热部署/热更新 | 同一个类要重新加载（卸载类=卸载它的加载器，需要**自定义加载器**） | OSGi、Tomcat 每个应用独立加载器（应用间类隔离+可卸载） |
| 隔离 | 两个应用用不同版本的同一个 jar，类不能混 | Tomcat、中间件容器化加载 |

```java
// 自定义加载器的最小骨架：重写 findClass（保留双亲委派）或 loadClass（打破）
public class MyLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) {
        byte[] bytes = readMyWay(name);      // 从文件/网络/加密字节里读
        return defineClass(name, bytes, 0, bytes.length);
    }
}
```

**Tomcat 为什么打破**：两个 webapp 各有一个不同版本的 `Foo` 类，若走双亲委派则先到的版本通吃，后到的用错版本——所以 WebappClassLoader 先自己找自己应用的类，找不到才委派。

## 与生产问题的连接

| 生产现象 | 类加载视角的原因 |
|---------|----------------|
| `NoSuchMethodError` / `ClassNotFoundException` | **jar 冲突**：classpath 里两个版本的同一个类，加载到了旧版——`mvn dependency:tree` 排查 + exclusions 排除 |
| 反射/代理报类型不匹配 | 同名类被两个加载器各加载了一次（instanceof 永远 false） |
| Metaspace OOM | 动态生成类（CGLib/脚本引擎）没被卸载——卸载类需要卸载它的加载器 |

## 面试问法

**Q: 类加载过程和双亲委派？**
A: 加载(字节流→元数据+Class对象)→验证→准备(静态变量零值，常量直接赋值)→解析→初始化(<clinit>，JVM加锁保证线程安全)。双亲委派：先委派父加载器，父加载不了才自己加载——保证核心类安全（自定义 java.lang.String 加载不了）、避免重复加载、层级定位唯一。打破场景：JDBC SPI 用线程上下文类加载器反向委派；Tomcat 应用隔离与热部署。

**Q: 一个类会被加载两次吗？**
A: 同一加载器下不会（缓存检查）；但不同加载器会各加载一次——同名类在不同加载器下是**两个不同的 Class 对象**（instanceof 不匹配）。这是 jar 冲突报 NoSuchMethodError 和应用隔离的原理。
