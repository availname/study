# 15 · 系统设计专题：支付系统

前两组设计题（[12](12-系统设计三题.md)、[14](14-系统设计进阶三题.md)）的组合题练完了——这篇是**综合度最高的一题**：支付串起了状态机、幂等、异步回调、对账，也是你 mq-mall 订单链路的收口（`OrderService.pay()` 就是本篇核心方案的真实实现）。

> 🎬 **配套动画**：[diagrams/payment-state-machine.html](../diagrams/payment-state-machine.html)——切换 ✅CAS/❌先查再改，跑四个剧本看胜负与分支。

## 需求：对接第三方支付（微信/支付宝）

```
用户下单 → 跳渠道支付 → 渠道异步回调你的服务器 → 改订单状态 → 发"已支付"事件给下游
约束：不丢单（付了没记录）/ 不多收不少收 / 回调可能重复、乱序、不来
```

**先立一个最重要的认知**：支付结果的**唯一可信来源是渠道的异步回调 + 主动查单**，不是用户手机上的"支付成功"页面——用户付完直接关页面、网络断掉都太常见了。

## 核心设计：四个关卡

### ① 状态机 + CAS（mq-mall 真实代码）

```
待支付(10) ──支付──→ 已支付(20)
    └────超时────→ 已关闭(30)
```

```java
// mq-mall OrderService.pay()——CAS 改状态，一次 UPDATE 解决并发竞态
int n = orderDao.casPay(orderNo);            // UPDATE ... SET status=20 WHERE order_no=? AND status=10
if (n == 0) {
    if (current.status() == PAID)  return;   // 重复回调/重复支付 → 幂等忽略
    if (current.status() == CLOSED) throw new BizException("已关闭，走退款");  // 关单赢了
}
```

**为什么 CAS 是关键**：支付回调与超时关单**并发到达**时——两个都要改同一行状态。❌ 先查再改（check-then-act）：两个都查到"待支付"，都改成功 → 既标记已支付又释放库存。✅ `UPDATE ... WHERE status=10`：数据库行锁保证**只有一个赢**，输方按当前状态走分支（已支付→忽略关单；已关闭→自动退款）。这就是 stage4/02 竞态推演的答案。

### ② 回调幂等（渠道会重发，可能同一单回调 N 次）

| 防线 | 手段 | 出处 |
|------|------|------|
| 第一层 | 回调流水表：渠道流水号**唯一索引**，重复回调 INSERT 失败即跳过 | mq stage3/02 两层幂等 |
| 第二层 | 状态机 CAS：`WHERE status=10` 天然只生效一次 | 本文① |
| 兜底 | 就算重复处理了，下游消费 `order.paid` 事件还有自己的幂等 | mq-mall 消费端 |

### ③ 掉单补偿（回调不来怎么办）

```
渠道回调（主路径）  →  30 秒没收到？  →  主动查单（调渠道查询接口，定时任务扫"待支付超 5 分钟"的单）
                          ↓                              ↓
                     正常推进                     查到已支付 → 补状态（本地消息表发事件）
                                                  查到未支付 → 继续等/到期关单
最后防线：T+1 对账（见④）—— 前面全漏了它兜住
```

**双保险思想**与订单超时关闭完全同构（mq stage4/02：延迟消息为主、扫表兜底）——**异步主路径 + 定时补偿**是处理"第三方不可靠"的通用范式。

### ④ 资金安全：三单对账 + 金额防线

```
每日 T+1 三单核对：平台支付流水  vs  渠道账单文件  vs  订单状态
  ├─ 渠道有、平台无   → 掉单：补单（回调+查单全漏了）
  ├─ 平台有、渠道无   → ❌ 严重：钱没收却标已支付（伪造回调没验签？）
  └─ 两边都有、状态没改 → 补状态 + 告警（为什么补偿任务也漏了）
差错进"差错池"：自动能修的自动修（补状态/退款），修不了的人工——mq-mall reconcile 的生产版
```

**金额两条铁律**：①金额单位一律**分（long）**，❌ double（0.1+0.2≠0.3，钱上不允许浮点）；②回调金额必须与本地订单金额**比对一致**才处理——否则用户 1 分钱下单回调改 100 元订单。③回调**验签**（渠道签名校验），防伪造回调——上面"平台有渠道无"的事故多半就是验签没做。

## 追问预演

①"**多渠道**（微信+支付宝）怎么设计？"→ 渠道适配层（策略模式，接口：下单/查单/退款/对账下载），路由层按配置选渠道——PaymentChannel 接口 + 微信/支付宝实现，新增渠道零改动主流程（06 篇设计模式的实际用途）；②"**退款**怎么设计？"→ 退款单独立表+状态机，同样回调驱动，原路退回，与支付单关联可追溯；③"支付回调为什么不用 MQ 解耦直接改库？"→ 回调处理本身要轻（验签+落流水+CAS），重活（通知/积分/发货）靠 `order.paid` 事件异步化——回调慢了渠道会判定失败重发，雪崩。

## 面试问法

**Q: 设计一个支付系统？**
A: 四关卡：①**状态机+CAS**——`UPDATE WHERE status=待支付` 一条语句解决支付回调与关单的并发竞态，输方按当前状态分支；②**回调幂等**——渠道流水号唯一索引 + 状态 CAS 双层防重；③**掉单补偿**——不信任同步结果，异步回调为主 + 定时查单补偿，T+1 三单对账兜底（平台流水/渠道账单/订单状态）；④**金额安全**——单位用分、回调金额比对、验签防伪造。下游用本地消息表发 `order.paid` 事件异步解耦，多渠道走策略模式适配层。
