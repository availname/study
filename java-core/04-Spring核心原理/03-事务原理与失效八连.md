# 03 · 事务原理与失效八连 ★★★

`@Transactional` 是 Spring 最常用的注解，也是**生产事故最密集的注解**。本篇 = 原理（AOP+ThreadLocal 连接绑定）+ 传播行为七种 + **失效八连**（每条都有错误代码与修复）。

## 原理：事务就是一个 AOP 环绕通知

```
调用 orderService.pay()
  → 代理拦截（TransactionInterceptor）
      → 从连接池取连接 → setAutoCommit(false)     ← 开启事务
      → 连接绑定到 ThreadLocal（DataSourceTransactionManager 持有）
  → 执行你的方法（方法里的 DAO 全用这个连接）
  → 正常返回 → commit | 抛 RuntimeException → rollback
  → 连接归还池
```

**三个关键认知**：

1. **事务边界 = 连接边界**：同一事务内的 SQL 必须用同一个连接；连接靠 **ThreadLocal** 绑定到当前线程——所以"事务内开子线程写库"不在同一事务（失效八连之一）
2. **@Transactional 是 AOP**：所以 AOP 失效场景（自调用等）全部适用
3. **`TransactionSynchronizationManager.isActualTransactionActive()`** 能查"当前有无事务"——mq-mall 的 `sendInTransaction` 强制事务纪律用的就是它（你在 community 又见过一次）

## 传播行为七种（重点前三个）

| 传播行为 | 语义 | 场景 |
|---------|------|------|
| **REQUIRED**（默认） | 有事务就加入，没有就新建 | 绝大多数业务方法 |
| **REQUIRES_NEW** | **挂起当前事务，开个新事务**（各自独立提交/回滚） | 操作日志/审计——主业务回滚，日志也要留下 |
| **NESTED** | 嵌套事务（savepoint）：内层回滚不影响外层，外层回滚连带内层 | 部分失败可容忍的批处理 |
| SUPPORTS | 有就加入，没有就非事务执行 | 查询类 |
| NOT_SUPPORTED | 挂起当前事务，以非事务执行 | 长操作不想占事务 |
| MANDATORY | 必须已有事务，否则抛异常 | 强制要求被事务包裹的基础方法 |
| NEVER | 必须没有事务，否则抛异常 | 极少 |

```java
@Transactional
public void pay() {
    auditLogService.record(payInfo);     // record 用 REQUIRES_NEW：支付回滚，审计仍保留
    ...支付主逻辑（回滚时不影响 auditLog 已提交的记录）
}
```

**REQUIRES_NEW 的注意**：内层用的是**另一个连接**（外层连接被挂起）——两事务操作同一行会互相等锁，注意死锁。

## 失效八连（逐条：现象 → 根因 → 修复）

### 失效 ①：自调用（最高频，no.1）

```java
@Transactional
public void create() { ... }

public void batchCreate() {
    this.create();       // ❌ this.create 走原始对象，事务失效！
}
```

根因：AOP 代理拦截"从外面调进来"的调用；`this.create()` 是对象内部调用，不经代理。修复：拆 bean（mq-mall 的 `SeckillOrderTxWorker`）/ @Lazy 注入自己 / getBean。（详见 [02-AOP 篇](02-AOP原理.md)）

### 失效 ②：方法不是 public

CGLib 生成的子类只能重写 public/protected 可覆盖方法；Spring 事务拦截器只对 public 方法生效（非 public 直接跳过事务增强，不报错）。**修复：加 public**。配合 mq-mall 教训："@Transactional 标注在 protected 方法上自调用"双重失效。

### 失效 ③：异常被 try-catch 吞掉

```java
@Transactional
public void pay() {
    try {
        doPay();                       // 内部出错
    } catch (Exception e) {
        log.error("出错了", e);        // ❌ 吞了！代理看不到异常 → 正常提交
    }
}
```

修复：catch 后**重新抛出**；或手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` 标记回滚。

### 失效 ④：默认只回滚 RuntimeException 和 Error

```java
@Transactional                              // 默认 rollbackFor = RuntimeException/Error
public void pay() throws IOException {
    throw new IOException("受检异常");       // ❌ 受检异常不回滚！数据照常提交
}
```

修复：`@Transactional(rollbackFor = Exception.class)`——**团队规约：一律显式写 rollbackFor**。

### 失效 ⑤：事务内多线程

```java
@Transactional
public void pay() {
    new Thread(() -> orderDao.insert(...)).start();   // ❌ 子线程用的是新连接，不在本事务！
}
// 主线程提交了，子线程的插入自己提交（或失败）——与主事务无关
```

根因：事务绑定 ThreadLocal 连接，子线程是新的 ThreadLocal。修复：子线程操作独立小事务（各自 @Transactional）；或改为发 MQ 由消费者处理。

### 失效 ⑥：存储引擎不支持

MyISAM 不支持事务（表锁引擎）——表必须 InnoDB。现代 MySQL 8 默认 InnoDB，老系统迁移时注意。

### 失效 ⑦：类没被 Spring 管理 / @Transactional 标在接口上

- `new OrderService()` 出来的对象没有代理 → 无事务
- `@Transactional` 写在接口方法上：CGLib 代理模式下**不生效**（注解要写在实现类的 public 方法上）

### 失效 ⑧：传播行为/嵌套调用误用

```java
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public void bigExport() { ... }              // 挂起事务执行——内层调用的 @Transactional 全失效
```

以及 REQUIRES_NEW 内外操作同一行：外层锁未放、内层等锁 → 死锁/超时（[MySQL 锁篇](../03-MySQL深入/03-锁体系.md) 案例二同款）。

## 失效八连检查清单（code review 用）

```
□ 方法是 public 且在 Spring 管理的 Bean 里？
□ 调用是否来自外部代理（没有 this 自调用）？→ 拆 bean / @Lazy self
□ rollbackFor = Exception.class 显式写了？
□ 异常没有在方法内被静默捕获？
□ 事务内没有 new Thread / 线程池提交？
□ 操作的表是 InnoDB？
□ 传播行为选对了吗（跨 bean 调用时的内外事务关系）？
□ 需要事务提交后执行的动作用了 afterCommit 而不是方法末尾？
```

## 面试问法

**Q: @Transactional 失效的场景有哪些？**
A: 按根因分三类——①**没走代理**：自调用 this、非 public、final/static、对象不是容器管理、注解标在接口；②**异常相关**：异常被 catch 吞掉、受检异常默认不回滚（要 rollbackFor=Exception.class）；③**线程与传播**：事务内多线程（ThreadLocal 连接隔离）、传播行为误用、存储引擎不支持。修复都要落到"走代理+显式 rollbackFor+异常上抛"。追问加分：事务通过 ThreadLocal 绑定连接实现，故跨线程必然失效。

**Q: 传播行为 REQUIRES_NEW 和 NESTED 的区别？**
A: REQUIRES_NEW 用**新连接开独立事务**，内外完全隔离（外回滚不影响内已提交），外层事务被挂起；NESTED 用 **savepoint 存档点**在同一个连接里，内层回滚到存档点不影响外层，外层回滚连带内层。REQUIRES_NEW 注意两连接操作同一行的锁问题。
