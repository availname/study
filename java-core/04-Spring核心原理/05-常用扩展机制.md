# 05 · 常用扩展机制：把 Spring 用成"自己的框架"

Spring 的强大在于**扩展点体系**：BeanPostProcessor（改 Bean）、Event（进程内广播）、Import/Conditional（装配开关）。你项目里已经"受益于"它们，这一篇教你"使用它们"。

## 一、BeanPostProcessor：每个 Bean 的加工流水线

```java
@Component
public class TimingBeanPostProcessor implements BeanPostProcessor {
    @Override
    public Object postProcessBeforeInitialization(Object bean, String name) {
        if (bean instanceof NeedsSpecialHandling special) special.prepare();   // 按"特征"加工
        return bean;
    }
    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        if (bean.getClass().isAnnotationPresent(Monitored.class)) {
            return MonitorProxy.wrap(bean);      // 返回代理替换原 Bean —— AOP 就是这么做的
        }
        return bean;
    }
}
```

**你在用的 BeanPostProcessor（看到了吗）**：
- `AutowiredAnnotationBeanPostProcessor`：处理 @Autowired/@Value（② 属性注入阶段）
- `AnnotationAwareAspectJAutoProxyCreator`：生成 AOP 代理（⑥ 阶段）
- `CommonAnnotationBeanPostProcessor`：处理 @PostConstruct/@PreDestroy/@Resource

**使用纪律**：BPP 会对**所有 Bean** 执行，逻辑要轻；不要在其中触发其它 Bean 的初始化（早初始化破坏生命周期）。

## 二、ApplicationEvent：进程内的"MQ"

MQ 教学 stage1 讲过"事件驱动解耦"——Spring 的进程内版本：

```java
// 定义事件（任意 POJO）
public record PostPublishedEvent(Long postId, Long authorId) {}

// 发布（同步默认；@TransactionalEventListener 可挂到事务提交后——比 afterCommit 更优雅的姿势！）
publisher.publishEvent(new PostPublishedEvent(postId, authorId));

@Transactional
public void publish(...) {
    db.update(...);
    eventPublisher.publishEvent(new PostPublishedEvent(...));   // 事务内发布
}

// 监听（加事务注解：事务提交后才执行——天然解决"提交后再发 MQ/发通知"）
@EventListener
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onPublished(PostPublishedEvent e) {
    rabbitTemplate.convertAndSend(...);   // 此时事务必已提交，无"读未提交"问题
}
```

**进程内 Event vs MQ 的选型**：

| | Spring Event | MQ |
|--|-------------|-----|
| 边界 | 同进程 | 跨进程 |
| 异步 | 默认同步（@Async 异步） | 天然异步 |
| 可靠性 | 内存（重启丢） | 持久化 |
| 用途 | 模块间解耦（单体！） | 服务间解耦 |

**单体阶段的正确姿势**：先用 Spring Event 解耦模块（成本低），等拆服务时把 `@EventListener` 平滑替换成 MQ 消费者——**事件语义不变，传输机制升级**。

## 三、配置体系：@Value / @ConfigurationProperties / Environment

```java
@Value("${mq.mall.order-timeout-ms:120000}")   // 单值 + 默认值（mq-mall 拓扑配置在用）
private long orderTimeoutMs;

@ConfigurationProperties(prefix = "spring.data.redis.lettuce.pool")   // 一组配置绑对象
```

- 占位符 `${key:default}` 的解析发生在 **BeanFactoryPostProcessor 阶段**（配方修改）——所以 @Value 失效要检查 key 拼写与 PropertySource 加载顺序
- `Environment.getProperty()` 运行时动态读取（结合 Nacos 刷新实现"动态线程池"参数——并发篇 05 的生产做法）

## 四、装配开关：@Import 与 @Conditional

```java
@Import({MyCoreConfig.class, MyHelper.class})          // 直接引入组件（自动化配置的积木）
@Bean
@ConditionalOnProperty(name = "feature.seckill", havingValue = "true")   // 配置开关
public SeckillService seckillService() { ... }
```

**Boot 自动装配的原理链**（面试加分）：

```
@SpringBootApplication
  └─ @EnableAutoConfiguration
       └─ AutoConfiguration.imports 文件（spring-boot-autoconfigure 里列了 100+ 配置类）
            └─ 每个配置类带 @ConditionalOnClass/@ConditionalOnMissingBean...
                 → classpath 有 Redis 类 + 你没自定义 → 自动装配 RedisTemplate 等
```

这就是 stage6/07（Testcontainers @ServiceConnection）与"yml 重试配置需要 spring-retry 才生效"（踩坑）背后的机制——**条件装配让一切自动，也让失效静默**。

## 扩展点全景表（知道什么时候找哪个钩子）

| 需求 | 扩展点 |
|------|--------|
| 改 Bean 配方（占位符/属性） | BeanFactoryPostProcessor |
| 加工 Bean（代理/校验） | BeanPostProcessor |
| 容器就绪后执行 | ApplicationRunner / CommandLineRunner / @EventListener(ApplicationReadyEvent) |
| 生命周期钩子 | @PostConstruct / @PreDestroy |
| 优雅停机 | @PreDestroy + SmartLifecycle.stop |
| 动态注册 Bean | ImportBeanDefinitionRegistrar |
| 环境隔离 | @Profile / @Conditional |

## 面试问法

**Q: Spring 有哪些扩展点？你用过哪些？**
A: Bean 级：BeanPostProcessor（AOP 代理生成处）/ BeanFactoryPostProcessor（占位符解析处）；生命周期：@PostConstruct/@PreDestroy/InitializingBean/DisposableBean；事件：ApplicationEvent + @TransactionalEventListener(AFTER_COMMIT) 解决"提交后再发消息"；装配：@Import/@ConditionalOnXxx（Boot 自动装配原理）；Runner：ApplicationRunner 启动后执行。实战例：秒杀库存预热用 @PostConstruct、发 MQ 用 AFTER_COMMIT 事件替代手动 afterCommit 注册。
