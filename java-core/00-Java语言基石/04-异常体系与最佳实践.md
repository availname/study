# 04 · 异常体系与最佳实践

异常处理写不好 = 生产事故看不到现场。本篇：异常层次、正确姿势、六个反模式。

## 异常家族树

```
Throwable
 ├─ Error                JVM 级严重错误（OOM/StackOverflow）——不要捕获，修代码
 └─ Exception
     ├─ RuntimeException（非受检）—— 编程 bug：NPE/数组越界/ClassCast/IllegalArgument
     │    编译器不强制处理 → 一般不 catch，让它炸出来暴露问题
     └─ 受检异常（IOException/SQLException...）—— 外部依赖失败：文件/网络/DB
          编译器强制 try-catch 或上抛 → 必须处理（重试/降级/转业务异常）
```

**选择原则**：
- **业务错误**（库存不足/参数非法）→ 自定义 `BizException extends RuntimeException`（项目里的做法）——让全局异常处理器统一转成响应
- **系统错误**（DB 挂了/网络失败）→ 保留原始异常上抛或包装，**不吞**

## 正确姿势五条

```java
// ① 异常链：保留现场（别丢掉根因）
catch (SQLException e) {
    throw new BizException("查询失败", e);     // 传入 cause！new BizException(msg) 丢栈=毁尸灭迹
}

// ② try-with-resources：自动关闭（AutoCloseable）
try (var conn = pool.borrow(); var ps = conn.prepareStatement(sql)) {
    ...                                       // 无论是否异常都自动 close（顺序逆序）
}

// ③ 全局兜底 + 业务细分（@RestControllerAdvice——community 已实现）
// ④ 日志带堆栈：log.error("转账失败 orderNo={}", no, e);   ← e 放最后一个参数
// ⑤ 业务校验前置：if (stock < 1) throw new BizException("库存不足")——别让异常当流程控制
```

## 异常反模式六连（每条都是真实代码里常见）

| 反模式 | 为什么烂 | 正确 |
|--------|---------|------|
| ① `catch (Exception e) {}` 吞掉 | 出错无感知，数据静默丢失（**坑二"无报错丢数据"同源**） | 至少 log.error 带堆栈 |
| ② `e.printStackTrace()` | 输出格式乱、生产环境看不到 | 用日志框架 `log.error("...", e)` |
| ③ catch Exception 后 return null | 调用方 NPE 延迟爆炸 | 抛业务异常或返回 Optional |
| ④ 用异常做流程控制 | 异常构造+栈捕获极贵（微秒级） | if 前置校验 |
| ⑤ catch (Throwable) / catch Error | 连 OOM 都想捞——捞不住还掩盖 | 只 catch Exception 及以下 |
| ⑥ finally 里 return | 吞掉 try/catch 里的异常与返回值 | finally 只做资源清理 |

## 面试问法

**Q: 受检异常和非受检异常怎么选？**
A: 受检（Exception 子类非 Runtime）= 可预期、可恢复的外部失败（网络/IO）→ 强制调用方处理；非受检（RuntimeException）= 编程错误或业务规则失败 → 不强制捕获，让全局处理器兜底。项目实践：业务失败抛自定义 BizException（Runtime 子类），由 @RestControllerAdvice 统一转响应；包装底层异常时必须传 cause 保留堆栈。

**Q: try-with-resources 原理？**
A: 编译器把资源声明转换为 try-finally + close() 调用（AutoCloseable），多资源逆序关闭，异常抑制机制（getSuppressed）保留主异常的同时不丢失关闭时的次异常——比手写 finally close 更安全简洁。
